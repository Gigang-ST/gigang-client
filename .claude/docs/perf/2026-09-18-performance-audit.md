## 1. 근본 원인 — 메모리 부족 → 상시 스왑

### 1-1. 증상: 쿼리 내용과 무관하게 모든 문장이 같은 배율로 부푼다

| 문장 | min | mean | max |
|---|---|---|---|
| `set_config(...)` — PostgREST가 요청마다 거는 세션 설정. **테이블 접근 0, I/O 0** | **0.02ms** | 6.10ms | 1,842ms |
| `get_team_story_feed` | 16.5ms | 1,092ms | 9,712ms |
| `get_team_ghost_members` | 2.4ms | 395ms | 8,443ms |
| `get_public_member_card` | 8.7ms | 396ms | 9,958ms |
| `get_team_recent_title_grants` | 3.9ms | 569ms | 7,080ms |

`set_config`는 **어떤 인덱스로도 어떤 SQL 튜닝으로도 빨라지지 않는 문장**이다. 그게 305배

### 1-3. ⭐ 대조 실험 2건 — "우리 탓인가"를 가른다

이 점검의 핵심 증거다. **원인을 우리 앱이 아니라 등급으로 확정한 근거.**

#### 대조군 1: dev 프로젝트 (스키마 동일 · 트래픽 1/8)

| | prd | dev |
|---|---|---|
| 등급 | 동일 (`shared_buffers` 224MB · `max_connections` 60) | 동일 |
| 스키마 | 함수 113개 | 함수 119개 (사실상 동일) |
| DB 크기 | 43MB | 32MB |
| **DB 작업량** | **12.7분/일** | **1.57분/일 (1/8)** |
| `set_config` min → mean | 0.02 → 6.10ms (**305배**) | 0.015 → 1.21ms (**82배**) |
| `set_config` 최대 멈춤 | 1,842ms | **630 ~ 1,191ms** |

→ **1/8 부하인 dev도 82배 부풀고 1초씩 멈춘다.** 트래픽·데이터 양은 원인이 아니다.
→ 단, dev는 **같은 스키마**라 "스키마 복잡도" 변수는 못 가른다. 그래서 대조군 2가 필요했다.

#### 대조군 2: 개인 프로젝트 (스키마 무관 · 거의 미사용)

| | 값 |
|---|---|
| **총 RAM** | **408 MB** ← Nano는 0.5GB. 이게 전부다 |
| Used | 184 MB (45%) |
| Cache + Buffers | 207 MB (51%) |
| **Free** | **16.9 MB (4.1%)** |
| **Swap 사용 중** | **216 MB (53%) — 24시간 내내** |
| Committed / Limit | **1.12 GB / 1.2 GB (93.3%)** |

→ **아무것도 안 하는 사이트가 216MB를 스왑하고 여유 메모리가 16.9MB다.**
→ **Supabase 무료 등급은 코드가 0줄이어도 한계의 93%를 쓴다. 확정.**

#### 두 프로젝트의 차이 = 우리 앱의 몫

| | 빈 프로젝트 | 기강 prd | 차이 |
|---|---|---|---|
| 총 RAM | 408 MB | 411 MB | 동일 |
| **Swap (실사용)** | 216 MB | 250~300 MB | **+50~80MB** ← 실제 추가 사용 |
| **Committed (예약)** | 1.12 GB | 1.4 GB | **+약 280MB** ← 예약이지 실사용 아님 |
| Limit 대비 | 93.3% | **약 117%** | **우리만 벽을 넘었다** |

```
                RAM 408MB              스왑 약 800MB (디스크)
         ├───────────────────┤├──────────────────────────────┤
         0                408MB                           1.2GB ← Commit limit

빈 프로젝트 ███████████████████ + ██████                        1.12GB 예약 (93%)
기강 prd    ███████████████████ + ████████                  ──▶ 1.4GB 예약 (117%)
                                                                ↑ 벽 넘음 = OOM 위험
```

**결론: 무료 등급이 구조적으로 모자란 게 먼저고(93%), 우리 앱이 그걸 벽 너머로 밀었다(117%).**

### 1-4. 스왑이란 무엇이고 왜 치명적인가

RAM이 꽉 차면 커널이 안 쓰는 메모리 페이지를 **디스크에 내다 놓는다**. 나중에 그 페이지가
필요하면 디스크에서 다시 읽어온다.

| | 접근 시간 |
|---|---|
| RAM 읽기 | 약 **0.0001 ms** |
| 디스크(스왑) 읽기 | 약 **0.1 ~ 수 ms** |

**1,000~10,000배 차이.** 이게 `set_config`가 0.02ms → 1,842ms가 된 이유다. 쿼리가 복잡해서가
아니라 그 쿼리를 돌릴 메모리가 디스크에 나가 있어서다. **어느 페이지가 나가 있는지는
무작위**라, 쿼리 종류와 무관하게 아무거나 걸린다.

> **스왑은 원래 비상용**이다. 평소엔 0이고 사고 날 때만 써야 한다.
> 그런데 여기선 **빈 프로젝트조차 216MB를 24시간 내내** 쓴다 — 비상용이 아니라 상시 가동이다.
> **그래서 "가끔 느린" 게 아니라 "평소에도 느린" 것이다.**

### 1-5. Commit limit이 RAM보다 큰 이유 (0.5GB인데 왜 1.2GB인가)

```
Commit limit = RAM + 스왑 공간
1.2 GB (limit) − 0.4 GB (실제 RAM) = 약 0.8 GB  ← 스왑 공간
```

리눅스는 "메모리를 예약해 줄 수 있는 총량"을 따질 때 디스크의 스왑 공간까지 쳐준다.

> **Supabase가 Nano에 RAM의 두 배나 되는 스왑을 붙여놨다는 것 자체가,
> "0.5GB로는 이 스택이 안 돌아간다"는 설계상의 인정이다.**

### 1-6. Committed(예약) vs Memory usage(실사용) — 헷갈리면 오진한다

| | Memory usage | Memory commitment |
|---|---|---|
| 재는 것 | **실제로 쓰고 있는** 물리 메모리 | 프로세스들이 **달라고 예약해 둔** 총합 (`Committed_AS`) |
| 한계선 | 물리 RAM (408MB) | Commit limit (1.2GB = RAM + 스왑) |
| 넘으면 | **스왑 → 느려짐** | **OOM(강제 종료) 위험** |

비유하면 Committed는 **은행이 승인한 대출 한도의 합**, Memory usage는 **실제로 인출한 돈**,
Commit limit은 **금고에 있는 돈**이다. 프로그램은 보통 예약만 하고 다 안 쓰므로
**Committed가 RAM보다 큰 건 정상**이다. 문제는 **Commit limit을 넘을 때**다.

**그래서 우리 증상은 하나가 아니라 둘이다:**

| 숫자 | 증상 |
|---|---|
| Swap 250~300MB | **느린 이유.** 지금 겪는 그것 |
| Committed 117% | **터질 위험.** Postgres·Realtime이 커널에 강제 종료될 수 있음 = **사이트 다운** |

> 실제 실사용은 RAM 408 + 스왑 약 280 = **약 690MB**다(1.4GB를 물리적으로 쓰는 게 아니다).
> 500MB짜리 기계가 690MB를 쓰고 있다.
> ⚠️ **간헐적 재시작·OOM이 실제로 있었는지는 `Logs → Postgres`에서 확인 필요** (미확인 항목).

### 1-7. 무엇이 램을 채우는가 — 데이터가 아니라 서비스 개수다

| 근거 | 수치 |
|---|---|
| DB 데이터 전체 | 43MB |
| 그런데 `shared_buffers` 하나가 | **224MB** — **prd(43MB)와 dev(32MB)가 값이 똑같다** = 등급이 정한다 |
| 클라이언트 연결 수 | prd **6** / dev **5** — 그리고 **우리 앱이 직접 연 건 0개** |

연결 6개의 정체: `postgrest` 3 · `postgres_exporter` 1 · `mgmt-api` 1 · 익명 1 —
**전부 Supabase 인프라다.** 우리 앱은 DB에 직접 연결하지 않고 PostgREST에 HTTP로 말을 건다.

Supabase는 한 인스턴스에 **Postgres · PostgREST · GoTrue · Realtime(BEAM VM) ·
Supavisor 풀러(또 다른 BEAM VM) · Storage API(Node) · Kong · pg_meta(Node) · 로그 수집기**를
전부 함께 올린다. 전체 테이블 108개 중 **50개가 Supabase 자기 것**(`auth` 27 · `realtime` 11 ·
`storage` 8 · 기타 4)이다 — 빈 프로젝트도 이걸 다 돌린다.

**우리가 그 위에 더한 것**(=Committed +280MB의 정체로 추정):

| | 왜 메모리를 먹나 |
|---|---|
| **스키마 복잡도** — 테이블 52 · 함수 113 · 컬럼 820 · RLS 117 | PostgREST·pg_meta가 **스키마 전체를 메모리 캐시로** 들고 있다 |
| `wal_level = logical` + Realtime 실사용 | 로그인 사용자 전원이 `noti_mst` 구독 → BEAM VM이 구독 수만큼 |
| Storage(사진) 사용 | Storage API(Node) 상주 |

> ⚠️ **서비스별 메모리 배분은 측정이 아니라 추정이다** — DB 바깥 프로세스 메모리는 SQL로 못 본다.
> 측정된 건 스키마 규모·연결 수·스왑 패턴이다.

### 1-8. 폐기된 가설 — CPU 버스트 크레딧 소진 (기록으로 남긴다)

처음엔 "공유 CPU 버스터블의 크레딧 소진"으로 진단했다. **틀렸다.**

1. **CPU 7일 피크가 40%** — 천장에 안 붙는다.
2. **146일 평균 DB CPU가 0.01 코어**(총 31.0시간 / 146.6일). 이 부하로 크레딧이 바닥날 수 없다.

같은 이유로 **"트래픽이 적으니 작은 인스턴스로 충분하다"는 추론은 CPU에 대해서만 맞다.**
메모리는 고정 비용이라 그 논리가 성립하지 않는다.

> **다음에 "느리다"는 제보가 오면 순서**: ① Reports → Database의 **Swap** ② Disk IO ③ CPU.
> 우리 규모에서 CPU가 범인인 경우는 아직 없었다.

### 1-9. 측정 도구의 함정 두 가지 (실제로 둘 다 걸렸다)

1. **`track_io_timing`이 `off`다.** `pg_stat_statements`의 `shared_blk_read_time`이 전부 0.00으로
   나오는데, 이걸 "디스크 I/O가 없다"로 읽으면 안 된다. `shared_blks_read = 0`은 **읽기 캐시
   히트**만 뜻하고 쓰기·WAL·**스왑 IO는 애초에 안 잡힌다.**
2. **7일 그래프는 분 단위 평균이라 1초 미만의 순간 포화를 못 본다.** "CPU 평균 40%"는
   "수백 ms짜리 100% 스파이크가 자주 있음"과 양립한다. 그래프로 무언가를 **배제**할 때는
   샘플링 주기를 먼저 확인할 것.

## 2. DB — 실제로 버리고 있는 일

전체 DB CPU 31.0시간 중 **46.5%가 앱 쿼리가 아니라 인프라 오버헤드**다.

| 소비처 | 시간 | 비중 |
|---|---|---|
| Realtime (WAL 디코딩 + 구독 갱신 + 퍼블리케이션 조회) | 12.0h | **38.7%** |
| PostgREST 스키마 캐시 재적재 | 2.4h | 7.7% |
| 앱 RPC 전체 | 약 9.7h | 약 31% |

### 2-1. Realtime 38.7% — 그중 절반은 죽은 기능 (무손실 개선)

```
supabase_realtime 퍼블리케이션: cmnt_mst, msg_mst, noti_mst, pldg_mst
```

| 테이블 | 상태 |
|---|---|
| `cmnt_mst` | 살아있음 (댓글 — `comment-section.tsx`, `use-post-comments.ts`) |
| `noti_mst` | 살아있음 (알림 벨 — `notification-bell-icon.tsx`) |
| `msg_mst` | **죽음** — `SHOW_MESSAGE_PLANES = false`. 구독 컴포넌트가 렌더되지 않음 |
| `pldg_mst` | **죽음** — `SHOW_PLEDGE_LEDE = false`, `SHOW_PLEDGE_SIGNS = false`. **살아있는 행 0개**, 구독 `.channel()` **코드에 없음** |

> ⚠️ **철회 (2026-09-18).** 여기 적었던 **"`msg_mst`·`pldg_mst`를 퍼블리케이션에서 빼자"는
> 안은 폐기했다.** 실측 결과 두 테이블의 **INSERT 누적이 0건**이라 WAL에 아무것도 안 흘러
> 절약이 **정확히 0**이다. 코드 상태(구독 없음)만 보고 비용을 어림한 실수였다 — §6 응원
> 총합과 같은 패턴이고, 둘 다 **"안 쓰는 것"과 "비용이 드는 것"을 혼동한 것**이다.
> 위 표는 *어느 구독이 살아 있나*를 적어 둔 기록으로만 남긴다. 빼 봐야 이득이 없고,
> 나중에 두 기능을 되살릴 때 마이그레이션만 한 번 더 들게 된다.
>
> Realtime 38.7%의 실제 뿌리는 **연결 재수립 연쇄**다(§2-2).

> **문서 결함(정정 완료)**: `DESIGN.md`는 "꽂으면 `pldg_mst` Realtime 구독으로 열린 모든
> 화면이 함께 갱신된다"고 단언했는데 **그 구독은 코드에 존재하지 않는다**(전체 grep에서
> `pldg` 채널 0건). 2026-09-18 서술을 고쳤다.

**구조적 참고**: 로그인 사용자는 어느 탭에 있든 `noti_mst`를 구독한다. **Realtime 구독 수 ≈
동시 접속 로그인 사용자 수**이고, 폴링 1회 비용이 구독 수에 비례한다. 알림 설계의 의도된
대가라 그대로 두되, **퍼블리케이션에 테이블을 추가할 때는 이 곱셈을 기억할 것.**

> 구독을 **누가 들고 있는지는 이 PR에서 바뀌었다.** 예전엔 `HeaderActions` →
> `NotificationBellIcon`이었는데, 벨은 탭마다 헤더 안에서 죽고 태어나므로 이동할 때마다
> 구독이 끊겼다 붙었다(§3-2). 지금은 루트 레이아웃의 `NotificationChannel` 하나가 소유하고
> 벨은 store를 **읽기만** 한다. **구독 수 자체는 안 변한다**(사람당 하나) — 줄어든 건
> 재구독 횟수다.

### 2-2. PostgREST 스키마 캐시 재적재 7.7% — **조사 완료: §1의 증상이다**

| 문장 | 호출 | mean | min |
|---|---|---|---|
| `SELECT name FROM pg_timezone_names` | 9,659 | **709.2ms** | 52.2ms |
| 도메인 base_types 재귀 조회 | 9,685 / 9,330 | 127.7 / 85.4ms | |

세 쿼리의 호출 수가 거의 같다 — **한 번의 스키마 캐시 적재가 약 9,600회 돌았다**는 뜻이다.
`pg_timezone_names`는 OS 타임존 DB를 훑어 **최소 52ms**로 원래 무거운 쿼리다(환경 배율과 별개).

**원인은 마이그레이션이 아니라 PostgREST 재시작이었다.** `postgrest_logs` 최근 24시간:

| 메시지 | 횟수 |
|---|---|
| `Successfully connected to PostgreSQL 17.6…` | **106** |
| `Connection Pool initialized with a maximum size of 10 connections` | **106** |
| `Config reloaded` | **106** |
| `Schema cache loaded 52 Relations, 51 Relationships, 65 Functions, … 1196 Timezones` | **105** |
| `Received a schema cache reload message on the "pgrst" channel` | 246 |

> ⚠️ **정정 (2026-09-18, 2차 분석).** 처음 이걸 **"프로세스가 하루 106회 재시작"** 이라고
> 적었는데 **틀렸다.** 같은 로그를 다시 뽑으면:
>
> ```
> Starting PostgREST : 0건     Listening on port : 0건     5xx : 0건
> ```
>
> **프로세스는 한 번도 안 죽었다.** 실제로 일어난 일은 **DB 커넥션 풀 10개를 버리고 새로
> 맺으면서 스키마 캐시를 다시 읽는 것**이다. 그래서 요청이 실패하지 않고 **느려지기만** 한다
> — "재시작 순간 에러·연결거부"라고 쓴 것도 틀렸다.
>
> 그리고 연쇄가 밝혀졌다: **Realtime이 DB 연결을 끊었다 다시 붙을 때(하루 33회)
> `realtime.messages` 일별 파티션 DDL이 돌고 → `pgrst_ddl_watch` 이벤트 트리거가
> `NOTIFY pgrst 'reload schema'`를 쏘고 → PostgREST가 풀을 통째로 재생성한다.**
> 비율이 **1(DDL) : 5(reload) : 2(재접속)** 로 매시간 일정하다.
> 즉 위의 `NOTIFY` 246회는 **비용이 아니라 원인**이었다 — 처음엔 "1.2ms로 끝나니 무시"라고
> 치워버렸다.
>
> **`realtime.messages`는 Realtime의 내부 테이블이라 `postgres_changes`만의 문제가 아니다.**
> 접속자 아바타 레이어(presence)가 루트 레이아웃에서 비로그인 포함 전원에게 붙어 있으므로,
> 알림 구독을 전부 떼도 이 연쇄는 남는다.
>
> ❓ **아직 안 풀린 것**: "유휴라서 끊긴다"는 설명이 시간대 분포와 안 맞는다 — 트래픽이
> 제일 많은 KST 22시에 재접속이 **가장 많다(14회)**. 유휴가 원인이면 반대여야 한다.
> 부하(=메모리)가 끊는 것일 가능성이 남아 있다. **2차에서 확인할 것.**

**재시작은 부하에 비례한다** (시간대 분포, KST):

| 시간 | 재시작 |
|---|---|
| **22시 (저녁 피크)** | **14회** |
| 낮 | 2~8회/시간 |
| **03~06시 (새벽)** | **0회** |

정기 재활용이라면 새벽에도 나와야 한다. **부하에 반응하는 재시작**이다.

**Postgres 본체는 멀쩡하다** — `postgres_logs`에 `FATAL`·크래시·OOM 메시지가 0건이다.
대신 `unexpected EOF on standby connection` 33회 + `starting logical decoding for slot` 32회가
찍힌다 → **Realtime도 반복해서 끊기고 재연결한다.** 한 서비스의 버그가 아니라 **여러 서비스가
동시에 불안정**하다는 뜻이고, Postgres가 `shared_buffers`를 선점한 뒤 곁다리(PostgREST=Haskell,
Realtime=BEAM)가 밀리는 메모리 압박의 전형적인 모양이다.

```
메모리 초과 커밋(1.4GB > 1.2GB) → 상시 스왑
  → 자원 부족 / 요청 지연
    → PostgREST 재시작 (하루 106회, 피크에 집중)
      → 스키마 캐시 전체 재적재 (타임존 709ms + 타입 조회)
        → DB CPU 7.7%
```

> ⚠️ **확정이 아니다.** 죽이는 직접 메커니즘을 못 봤다 — ① OOM kill ② 헬스체크 타임아웃 후
> 플랫폼 재시작 ③ 무료 등급 자원 제한 중 로그로는 갈리지 않는다. ①②는 뿌리가 메모리라
> 조치가 같고, ③이면 상향해도 안 줄어든다(다만 새벽 0회 패턴이 ③과 안 맞는다).
> **검증은 §1을 하고 같은 로그 쿼리를 다시 돌리는 것** — 줄면 확정, 그대로면 지원 문의.

### ⭐ 이것이 §1의 심각도를 바꾼다

§1을 "느리다"로만 규정했는데 로그는 조금 다른 얘기를 한다:

| | 기존 인식 | 관측된 것 |
|---|---|---|
| 증상 | 응답이 느림 | **API 계층이 하루 106번 커넥션 풀을 통째로 새로 맺음** |
| 사용자 체감 | 가끔 답답함 | 그 구간의 요청은 **눈에 띄게 느려짐** (실패는 아님 — 5xx 0건) |

**관측된 사실은 여기까지다**: `Successfully connected to PostgreSQL` 106건 + 스키마 캐시
재적재. 프로세스가 죽었다는 증거는 **없다**(`Starting PostgREST` 0건, `Listening on port`
0건, 5xx 0건 — §2-2 정정 블록). 플랫폼 재시작이나 OOM kill은 **미확정 가설**이고, 로그로는
연결 재수립과 갈라지지 않는다.

한 번에 수 초가 걸리고 **저녁 피크에 몰린다.** "가끔 느려요 / 새로고침하면 돼요" 류의
제보가 있었다면 코드 버그가 아니라 **창구가 잠깐 비어 있던 것**일 수 있다.

**연결 재수립 자체가 원인이 아니라 결과**라는 점이 중요하다 — 그걸 막으려 할 게 아니라
그것을 유발하는 자원 부족(§1)을 없애야 한다.

**재확인용 쿼리** (Logs → 쿼리):

```sql
select count(*) from postgrest_logs
where event_message like 'Successfully connected to PostgreSQL%';

select toStartOfHour(timestamp) as hr, count(*)
from postgrest_logs
where event_message like 'Successfully connected to PostgreSQL%'
group by hr order by hr;
```

### 2-3. `get_team_ghost_members` — 주석의 근거가 프로덕션에서 무효

`lib/queries/ghost-members.ts`가 캐시를 안 하는 이유로 적어 둔 문장:

> *"30명 짜리 가벼운 조회라(**실측 2.5ms**, 전량 버퍼 히트) 매 요청 최신값을 읽어도 부담이 없고"*

프로덕션 실측: **평균 395.4ms · 호출 11,458회 · 누적 1.26시간 — RPC 중 2위.**
min이 2.4ms라 당시 측정은 맞았지만, §1의 배율이 붙은 지금은 **홈에서 캐시 없이 도는 가장 비싼
쿼리**다.

**해법 — 설계 의도를 그대로 지키면서 고칠 수 있다.** RPC에서 시드는 정렬에만 쓰이고,
*누가 유령인가*를 정하는 필터는 시드와 무관하다:

```sql
WHERE (la.last_dt < today.d - 100) OR (...)       -- 시드 무관 (누가 대상인가)
ORDER BY md5(mm.mem_id::text || p_seed) LIMIT 30  -- 시드 의존 (누가 앞에 서나)
```

→ **후보 목록만 캐시하고 셔플은 Node에서 시드로 돌린다.** "진입마다 새 조합"이 그대로
유지되고 DB 호출은 캐시 주기에 1회가 된다.

**구현은 TTL을 24시간으로 잡았다**(처음엔 5분으로 적었다). 후보 조건이 "100일 이상 안 나온
사람"이라 하루가 지나도 한두 명 차이고, 만료돼도 stale-while-revalidate라 **기다리는 사람이
없기 때문**이다(§랭킹탭과 같은 규약). `days_ago`만 응답 시점에 다시 계산한다 — 그건 캐시에
담긴 `last_actv_dt`와 오늘의 뺄셈이라 공짜고, 안 하면 캐시가 하루 묵는 동안 "137일째"가
화면에 고정된다.

⚠️ **선행 확인이었던 "`LIMIT 30` 이전 후보가 몇 명인가"가 실제로 문제였다** — RPC 안에
`LIMIT`을 남겨 둔 채 캐시하면 **담기는 30명이 고정**된다(dev에서 30 → 36으로 실증).
마이그레이션 `20260918160000`이 RPC의 정렬·상한을 걷어냈다.

### 2-4. `get_team_story_feed` — 비싼 건 실행이 아니라 **계획**이었다

> ⚠️ **전면 정정 (2026-09-18, 2차).** 여기 적었던 "`upcoming` CTE의 이중 스캔 때문에
> 호출당 37MB를 훑는다"는 **원인 지목이 틀렸다.** 같은 세션 연속 호출로 한계비용을 재보니
> 버퍼의 **2/3이 계획 수립(planning)** 몫이고, `upcoming`은 전체의 **6.7%**였다.
> 아래는 그 실측으로 다시 쓴 것이다.

**측정** (prd, 같은 세션에서 연속 호출해 한계비용을 분리):

| | 버퍼 | 시간 |
|---|---|---|
| 1회 호출 | 5,142 | ~119ms |
| 3회 호출 | 8,534 | ~124ms |
| **추가 1회당(= 순수 실행)** | **1,696** | **~2ms** |
| **계획 수립 몫** | **3,446 (67%)** | **~117ms** |

**이 함수는 일을 2ms어치 하고 계획을 117ms 세운다.** CTE 7개(`today`·`newbies`·`recent_recs`·
`upcoming`·`actv_rank`·`recent_pledges`·`rctn`)에 상관 서브쿼리가 겹겹이라 플래너가 매번
그 구조를 다시 궁리하는데, 실제 데이터는 43MB짜리 작은 DB라 실행은 금방 끝난다.

#### 왜 매번 다시 궁리하나 — §2-2와 같은 뿌리다

계획은 **세션(백엔드 커넥션)에 캐시된다.** 한 번 세우면 그 커넥션이 사는 동안 재사용한다.
그런데 PostgREST가 하루 106회 커넥션 풀을 통째로 버리고 새로 맺으므로(§2-2), 새 커넥션은
계획 캐시가 비어 있어 처음부터 다시 궁리한다.

```
Realtime 재연결 → realtime.messages 파티션 DDL → pgrst_ddl_watch
  → NOTIFY pgrst 'reload schema' → PostgREST 풀 재생성 → 계획 캐시 전멸
```

**그래서 SQL을 아무리 다듬어도 67%는 안 줄어든다.** 오히려 CTE 구조를 건드리면 계획이 더
복잡해질 수도 있다. 이 층에 닿는 건 **§1(RAM)**뿐이다 — 풀 재생성이 멎으면 계획 캐시가
살아남는다.

**알림 벨(2차 검토 B)을 떼도 이 부분은 안 고쳐진다.** 위 연쇄의 방아쇠는 Realtime **연결**
자체이고, presence 레이어가 루트에서 전원에게 붙어 있어 `postgres_changes`를 전부 떼도
Realtime 세션은 남는다. 벨을 떼면 WAL 폴링은 빠지지만 계획 낭비는 그대로다.

#### `upcoming` CTE — 비효율은 진짜지만 고칠 값이 없다

실측 **345버퍼 · 23ms**(전체의 6.7%). 그중 **158버퍼가 `INNER JOIN mem_mst mm` 하나**인데,
이 조인은 **컬럼을 하나도 안 쓴다** — "탈퇴 안 한 멤버만 세자"는 존재 검사를 조인으로 쓴 것이라
`EXISTS`가 맞다. 이 조인이 행을 부풀리는 탓에 `count(DISTINCT)`와 `GROUP BY`까지 딸려 왔다.

⚠️ **`reg_cnt`와 `runners`는 같은 값이 아니다 — 합치려다 숫자를 바꾸게 된다.**
바깥은 `prt_role_cd` 필터가 없고 안쪽은 `= 'participant'`다. 즉 `reg_cnt`는 **응원·자원봉사까지
포함한 등록 인원**, `runners`는 **실제 달리는 사람**이다(prd 실측 participant 179 / cheering 3 /
volunteer 2). "명단 길이로 세면 된다"는 단순 병합은 **동작 변경**이다. 예전 서술("같은 데이터를
두 번 구한다")이 이 차이를 놓쳤다.

**결론: 나쁘게 짜였지만 나쁘게 굴러가진 않는다.** `comp_reg_rel`이 186행이라 비효율이 드러나지
않는다. 등록이 100배쯤 되면 그때 고치는 게 맞고, 지금 손대면 체감 이득 0에 `reg_cnt`가 조용히
바뀔 위험만 진다.

부수적으로 `pledges` CTE는 `SHOW_PLEDGE_*`가 전부 false라 **클라이언트가 버리는 값**을
계산한다(현재 행이 0개라 비용 자체는 작다).

## 3. 서버 로직 — 직렬 왕복

**Vercel `icn1`(서울) · Supabase `ap-northeast-1`(도쿄)** — 리전 배치는 문제가 아니다(RTT 약 30ms).
다만 **직렬 왕복 수**는 그대로 곱해진다.

### 3-0. ⭐ 왜 왕복 줄이기가 메모리를 안 고치는데도 효과가 있나

**스왑 지연은 복권이고, 왕복 횟수는 복권을 몇 장 사느냐다.**

로그인 사용자가 홈에 들어오면 서버가 **순차로** 왕복한다:

```
① getCurrentMember → mem_mst 조회
② getCurrentMember → team_mem_rel 조회      ← ①이 끝나야 시작
③ getStoryReactions (내 응원)               ← ②가 끝나야 시작
④ HeaderActions (알림 카운트 + 목록 20건)
   + 이 사이에 유령회원 RPC 395ms (캐시 없음)
```

**각 왕복마다 "이번엔 스왑에 걸릴까" 주사위를 굴린다.** 한 번만 걸려도 그 페이지는 느려진다.
왕복이 5번이면 걸릴 기회가 5번이다. dev가 1/8 부하로 82배, prd가 305배인 것도 같은 원리다.

→ **§3의 개선은 메모리를 안 고치지만 주사위를 덜 굴리게 한다.** 그래서 유효하다.

### 3-1. `getCurrentMember()` — 인증된 모든 렌더에서 왕복 2회 직렬

`lib/queries/app-member.ts`의 `fetchMemMstWithTeamRel`이 `mem_mst` → `team_mem_rel`을 **순차**로
조회한다 (각 75,345회 / 39,792회 호출). 인덱스는 이미 완벽하다(BitmapOr 3인덱스, 버퍼 4개).
**문제는 왕복이 2회라는 것 하나.** PostgREST 리소스 임베딩으로 1회로 합칠 수 있다:

```ts
.from("mem_mst").select("*, team_mem_rel!inner(*)")
  .eq("vers", 0).eq("del_yn", false).or(orFilter)
  .eq("team_mem_rel.team_id", teamId).eq("team_mem_rel.vers", 0)
```

### 3-2. 알림 20건을 모든 탭 렌더에서 미리 가져온다 — 지연로딩 경로가 죽어 있다

`components/common/header-actions.tsx`가 **5개 메인 탭 전부**에서
`getNotifications(member.id, { limit: 20 })`을 서버에서 부른다. 그런데 벨 컴포넌트:

```ts
// components/notifications/notification-bell-icon.tsx:82
const notificationsLoaded = useRef(initialNotifications !== undefined);
```

`HeaderActions`가 `initialNotifications`를 **항상** 넘기므로(비로그인도 `[]`) 이 ref는 늘
`true`이고, 아래의 "팝오버 처음 열 때 1회 로드" `useEffect`는 **영원히 실행되지 않는다.**

→ 전달을 빼면 모든 탭 렌더에서 DB 조회 1건(누적 41,410회) 제거. 뱃지 카운트는 유지.
**새 코드 없이 이미 구현된 경로를 살리는 것뿐.**

### 3-3. 홈 전광판의 마지막 직렬 구간

`app/(main)/story/page.tsx`가 `Promise.all(...)` 6개를 기다린 뒤
`await getStoryReactions(teamId, member?.id)`를 **순차로** 붙인다. 그 안의
`getReactionTotals(teamId)`(30초 캐시)는 **멤버와 무관하다** — `Promise.all`에 합류시키고
멤버 의존인 `mine`만 뒤에 남기면 왕복 1회가 임계경로에서 빠진다.

**#4 — 알림을 페이지 렌더에서 분리** (`a4b5cdc`)

원래 이 프리로드는 `#314`(2026-06-17)에서 **홈 한 곳** 전제로 들어왔는데, 이후
`HeaderActions`가 전 탭으로 확대되면서 재검토 없이 따라 올라가 여섯 지면이 되었다.
**코드는 안 바뀌고 쓰이는 자리가 6배가 된** 경우다.

구조를 presence와 같은 패턴으로 바꿨다 — **채널 소유와 그리기를 분리한다**:

```
app/layout.tsx  ← 탭 이동(클라이언트 네비게이션)에 안 죽는다

            ↑ 읽기
  각 탭 헤더의 <NotificationBellIcon>   그리기만 (조회 0 · 채널 0)
```

| | 이전 | 이후 |
|---|---|---|
| 서버 렌더가 기다리는 알림 조회 | 2건 × 6지면 | **0건** |
| 탭 이동당 목록·카운트 조회 | 각 1 | **0** |
| 탭 이동당 Realtime 재구독 | 1 | **0** |
| 앱 세션당 알림 요청 | — | **1회** (목록+뱃지 동봉) |

- **뱃지 숫자까지 클라이언트로 내렸다.** 서버에 남기면 여섯 지면의 모든 렌더가 여전히
  알림을 기다린다 — **알림은 페이지 렌더와 무관해야 한다**는 게 이 작업의 원칙이다.
  대가는 세션당 한 번 뱃지가 잠깐 늦게 뜨는 것뿐이고, 탭 이동엔 store에 있어 안 깜빡인다.
- 함께 고친 결함 둘: 받아오는 중 **"아직 알림이 없어요" 오표시**(`loaded` 플래그로 구분),
  `hasMore` 초기값이 `false`가 되어 **무한스크롤이 정지**하던 문제.

**#6 — 응원 총합 임계경로 분리** (`af93091`)

`getStoryReactions` → `getReactionTotals`(공개·캐시) + `getMyReactions`(사용자별)로 쪼개
총합은 `Promise.all`에 합류시키고 내 몫만 뒤에 남겼다. 비로그인은 조회 자체가 사라졌다.

> ⚠️ **효과를 과대평가하지 말 것.** 처음 이 항목을 "임계경로 왕복 1회 제거"로 적었는데
> 사실과 다르다. 앞으로 옮긴 `getReactionTotals`는 **30초 `unstable_cache` +
> stale-while-revalidate**라 평상시 DB 왕복이 0이고, 만료돼도 옛 값을 바로 주므로 사용자가
> 기다리지 않는다. 즉 **대부분 0ms짜리를 병렬로 옮긴 것**이다.
>
> 진짜 비용인 `mine`(비캐시, 로그인 사용자마다 1왕복)은 **멤버에 의존해 병렬화할 수 없어
> 그대로 남아 있다.** 이 변경의 값은 성능이 아니라 구조다 — "공개 집계가 멤버 조회를
> 기다릴 이유가 없다"는 잘못된 직렬을 없앴고, 비로그인은 함수 호출 자체가 사라졌다.
> **#4와 같은 급으로 묶어 읽지 말 것.**

**#3 — 유령회원 후보 캐시** (`e195a8c`)

홈 진입마다 캐시 없이 RPC를 돌았다(평균 395.4ms · 11,458회 · 누적 1.26시간, RPC 중 2위).
캐시를 못 걸던 이유는 **시드가 RPC 인자라 캐시 키가 매번 달라져서**였는데, 시드는 `ORDER BY`
에만 쓰이고 필터는 시드와 무관했다. 필터만 캐시(24h)하고 순서는 JS로 옮겨 둘 다 얻었다.
`days_ago`는 `todayKST()` 기준으로 다시 센다 — RPC 값은 조회 시점 날짜라 캐시에서 낡는다.

주석에 적힌 근거 두 개가 모두 현재 사실과 달라 함께 정정했다:
① "실측 2.5ms" → **프로덕션 평균 395ms**(min은 여전히 2.4ms — 인스턴스가 부풀린 값이 평균이 됐다)
② "대상이 30명 상한보다 많다" → **후보 27명**으로 상한 미달. 전원이 매번 뜨고 시드는 순서만 정한다.

> 🐛 **회귀 테스트가 버그를 잡았다.** 해시에 시드를 뒤에 붙이면(`mem_id + seed`) FNV-1a가
> 마지막 한 바이트만 다른 상태로 끝나 **시드를 바꿔도 상대 순서가 그대로**였다. 시드를 앞에
> 붙여 해결. 테스트가 없었으면 "섞이는 줄 알았는데 안 섞이는" 채로 배포됐다.

구버전 오버로드 `get_team_ghost_members(uuid)`도 지웠다(상한 8명·오래된 순·`never_actv` 없음).
인자 하나만 빠져도 조용히 그쪽이 걸려 화면이 가입일을 "최종 목격"이라 찍는다.
**dev 적용 완료 / prd 미적용.** 앱은 `p_seed`를 명시해 배포 순서와 무관하게 안전하다.

**#5 — 멤버 조회 조인 1회** (`d4c0743`)

`getCurrentMember()`의 관문이라 호출 수가 어떤 쿼리보다 많다(`mem_mst` 75,345 /
`team_mem_rel` 66,586). **인덱스는 이미 완벽했고**(`BitmapOr` 3인덱스 · 버퍼 4개)
문제는 왕복이 2회라는 것 하나였다. 레거시 OAuth 탓에 auth uid와 `mem_id`가 달라 병렬화도
불가능했다. PostgREST 임베딩(`!inner`)으로 조인해 SQL 한 방으로 만들었다.

배포 전 검증(실측):
- prd 전수 대조 — 2단계 방식과 조인 방식이 **265명 전원 일치**(차집합 0/0)
- 한 auth uid가 서로 다른 `mem_mst` 행에 걸리는 경우 **0건** → `maybeSingle()` 안전
- 한 멤버가 같은 팀에 `team_mem_rel` 복수 보유 **0건** → 임베디드 배열 `[0]` 안전
- dev PostgREST에 실제 요청 → 생성 SQL이 `INNER JOIN LATERAL` 한 방, 임베딩 필터는 안쪽,
  `.or()`는 바깥, `json_agg`로 배열 반환까지 의도대로

> ⚠️ **RLS(`authenticated`) 아래 동작은 실제 로그인으로만 확인된다.** dev에서 **레거시
> 카카오/구글 연동 계정** 로그인을 반드시 확인하고 prd로 옮길 것 — 그 OR 조건이 이 함수의
> 존재 이유다.

### #2를 철회한 이유 (기록으로 남긴다)

"`msg_mst`·`pldg_mst`를 퍼블리케이션에서 빼면 DB CPU 최대 소비처가 준다"고 적었는데 **틀렸다.**
두 테이블은 **INSERT 누적이 0건**이다 — Realtime의 WAL 디코딩 비용은 *쓰기가 있을 때* 생기므로
빼도 절약이 **0**이다. 코드 상태만 보고 비용을 추정하고 실측을 안 한 결과다(#6과 같은 실수).

Realtime 38.7%의 정체는 테이블 수가 아니라 **폴링 × 구독 수**이고, 구독을 만드는 건
`noti_mst` 하나(알림 벨)다. 그래서 **이 부분을 실제로 건드린 건 #4**다(탭 이동마다 나던
재구독 제거 — 재측정 때 `sub_tables` 쿼리 호출 수로 확인할 것).

퍼블리케이션 등록은 **그대로 둔다** — 빼면 기능을 되살릴 때 재추가를 잊는 함정만 생긴다.
대신 `DESIGN.md`의 사실 오류만 정정했다(`83ae235`): 팻말에 Realtime 구독이 있다고 적혀
있었으나 `pledge-signs.tsx`는 **처음부터 채널을 가진 적이 없다.**

## 2차 작업 — 최적화 v2 (`feature/perf-optimize-v2`)

1차(§5)는 배포됐다(`398d02c`). 2차는 위 표를 **효과 순이 아니라 위험 순**으로 집는다 —
가장 큰 B(알림 벨)는 PWA 설치율이라는 선행 조건이 있어, 같은 구조 변경을 **작은 표면에서
먼저 굴려 보는** C부터 시작했다.

### C — 댓글 실시간 구독 제거 ✅

**Broadcast 전환이 아니라 제거로 결론이 바뀌었다.** 표에 적어 둔 안은
`postgres_changes` → `Broadcast`였는데, 실제로 무엇을 사는지 따져 보니 값이 안 맞았다:

- Broadcast로 가면 **쓰는 경로마다 `send`를 붙여야 한다**(작성·수정·삭제, 그리고 나중에
  생길 경로까지). 하나 빠뜨리면 그 경로만 조용히 실시간이 안 된다 — `postgres_changes`가
  구조적으로 막아 주던 실수다.
- 채널 인가도 따라온다. Broadcast 채널은 **이름을 아는 사람이면 듣는다.** 댓글 본문을
  payload에 실으려면 private 채널 + `realtime.messages` RLS를 새로 짜야 하고, 그러면
  아끼려던 DB 일이 일부 돌아온다.
- 그렇게까지 해서 사는 건 **"같은 글을 동시에 보고 있을 때 남의 댓글이 자동으로 뜨는 것"**
  하나다. 실측 댓글량에서 그 상황은 드물다.

**값이 낮은 기능은 싸게 만드는 게 아니라 안 만드는 게 맞다.** 그래서 걷어냈다.

| | 내가 쓴 댓글 | 남이 쓴 댓글 |
|---|---|---|
| 전 | 즉시 | 즉시 |
| 후 | 즉시 (그대로) | 다시 열거나 새로고침해야 |

#### ⚠️ 구독만 빼면 화면이 깨진다 — 실제로 세 군데가 실시간에 업혀 있었다

"구독 제거"가 한 줄 작업이 아니었던 이유다. `cmnt_mst` Realtime은 알림 역할만 한 게
아니라 **상태 갱신 경로 그 자체**였다.

| 깨지는 것 | 왜 | 고친 방법 |
|---|---|---|
| **내가 수정한 댓글** | `CommentItem`이 `updateComment()`만 부르고 부모 목록을 안 고쳤다. Realtime UPDATE가 돌아와 고쳐 주던 것 — 없으면 `setEditing(false)`가 원본으로 되돌려 **고치기 전 내용이 그대로 남는다** | `onEdited` 콜백 |
| **내가 삭제한 댓글** | 같은 이유로 **지운 댓글이 그대로 보인다** | `onDeleted` 콜백 (행은 남기고 `del_yn`만 세운다 — 자리표시자로 스레드 맥락 유지) |
| **깅스타그램 말풍선·하단 개수·격자 배지** | 시트와 릴스가 **별개 state**다. 시트의 낙관적 업데이트는 시트 안에만 남고, 밖의 세 표면은 Realtime INSERT가 갱신해 줬다 | `CommentSection.onCommentsChange` → `RecordCommentSheet` → `usePostComments.syncComments` |

작성은 원래 **완전한 낙관적 업데이트**였다(`handleSubmitComment`/`handleSubmitReply`가
이름·프사까지 미리 채우고 서버 응답으로 임시 id만 갈아끼운다). 그래서 작성 경로만은
실시간 없이도 멀쩡했고, 그게 "빼도 된다"는 판단의 근거였다 — **수정·삭제가 그렇지
않다는 건 코드를 열고서야 드러났다.**

덤으로 수정·삭제가 **결과를 확인하게** 됐다. 예전엔 `await` 후 결과를 안 보고 무조건
닫았는데, Realtime이 고쳐 주던 시절엔 실패해도 목록이 원본이라 티가 안 났다. 이제 이
콜백이 유일한 반영 경로라 성공·실패를 갈라야 한다(실패 시 입력을 열어 둬 쓴 글을
지키고 토스트로 알린다).

**#8 철회** — §2-4 전면 정정 참조. 비용의 67%가 계획 수립이라 SQL로 닿지 않는다.

**3-b(미니캘린더) 보류.** 2차 검토 A의 판단을 유지하되 이유를 보탠다:

- `prefetchAdjacent`는 `useEffect` 안이라 **페인트 후**에 돌고 `startTransition` 밖이라 흐림
  처리도 안 걸린다 — **사용자가 기다리는 게 없다.** "마운트 직후 8개가 첫 진입을 방해한다"는
  추측은 틀렸고, 실측은 오히려 **동시 요청이 많을수록 빨랐다**(11개 이상 p50 180ms vs
  1~2개 546ms). 프리페치를 빼면 달 이동이 캐시 히트에서 재조회로 바뀌어 **UX가 실제로 나빠진다.**
- 남은 실질 낭비는 **`comp_reg_rel`이 달과 무관한데 달마다 다시 받는 것**이다
  (`fetchMonthData` 안의 그 조회엔 **날짜 필터가 없다** — 몇 월을 보든 같은 결과).
  마운트에 3회(`fetchUserData` 1 + 프리페치 2), 달 이동마다 +2회.
- ⚠️ **그 중복은 실수가 아니라 자가 치유 장치다.** 코드 주석대로 "달을 한 번이라도 넘기면 등록
  맵이 스스로 낫는다" — 마운트 조회보다 스와이프가 빨라 맵이 버려지면 다시 만들 경로가 없어,
  이미 신청한 사람에게 "참가 신청"이 뜨고 누르면 유니크 제약(23505)으로 실패했다. 걷어내려면
  **명시적 재시도로 바꿔야** 한다. 이 구역은 레이스로 이미 세 번 깨졌다(`cacheVersionRef`).

**2차 검토 B(알림 벨)의 선행 조건을 실측했다 — 대안이 성립하지 않는다.**

| | prd 실측 |
|---|---|
| 활동 회원 | 135명 |
| 푸시 구독 보유 | **25명 (18.5%)** |

`canUsePush()`가 **모바일 + PWA 설치**만 통과시키므로(데스크톱 제외·모바일 웹 미설치 제외)
"푸시 + 서비스워커 postMessage로 대체" 안은 **81%를 커버하지 못한다.**

게다가 **구독만 빼면 뱃지가 세션 내내 얼어붙는다**: `NotificationChannel`은 루트 레이아웃에서
앱을 닫을 때까지 살고 목록 fetch에 `isLoaded()` 가드가 있어 **세션당 1회만** 받는다. 그 뒤의
변화를 지금은 Realtime이 전부 메우고 있다 — 떼면 **전체 새로고침**을 해야 새 알림이 보인다
(댓글의 "다시 열면 보임"과 급이 다르다). 최소한 **복귀 시 갱신**(`visibilitychange` +
라우트 변경 시 안읽음 수만 조회)을 함께 깔아야 성립한다.

**그래서 남은 선택은 기능을 깎느냐, RAM을 사느냐다.** §2-4의 계획 비용까지 더하면 **§1(RAM)이
앱 최적화로 닿지 않는 층을 유일하게 건드린다.** 재측정 뒤 이 판단을 내린다.

| `.rpc(...)` 호출 | **53곳** |
| 해당 파일 수 | **200개** |

| Storage | 5곳 |
| Realtime | 5곳 |

**이게 두 종류로 갈린다 — 이 구분이 전부다:**

| 묶인 대상 | 옮길 때 |

| 함수 113 · 트리거 57 · 마이그레이션 205 → **Postgres 자체** | **어느 Postgres로든 그대로 간다** (족쇄 아님) |

### 6-2. 선택지 비교

> ⚠️ 가격·리전은 2026년 5월 기준 정보다. **반드시 직접 확인할 것.** 구조와 트레이드오프는 유효하다.

| | 월 비용 | RAM | 코드 변경 | DB 재설계 | 운영 | 백업 | 탈출 |
|---|---|---|---|---|---|---|---|
| **A. Supabase Pro + Small** | $25~30 | 2GB | **0** | 없음 | **0** | 자동 | 쉬움 |
| **B. Supabase 셀프호스팅** | **$20~24** (한국 리전) | 4GB+ | **0** (env만) | 없음 | **높음** | 직접 | 쉬움 |
| C. Neon/Railway 등 이전 | $5~20 | 선택 | **749곳** | 없음 | 중 | 자동 | 쉬움 |
| D. Firebase | $0~5 | — | **749곳** | **전면** | 0 | 자동 | **어려움** |

### 6-3. C·D 탈락 이유

**C (Neon 등)**: DB는 Postgres 그대로지만 PostgREST가 없어 **749곳 재작성 + Auth·Storage·
Realtime 대체 + RLS 117개 이관**이 따라온다. 월 몇 달러 아끼려고 수 주~수 개월 재작성 +
회원 135명 서비스에 회귀 위험. 계산이 안 맞는다.

**D (Firebase)**: Firestore는 **NoSQL**이라 우리 데이터 모델과 모양이 다르다.

| 우리가 쓰는 것 | Firestore에서 |
|---|---|
| `get_team_story_feed` — 테이블 8개 조인 + CTE 7개 | **JOIN 없음.** 불가능 |
| 전당 랭킹 — `row_number() OVER (...)` | **윈도우 함수 없음.** 불가능 |
| 기강 포인트 — 트리거 57개 자동 적립 | 전부 Cloud Functions로 재작성 |
| RLS 117 / DB 함수 113 / 마이그레이션 205 | 전부 폐기 |

AGENTS.md의 **"DB 트리거가 자동 적립, 앱 코드에 훅 없음"** 이라는 설계 원칙이 통째로 무너진다.
추가로 **카카오 로그인 미지원**(Cloud Functions 커스텀 토큰 우회 필요)이고,
**Firestore는 독자 포맷이라 나중에 관계형으로 되돌리기 어렵다** — 지금 갖고 있는 "갈아탈 수
있다"는 선택지 자체가 사라진다.

> Firebase는 **새 프로젝트**이고 관계형 질의가 거의 없다면 좋은 선택지다. 우리는 반대 방향으로
> 이미 205개 마이그레이션을 쌓았다.

### 6-4. B (셀프호스팅)의 실체와 함정

**뭘로 돌리나**: VPS 1대에서 공식 `docker-compose`로 컨테이너 약 10개
(`postgres` · `postgrest` · `gotrue` · `realtime` · `storage-api` · `imgproxy` · `kong` ·
`supavisor` · `studio` · `meta` · `vector`). 지금 클라우드에서 도는 그 스택이 그대로 뜬다 —
**그래서 코드가 안 바뀐다**(URL·키만 교체). **RAM 최소 4GB, 실용적으로 8GB.**

> ⚠️ **가장 중요한 함정: 리전을 틀리면 지금보다 느려진다.**
> ```
> 현재: Vercel 서울(icn1) → Supabase 도쿄   = 왕복 약 30ms
> 독일: Vercel 서울(icn1) → 내 서버 독일      = 왕복 약 250ms
> ```
> 페이지당 왕복이 5번이라 **유럽에 올리면 1초 이상 그냥 추가된다.** 메모리는 고쳤는데 지연이
> 더 나빠지는 최악의 결과. **반드시 한국 또는 일본 리전.**

| 업체 | 스펙 | 월 비용 | 한/일 리전 |
|---|---|---|---|
| **Oracle Cloud 프리티어** | **ARM 4코어 / 24GB** | **무료** | ✅ 춘천·서울 |
| Vultr | 4GB | 약 $24 | ✅ 서울·도쿄 |
| AWS Lightsail | 4GB | 약 $20 | ✅ 서울 |
| Hetzner | 4GB | 약 €4.5 | ❌ 유럽·미국만 → **탈락** |

**Oracle 프리티어의 함정**: ARM 재고가 거의 없어 생성 시도를 반복해야 하고, 유휴 인스턴스
회수 정책이 있으며, 계정 정지 사례가 보고된다. **회원 135명이 쓰는 서비스를 SLA 없는 무료
자원에 올리는 것 자체가 리스크.**

**떠안는 일**: 백업(`pg_dump` 크론 + 외부 보관) · SSL(Caddy/Traefik + Let's Encrypt) ·
도메인 · 방화벽·패치 · 모니터링 · Supabase 버전 업그레이드.
초기 세팅 반나절~하루, 이후 월 1~2시간 + 장애 시 즉시 대응.

### 6-5. 결론

**제대로 된 한국 리전 VPS는 월 $20~24, Supabase Pro는 $25~30.** 차이가 월 5천원 남짓인데
그 대가로 백업·SSL·보안·모니터링·장애대응을 전부 떠안는다.
(초기에 "셀프호스팅 $5"로 봤던 건 **유럽 기준이라 우리는 못 쓰는 가격**이었다 — 정정.)

> **추천: A (Supabase Pro + Small 2GB).** 이유 하나만 꼽으면 **백업**이다.
> 회원 135명의 가입정보·회비·기록이 든 DB인데, 지금 Free에는 일일 백업이 없다.
> B는 그 문제를 **해결이 아니라 이전**한다.
> B를 택한다면 **백업 자동화부터 먼저** 세팅하고 옮길 것.

**Vercel은 사지 않는다.** 측정상 병목이 0이다(icn1 · TTFB 120~145ms · 캐시 HIT).
다만 **크론이 이미 천장**이다 — Hobby는 크론 2개/하루 1회인데 `vercel.json`에 정확히 2개
(`0 0 * * *`)가 있다. 크론을 늘리거나 더 자주 돌려야 하면 그때가 Vercel Pro 시점이다.

### 6-6. 속도와 무관하게 Free를 벗어나야 하는 이유 둘

| 위험 | 내용 |
|---|---|
| **백업 없음** | 회원 135명의 실데이터. 속도보다 먼저 볼 문제일 수 있다 |
| **자동 일시정지** | Free는 일정 기간 비활성 시 정지된다. 조용한 주에 사이트가 죽는다 |

```

그리고 **최소 3~4일(주말 포함)** 뒤 비교한다.

| 지표 | 현재 (prd) | 목표 |
|---|---|---|
| `set_config` mean | 6.10ms | 2ms 이하 |
| `get_team_story_feed` mean | 1,092ms | 300ms 이하 |
| 총 DB CPU / 일 | 12.7분 | 절반 이하 |

> ⚠️ **메모리 그래프는 거의 안 변한다.** 스왑 250~300MB는 그대로일 것이다(§1-3).
> 앱 최적화의 성과를 볼 곳은 **`pg_stat_statements`이지 메모리 차트가 아니다.**
> 여기서 "효과 없네"로 오독하지 말 것.

라이브 상태를 즉석에서 잡으려면 SQL Editor에서:

```sql
-- 테이블을 전혀 안 건드리는 순수 부하. 정상이면 100ms 미만
select count(*) from generate_series(1, 3000000);
```
