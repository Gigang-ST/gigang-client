## 1. 근본 원인 — 메모리 부족 → 상시 스왑

### 1-1. 증상: 쿼리 내용과 무관하게 모든 문장이 같은 배율로 부푼다

| 문장 | min | mean | max |
|---|---|---|---|
| `set_config(...)` — PostgREST가 요청마다 거는 세션 설정. **테이블 접근 0, I/O 0** | **0.02ms** | 6.10ms | 1,842ms |
| `get_team_story_feed` | 16.5ms | 1,092ms | 9,712ms |
| `get_team_ghost_members` | 2.4ms | 395ms | 8,443ms |
| `get_public_member_card` | 8.7ms | 396ms | 9,958ms |
| `get_team_recent_title_grants` | 3.9ms | 569ms | 7,080ms |

`set_config`는 **어떤 인덱스로도 어떤 SQL 튜닝으로도 빨라지지 않는 문장**이다. 그게 305배
부풀어 있다는 건 문제가 쿼리에 없다는 뜻이다. 같은 날 `get_team_story_feed`를 직접
EXPLAIN ANALYZE 하니 **64ms**였다 — 실전 평균의 1/17.

실행계획 안에서도 269행짜리 `mem_mst`의 PK 단건 조회가 `0.069ms`씩 찍힌다(정상 ~0.001ms).

| 지표 | 값 | 판정 |
|---|---|---|
| Memory usage — **Swap** | **250~300MB가 24시간 내내 상시** | 위험 |

**인과 사슬**

```

```

### 1-3. ⭐ 대조 실험 2건 — "우리 탓인가"를 가른다

이 점검의 핵심 증거다. **원인을 우리 앱이 아니라 등급으로 확정한 근거.**

#### 대조군 1: dev 프로젝트 (스키마 동일 · 트래픽 1/8)

| | prd | dev |
|---|---|---|
| 등급 | 동일 (`shared_buffers` 224MB · `max_connections` 60) | 동일 |
| 스키마 | 함수 113개 | 함수 119개 (사실상 동일) |
| DB 크기 | 43MB | 32MB |
| **DB 작업량** | **12.7분/일** | **1.57분/일 (1/8)** |
| `set_config` min → mean | 0.02 → 6.10ms (**305배**) | 0.015 → 1.21ms (**82배**) |
| `set_config` 최대 멈춤 | 1,842ms | **630 ~ 1,191ms** |

→ **1/8 부하인 dev도 82배 부풀고 1초씩 멈춘다.** 트래픽·데이터 양은 원인이 아니다.
→ 단, dev는 **같은 스키마**라 "스키마 복잡도" 변수는 못 가른다. 그래서 대조군 2가 필요했다.

#### 대조군 2: 개인 프로젝트 (스키마 무관 · 거의 미사용)

| | 값 |
|---|---|
| **총 RAM** | **408 MB** ← Nano는 0.5GB. 이게 전부다 |
| Used | 184 MB (45%) |
| Cache + Buffers | 207 MB (51%) |
| **Free** | **16.9 MB (4.1%)** |
| **Swap 사용 중** | **216 MB (53%) — 24시간 내내** |
| Committed / Limit | **1.12 GB / 1.2 GB (93.3%)** |

→ **아무것도 안 하는 사이트가 216MB를 스왑하고 여유 메모리가 16.9MB다.**
→ **Supabase 무료 등급은 코드가 0줄이어도 한계의 93%를 쓴다. 확정.**

#### 두 프로젝트의 차이 = 우리 앱의 몫

| | 빈 프로젝트 | 기강 prd | 차이 |
|---|---|---|---|
| 총 RAM | 408 MB | 411 MB | 동일 |
| **Swap (실사용)** | 216 MB | 250~300 MB | **+50~80MB** ← 실제 추가 사용 |
| **Committed (예약)** | 1.12 GB | 1.4 GB | **+약 280MB** ← 예약이지 실사용 아님 |
| Limit 대비 | 93.3% | **약 117%** | **우리만 벽을 넘었다** |

```
                RAM 408MB              스왑 약 800MB (디스크)
         ├───────────────────┤├──────────────────────────────┤
         0                408MB                           1.2GB ← Commit limit

빈 프로젝트 ███████████████████ + ██████                        1.12GB 예약 (93%)
기강 prd    ███████████████████ + ████████                  ──▶ 1.4GB 예약 (117%)
                                                                ↑ 벽 넘음 = OOM 위험
```

**결론: 무료 등급이 구조적으로 모자란 게 먼저고(93%), 우리 앱이 그걸 벽 너머로 밀었다(117%).**

### 1-4. 스왑이란 무엇이고 왜 치명적인가

RAM이 꽉 차면 커널이 안 쓰는 메모리 페이지를 **디스크에 내다 놓는다**. 나중에 그 페이지가
필요하면 디스크에서 다시 읽어온다.

| | 접근 시간 |
|---|---|
| RAM 읽기 | 약 **0.0001 ms** |
| 디스크(스왑) 읽기 | 약 **0.1 ~ 수 ms** |

**1,000~10,000배 차이.** 이게 `set_config`가 0.02ms → 1,842ms가 된 이유다. 쿼리가 복잡해서가
아니라 그 쿼리를 돌릴 메모리가 디스크에 나가 있어서다. **어느 페이지가 나가 있는지는
무작위**라, 쿼리 종류와 무관하게 아무거나 걸린다.

> **스왑은 원래 비상용**이다. 평소엔 0이고 사고 날 때만 써야 한다.
> 그런데 여기선 **빈 프로젝트조차 216MB를 24시간 내내** 쓴다 — 비상용이 아니라 상시 가동이다.
> **그래서 "가끔 느린" 게 아니라 "평소에도 느린" 것이다.**

### 1-5. Commit limit이 RAM보다 큰 이유 (0.5GB인데 왜 1.2GB인가)

```
Commit limit = RAM + 스왑 공간
1.2 GB (limit) − 0.4 GB (실제 RAM) = 약 0.8 GB  ← 스왑 공간
```

리눅스는 "메모리를 예약해 줄 수 있는 총량"을 따질 때 디스크의 스왑 공간까지 쳐준다.

> **Supabase가 Nano에 RAM의 두 배나 되는 스왑을 붙여놨다는 것 자체가,
> "0.5GB로는 이 스택이 안 돌아간다"는 설계상의 인정이다.**

### 1-6. Committed(예약) vs Memory usage(실사용) — 헷갈리면 오진한다

| | Memory usage | Memory commitment |
|---|---|---|
| 재는 것 | **실제로 쓰고 있는** 물리 메모리 | 프로세스들이 **달라고 예약해 둔** 총합 (`Committed_AS`) |
| 한계선 | 물리 RAM (408MB) | Commit limit (1.2GB = RAM + 스왑) |
| 넘으면 | **스왑 → 느려짐** | **OOM(강제 종료) 위험** |

비유하면 Committed는 **은행이 승인한 대출 한도의 합**, Memory usage는 **실제로 인출한 돈**,
Commit limit은 **금고에 있는 돈**이다. 프로그램은 보통 예약만 하고 다 안 쓰므로
**Committed가 RAM보다 큰 건 정상**이다. 문제는 **Commit limit을 넘을 때**다.

**그래서 우리 증상은 하나가 아니라 둘이다:**

| 숫자 | 증상 |
|---|---|
| Swap 250~300MB | **느린 이유.** 지금 겪는 그것 |
| Committed 117% | **터질 위험.** Postgres·Realtime이 커널에 강제 종료될 수 있음 = **사이트 다운** |

> 실제 실사용은 RAM 408 + 스왑 약 280 = **약 690MB**다(1.4GB를 물리적으로 쓰는 게 아니다).
> 500MB짜리 기계가 690MB를 쓰고 있다.
> ⚠️ **간헐적 재시작·OOM이 실제로 있었는지는 `Logs → Postgres`에서 확인 필요** (미확인 항목).

### 1-7. 무엇이 램을 채우는가 — 데이터가 아니라 서비스 개수다

| 근거 | 수치 |
|---|---|
| DB 데이터 전체 | 43MB |
| 그런데 `shared_buffers` 하나가 | **224MB** — **prd(43MB)와 dev(32MB)가 값이 똑같다** = 등급이 정한다 |
| 클라이언트 연결 수 | prd **6** / dev **5** — 그리고 **우리 앱이 직접 연 건 0개** |

연결 6개의 정체: `postgrest` 3 · `postgres_exporter` 1 · `mgmt-api` 1 · 익명 1 —
**전부 Supabase 인프라다.** 우리 앱은 DB에 직접 연결하지 않고 PostgREST에 HTTP로 말을 건다.

Supabase는 한 인스턴스에 **Postgres · PostgREST · GoTrue · Realtime(BEAM VM) ·
Supavisor 풀러(또 다른 BEAM VM) · Storage API(Node) · Kong · pg_meta(Node) · 로그 수집기**를
전부 함께 올린다. 전체 테이블 108개 중 **50개가 Supabase 자기 것**(`auth` 27 · `realtime` 11 ·
`storage` 8 · 기타 4)이다 — 빈 프로젝트도 이걸 다 돌린다.

**우리가 그 위에 더한 것**(=Committed +280MB의 정체로 추정):

| | 왜 메모리를 먹나 |
|---|---|
| **스키마 복잡도** — 테이블 52 · 함수 113 · 컬럼 820 · RLS 117 | PostgREST·pg_meta가 **스키마 전체를 메모리 캐시로** 들고 있다 |
| `wal_level = logical` + Realtime 실사용 | 로그인 사용자 전원이 `noti_mst` 구독 → BEAM VM이 구독 수만큼 |
| Storage(사진) 사용 | Storage API(Node) 상주 |

> ⚠️ **서비스별 메모리 배분은 측정이 아니라 추정이다** — DB 바깥 프로세스 메모리는 SQL로 못 본다.
> 측정된 건 스키마 규모·연결 수·스왑 패턴이다.

### 1-8. 폐기된 가설 — CPU 버스트 크레딧 소진 (기록으로 남긴다)

처음엔 "공유 CPU 버스터블의 크레딧 소진"으로 진단했다. **틀렸다.**

1. **CPU 7일 피크가 40%** — 천장에 안 붙는다.
2. **146일 평균 DB CPU가 0.01 코어**(총 31.0시간 / 146.6일). 이 부하로 크레딧이 바닥날 수 없다.

같은 이유로 **"트래픽이 적으니 작은 인스턴스로 충분하다"는 추론은 CPU에 대해서만 맞다.**
메모리는 고정 비용이라 그 논리가 성립하지 않는다.

> **다음에 "느리다"는 제보가 오면 순서**: ① Reports → Database의 **Swap** ② Disk IO ③ CPU.
> 우리 규모에서 CPU가 범인인 경우는 아직 없었다.

### 1-9. 측정 도구의 함정 두 가지 (실제로 둘 다 걸렸다)

1. **`track_io_timing`이 `off`다.** `pg_stat_statements`의 `shared_blk_read_time`이 전부 0.00으로
   나오는데, 이걸 "디스크 I/O가 없다"로 읽으면 안 된다. `shared_blks_read = 0`은 **읽기 캐시
   히트**만 뜻하고 쓰기·WAL·**스왑 IO는 애초에 안 잡힌다.**
2. **7일 그래프는 분 단위 평균이라 1초 미만의 순간 포화를 못 본다.** "CPU 평균 40%"는
   "수백 ms짜리 100% 스파이크가 자주 있음"과 양립한다. 그래프로 무언가를 **배제**할 때는
   샘플링 주기를 먼저 확인할 것.

## 2. DB — 실제로 버리고 있는 일

전체 DB CPU 31.0시간 중 **46.5%가 앱 쿼리가 아니라 인프라 오버헤드**다.

| 소비처 | 시간 | 비중 |
|---|---|---|
| Realtime (WAL 디코딩 + 구독 갱신 + 퍼블리케이션 조회) | 12.0h | **38.7%** |
| PostgREST 스키마 캐시 재적재 | 2.4h | 7.7% |
| 앱 RPC 전체 | 약 9.7h | 약 31% |

### 2-1. Realtime 38.7% — 그중 절반은 죽은 기능 (무손실 개선)

```
supabase_realtime 퍼블리케이션: cmnt_mst, msg_mst, noti_mst, pldg_mst
```

| 테이블 | 상태 |
|---|---|
| `cmnt_mst` | 살아있음 (댓글 — `comment-section.tsx`, `use-post-comments.ts`) |
| `noti_mst` | 살아있음 (알림 벨 — `notification-bell-icon.tsx`) |
| `msg_mst` | **죽음** — `SHOW_MESSAGE_PLANES = false`. 구독 컴포넌트가 렌더되지 않음 |
| `pldg_mst` | **죽음** — `SHOW_PLEDGE_LEDE = false`, `SHOW_PLEDGE_SIGNS = false`. **살아있는 행 0개**, 구독 `.channel()` **코드에 없음** |

`msg_mst`·`pldg_mst`를 퍼블리케이션에서 빼는 건 마이그레이션 두 줄이고 잃는 게 없다.

> **문서 결함**: `DESIGN.md`는 "꽂으면 `pldg_mst` Realtime 구독으로 열린 모든 화면이 함께
> 갱신된다"고 단언하는데 **그 구독은 코드에 존재하지 않는다**(전체 grep에서 `pldg` 채널 0건).

**구조적 참고**: 로그인 사용자는 어느 탭에 있든 `HeaderActions` → `NotificationBellIcon`이
`noti_mst`를 구독한다. **Realtime 구독 수 ≈ 동시 접속 로그인 사용자 수**이고, 폴링 1회 비용이
구독 수에 비례한다. 알림 설계의 의도된 대가라 그대로 두되, **퍼블리케이션에 테이블을 추가할
때는 이 곱셈을 기억할 것.**

### 2-2. PostgREST 스키마 캐시 재적재 7.7%

| 문장 | 호출 | mean |
|---|---|---|
| `SELECT name FROM pg_timezone_names` | 9,626 | **708.7ms** |
| 도메인 base_types 재귀 조회 | 9,652 / 9,297 | 127.7 / 85.2ms |

**9,626번 재적재**, 회당 약 920ms. 마이그레이션 횟수보다 훨씬 많다 — PostgREST 재시작이
잦거나 `pgrst_ddl_watch` 이벤트 트리거가 예상보다 자주 발화한다. **운영 측 조사 항목.**
(§1-7의 스키마 복잡도와 같은 뿌리 — 재적재 1회 비용이 테이블·함수 수에 비례한다.)

### 2-3. `get_team_ghost_members` — 주석의 근거가 프로덕션에서 무효

`lib/queries/ghost-members.ts`가 캐시를 안 하는 이유로 적어 둔 문장:

> *"30명 짜리 가벼운 조회라(**실측 2.5ms**, 전량 버퍼 히트) 매 요청 최신값을 읽어도 부담이 없고"*

프로덕션 실측: **평균 395.4ms · 호출 11,458회 · 누적 1.26시간 — RPC 중 2위.**
min이 2.4ms라 당시 측정은 맞았지만, §1의 배율이 붙은 지금은 **홈에서 캐시 없이 도는 가장 비싼
쿼리**다.

**해법 — 설계 의도를 그대로 지키면서 고칠 수 있다.** RPC에서 시드는 정렬에만 쓰이고,
*누가 유령인가*를 정하는 필터는 시드와 무관하다:

```sql
WHERE (la.last_dt < today.d - 100) OR (...)       -- 시드 무관 (누가 대상인가)
ORDER BY md5(mm.mem_id::text || p_seed) LIMIT 30  -- 시드 의존 (누가 앞에 서나)
```

→ **후보 목록만 캐시(5분)하고 셔플은 Node에서 시드로 돌린다.** "진입마다 새 조합"이 그대로
유지되고 DB 호출은 5분에 1회가 된다. (선행 확인: `LIMIT 30` 이전 후보가 실제로 몇 명인지)

### 2-4. `get_team_story_feed` — 호출당 버퍼 4,733개 = **37MB를 훑는다** (DB 전체가 43MB)

`upcoming` CTE가 `comp_reg_rel`을 **두 번** 스캔한다. 바깥 조인은 `count(DISTINCT cr.mem_id)`
하나 때문에 있고, 안쪽 상관 서브쿼리가 같은 테이블을 다시 훑는다. 바깥의
`INNER JOIN mem_mst`는 필터 역할만 할 뿐 컬럼을 하나도 안 쓴다.

`mem_mst`의 누적 인덱스 스캔이 **1,350만 회**(269행 테이블에), `team_mem_rel` 568만,
`comp_evt_cfg` 232만 — 전부 "SQL 안의 N+1"(행마다 상관 서브쿼리) 패턴의 총합이다.

부수적으로 `pledges` CTE는 `SHOW_PLEDGE_*`가 전부 false라 **클라이언트가 버리는 값**을
계산한다(현재 행이 0개라 비용 자체는 작다).

## 3. 서버 로직 — 직렬 왕복

**Vercel `icn1`(서울) · Supabase `ap-northeast-1`(도쿄)** — 리전 배치는 문제가 아니다(RTT 약 30ms).
다만 **직렬 왕복 수**는 그대로 곱해진다.

### 3-0. ⭐ 왜 왕복 줄이기가 메모리를 안 고치는데도 효과가 있나

**스왑 지연은 복권이고, 왕복 횟수는 복권을 몇 장 사느냐다.**

로그인 사용자가 홈에 들어오면 서버가 **순차로** 왕복한다:

```
① getCurrentMember → mem_mst 조회
② getCurrentMember → team_mem_rel 조회      ← ①이 끝나야 시작
③ getStoryReactions (내 응원)               ← ②가 끝나야 시작
④ HeaderActions (알림 카운트 + 목록 20건)
   + 이 사이에 유령회원 RPC 395ms (캐시 없음)
```

**각 왕복마다 "이번엔 스왑에 걸릴까" 주사위를 굴린다.** 한 번만 걸려도 그 페이지는 느려진다.
왕복이 5번이면 걸릴 기회가 5번이다. dev가 1/8 부하로 82배, prd가 305배인 것도 같은 원리다.

→ **§3의 개선은 메모리를 안 고치지만 주사위를 덜 굴리게 한다.** 그래서 유효하다.

### 3-1. `getCurrentMember()` — 인증된 모든 렌더에서 왕복 2회 직렬

`lib/queries/app-member.ts`의 `fetchMemMstWithTeamRel`이 `mem_mst` → `team_mem_rel`을 **순차**로
조회한다 (각 75,345회 / 39,792회 호출). 인덱스는 이미 완벽하다(BitmapOr 3인덱스, 버퍼 4개).
**문제는 왕복이 2회라는 것 하나.** PostgREST 리소스 임베딩으로 1회로 합칠 수 있다:

```ts
.from("mem_mst").select("*, team_mem_rel!inner(*)")
  .eq("vers", 0).eq("del_yn", false).or(orFilter)
  .eq("team_mem_rel.team_id", teamId).eq("team_mem_rel.vers", 0)
```

### 3-2. 알림 20건을 모든 탭 렌더에서 미리 가져온다 — 지연로딩 경로가 죽어 있다

`components/common/header-actions.tsx`가 **5개 메인 탭 전부**에서
`getNotifications(member.id, { limit: 20 })`을 서버에서 부른다. 그런데 벨 컴포넌트:

```ts
// components/notifications/notification-bell-icon.tsx:82
const notificationsLoaded = useRef(initialNotifications !== undefined);
```

`HeaderActions`가 `initialNotifications`를 **항상** 넘기므로(비로그인도 `[]`) 이 ref는 늘
`true`이고, 아래의 "팝오버 처음 열 때 1회 로드" `useEffect`는 **영원히 실행되지 않는다.**

→ 전달을 빼면 모든 탭 렌더에서 DB 조회 1건(누적 41,410회) 제거. 뱃지 카운트는 유지.
**새 코드 없이 이미 구현된 경로를 살리는 것뿐.**

### 3-3. 홈 전광판의 마지막 직렬 구간

`app/(main)/story/page.tsx`가 `Promise.all(...)` 6개를 기다린 뒤
`await getStoryReactions(teamId, member?.id)`를 **순차로** 붙인다. 그 안의
`getReactionTotals(teamId)`(30초 캐시)는 **멤버와 무관하다** — `Promise.all`에 합류시키고
멤버 의존인 `mine`만 뒤에 남기면 왕복 1회가 임계경로에서 빠진다.

|---|---|
| `.from(...)` 호출 | **696곳** |
| `.rpc(...)` 호출 | **53곳** |
| 해당 파일 수 | **200개** |
| `supabase.auth` (카카오·구글 OAuth) | 19곳 |

| DB | 개수 |
|---|---|
| 함수(RPC) | 113 · 트리거 57 · RLS 정책 117 · 마이그레이션 205 |

**이게 두 종류로 갈린다 — 이 구분이 전부다:**

| 묶인 대상 | 옮길 때 |
|---|---|
| 함수 113 · 트리거 57 · 마이그레이션 205 → **Postgres 자체** | **어느 Postgres로든 그대로 간다** (족쇄 아님) |

| Auth · Storage · Realtime | 각각 대체재 필요 |

### 6-2. 선택지 비교

> ⚠️ 가격·리전은 2026년 5월 기준 정보다. **반드시 직접 확인할 것.** 구조와 트레이드오프는 유효하다.

| | 월 비용 | RAM | 코드 변경 | DB 재설계 | 운영 | 백업 | 탈출 |
|---|---|---|---|---|---|---|---|
| **A. Supabase Pro + Small** | $25~30 | 2GB | **0** | 없음 | **0** | 자동 | 쉬움 |
| **B. Supabase 셀프호스팅** | **$20~24** (한국 리전) | 4GB+ | **0** (env만) | 없음 | **높음** | 직접 | 쉬움 |
| C. Neon/Railway 등 이전 | $5~20 | 선택 | **749곳** | 없음 | 중 | 자동 | 쉬움 |
| D. Firebase | $0~5 | — | **749곳** | **전면** | 0 | 자동 | **어려움** |

### 6-3. C·D 탈락 이유

**C (Neon 등)**: DB는 Postgres 그대로지만 PostgREST가 없어 **749곳 재작성 + Auth·Storage·
Realtime 대체 + RLS 117개 이관**이 따라온다. 월 몇 달러 아끼려고 수 주~수 개월 재작성 +
회원 135명 서비스에 회귀 위험. 계산이 안 맞는다.

**D (Firebase)**: Firestore는 **NoSQL**이라 우리 데이터 모델과 모양이 다르다.

| 우리가 쓰는 것 | Firestore에서 |
|---|---|
| `get_team_story_feed` — 테이블 8개 조인 + CTE 7개 | **JOIN 없음.** 불가능 |
| 전당 랭킹 — `row_number() OVER (...)` | **윈도우 함수 없음.** 불가능 |
| 기강 포인트 — 트리거 57개 자동 적립 | 전부 Cloud Functions로 재작성 |
| RLS 117 / DB 함수 113 / 마이그레이션 205 | 전부 폐기 |

AGENTS.md의 **"DB 트리거가 자동 적립, 앱 코드에 훅 없음"** 이라는 설계 원칙이 통째로 무너진다.
추가로 **카카오 로그인 미지원**(Cloud Functions 커스텀 토큰 우회 필요)이고,
**Firestore는 독자 포맷이라 나중에 관계형으로 되돌리기 어렵다** — 지금 갖고 있는 "갈아탈 수
있다"는 선택지 자체가 사라진다.

> Firebase는 **새 프로젝트**이고 관계형 질의가 거의 없다면 좋은 선택지다. 우리는 반대 방향으로
> 이미 205개 마이그레이션을 쌓았다.

### 6-4. B (셀프호스팅)의 실체와 함정

**뭘로 돌리나**: VPS 1대에서 공식 `docker-compose`로 컨테이너 약 10개
(`postgres` · `postgrest` · `gotrue` · `realtime` · `storage-api` · `imgproxy` · `kong` ·
`supavisor` · `studio` · `meta` · `vector`). 지금 클라우드에서 도는 그 스택이 그대로 뜬다 —
**그래서 코드가 안 바뀐다**(URL·키만 교체). **RAM 최소 4GB, 실용적으로 8GB.**

> ⚠️ **가장 중요한 함정: 리전을 틀리면 지금보다 느려진다.**
> ```
> 현재: Vercel 서울(icn1) → Supabase 도쿄   = 왕복 약 30ms
> 독일: Vercel 서울(icn1) → 내 서버 독일      = 왕복 약 250ms
> ```
> 페이지당 왕복이 5번이라 **유럽에 올리면 1초 이상 그냥 추가된다.** 메모리는 고쳤는데 지연이
> 더 나빠지는 최악의 결과. **반드시 한국 또는 일본 리전.**

| 업체 | 스펙 | 월 비용 | 한/일 리전 |
|---|---|---|---|
| **Oracle Cloud 프리티어** | **ARM 4코어 / 24GB** | **무료** | ✅ 춘천·서울 |
| Vultr | 4GB | 약 $24 | ✅ 서울·도쿄 |
| AWS Lightsail | 4GB | 약 $20 | ✅ 서울 |
| Hetzner | 4GB | 약 €4.5 | ❌ 유럽·미국만 → **탈락** |

**Oracle 프리티어의 함정**: ARM 재고가 거의 없어 생성 시도를 반복해야 하고, 유휴 인스턴스
회수 정책이 있으며, 계정 정지 사례가 보고된다. **회원 135명이 쓰는 서비스를 SLA 없는 무료
자원에 올리는 것 자체가 리스크.**

**떠안는 일**: 백업(`pg_dump` 크론 + 외부 보관) · SSL(Caddy/Traefik + Let's Encrypt) ·
도메인 · 방화벽·패치 · 모니터링 · Supabase 버전 업그레이드.
초기 세팅 반나절~하루, 이후 월 1~2시간 + 장애 시 즉시 대응.

### 6-5. 결론

**제대로 된 한국 리전 VPS는 월 $20~24, Supabase Pro는 $25~30.** 차이가 월 5천원 남짓인데
그 대가로 백업·SSL·보안·모니터링·장애대응을 전부 떠안는다.
(초기에 "셀프호스팅 $5"로 봤던 건 **유럽 기준이라 우리는 못 쓰는 가격**이었다 — 정정.)

> **추천: A (Supabase Pro + Small 2GB).** 이유 하나만 꼽으면 **백업**이다.
> 회원 135명의 가입정보·회비·기록이 든 DB인데, 지금 Free에는 일일 백업이 없다.
> B는 그 문제를 **해결이 아니라 이전**한다.
> B를 택한다면 **백업 자동화부터 먼저** 세팅하고 옮길 것.

**Vercel은 사지 않는다.** 측정상 병목이 0이다(icn1 · TTFB 120~145ms · 캐시 HIT).
다만 **크론이 이미 천장**이다 — Hobby는 크론 2개/하루 1회인데 `vercel.json`에 정확히 2개
(`0 0 * * *`)가 있다. 크론을 늘리거나 더 자주 돌려야 하면 그때가 Vercel Pro 시점이다.

### 6-6. 속도와 무관하게 Free를 벗어나야 하는 이유 둘

| 위험 | 내용 |
|---|---|
| **백업 없음** | 회원 135명의 실데이터. 속도보다 먼저 볼 문제일 수 있다 |
| **자동 일시정지** | Free는 일정 기간 비활성 시 정지된다. 조용한 주에 사이트가 죽는다 |

## 7. 재측정 프로토콜

최적화 후 효과를 재려면 **반드시 통계를 리셋**해야 한다. 지금 통계는 146일치 누적이라
개선분이 옛 숫자에 묻힌다.

```sql
-- 배포 직후 실행
select pg_stat_statements_reset();
```

그리고 **최소 3~4일(주말 포함)** 뒤 비교한다.

| 지표 | 현재 (prd) | 목표 |
|---|---|---|
| `set_config` mean | 6.10ms | 2ms 이하 |
| `get_team_story_feed` mean | 1,092ms | 300ms 이하 |
| 총 DB CPU / 일 | 12.7분 | 절반 이하 |

> ⚠️ **메모리 그래프는 거의 안 변한다.** 스왑 250~300MB는 그대로일 것이다(§1-3).
> 앱 최적화의 성과를 볼 곳은 **`pg_stat_statements`이지 메모리 차트가 아니다.**
> 여기서 "효과 없네"로 오독하지 말 것.
