# ADR-0002: 점검 모드를 없애고 화면만 보관한다 — 요청마다 과금되는 호출을 proxy에 두지 않는다

- 상태: 승인
- 날짜: 2026-10-22
- 결정자: 기록 없음 — 출처 PR #606(임시 차단) · #608(제거)
- 대체: 없음

## 맥락

2026-09-23 장애 후속(#552)으로 점검 모드를 만들었다. 스위치는 Supabase 가 아니라 **Vercel Global Config**
(옛 Edge Config)에 뒀다 — 점검이 필요한 상황은 대개 Supabase 가 죽은 때라, 스위치를 DB 에 두면 "점검 중인가?"를
묻는 질문 자체가 타임아웃 나기 때문이다. `proxy.ts` 가 요청마다 그 스위치를 읽어 켜져 있으면 점검 화면으로 보냈다.

그런데 `proxy.ts` 는 화면 하나에 여러 번 돈다 — 링크 prefetch(링크 1개당 2~3 요청), RSC 이동, 서버 액션,
앱 복귀 때의 `router.refresh()`. 스위치 읽기가 거의 모든 요청에서 돌아 **한 달 약 15만 회**(Hobby 무료 한도
5만의 300%)를 넘겼고, **2026-10-22 Vercel 팀 계정이 정지됐다.** 해제는 일회성 courtesy unblock 으로 받았고,
다음엔 Pro 전환 말고는 길이 없다.

## 결정

1. **점검 모드를 기능째 없앤다** — 스위치 읽기(`lib/maintenance-config.ts`)·판정과 운영자 우회
   (`lib/maintenance.ts`, `?bypass=`)·관련 환경변수·`@vercel/global-config` 의존성을 전부 걷어낸다.
2. **점검 화면 HTML 만 `app/_maintenance/route.ts` 에 보관한다.** `_` 폴더는 Next.js 가 라우팅에서 빼므로
   어떤 주소로도 열리지 않는다. 되살리는 법은 그 파일 머리 주석에 있다.
3. **`proxy.ts` 에는 요청 수에 비례해 과금되는 호출을 두지 않는다.** 지금 밖으로 나가는 호출은 Supabase 인증
   하나다(`getClaims()` — 평소엔 캐시한 공개키로 서버 안에서 검증하고, MAU 기준이라 이 한도와 무관).
4. **읽기·호출·전송량으로 세는 Vercel 기능을 쓰면 한 달 호출 수를 계산해 한도와 견준다.** "평소 몇 ms 라
   가볍다"는 지연 얘기지 비용 얘기가 아니다. 배포 뒤 며칠은 Usage 에서 새 항목의 기울기를 본다.

## 고려한 대안

백필이라 당시 검토한 대안의 기록은 거의 없다. 출처에 남은 것만 적는다.

- **스위치 읽기만 막아 두고 코드는 유지(#606)** — 실제로 먼저 한 임시 조치다. #608 이 "임시 조치였고 이번에
  전부 걷어낸다"고 이어받았다.
- **Pro 플랜 전환** — 다음에 한도를 넘기면 남는 유일한 길로만 언급돼 있다.

## 결과

- 쉬워지는 것: proxy 경로의 과금 위험이 Supabase 인증 하나로 줄었다.
- 어려워지는 것: **지금은 점검 화면을 띄울 수단이 없다.** 되살리려면 요청마다 과금되지 않는 장치를 새로
  만들어야 한다(`app/_maintenance/route.ts` 머리 주석).
- 이 결정을 지키는 곳: `AGENTS.md` 핵심 원칙 「Vercel 사용량」.
