# ADR-0005: 모임 참석 조건의 OR 면제는 모임별 설정(`exm_evt_id`)으로 둔다

- 상태: 승인
- 날짜: 2026-10-29
- 결정자: @LHG4650
- 대체: 없음 (참여조건 설계 §1 Non-goals 의 「조건 OR 조합」을 연다)

## 맥락

2026 송년회(「기강의밤」, 12/12)는 `최근 6개월 모임 참석 6회 이상` 조건이 걸린 승인제 모임이다. 동계훈련
(「동계훈련 10K PB클래스 3기」)에 등록하고 입금까지 마친 사람도 송년회를 신청할 수 있어야 했다. 참여조건은
횟수 하나뿐이라 그 사람들이 신청 버튼에서 막혔다 — prd 실측(2026-10-29) 승인자 13명 중 7명.

원 설계(`docs/superpowers/specs/2026-08-25-모임-참여조건-승인제-design.md`)는 조건 OR 조합을 범위 밖으로 뺐었다.

## 결정

1. **모임 행에 면제 프로젝트를 둔다** — `gthr_mst.exm_evt_id`(`evt_team_mst` FK, `ON DELETE SET NULL`).
   운영진이 그 모임의 수정 폼에서 고른다.
2. **면제는 횟수 조건에 딸린다** — CHECK `ck_gthr_mst_exm_evt`. 횟수가 비면 서버가 면제를 접는다.
3. **조건 목록은 OR 다**(`ok = some(met)`). 통과 기준은 그 프로젝트의 **승인된 참가자**
   (`evt_pb_prt_rel.aprv_yn` — 운영진 입금 확인). 신청만 하고 승인 전이면 면제되지 않는다.
4. **고를 수 있는 건 PB 클래스뿐이다** — 승인 개념이 있는 프로젝트가 그것뿐이다(`EXEMPTION_EVT_TYPE`).
5. **면제 조회가 실패하거나 남의 팀 프로젝트면 면제 줄을 버린다** — 원래 횟수 조건은 그대로 서므로 문이
   열리지 않는 쪽이다.

## 고려한 대안

- **진행 중인 PB 클래스 승인 참가자는 조건이 걸린 모든 모임에서 면제** — 택하지 않았다. DB·폼 변경 없이
  빠르지만, 모임 설정 화면에 안 보이는 예외가 되고 앞으로 만들 다른 조건부 모임에도 저절로 번진다.
  원 설계 §3.1 "모임 행이 자기 조건을 영구히 들고 있다"와도 어긋난다.
- **운영진이 대리 참석 추가로 한 명씩 넣는다** — 기존 예외 경로(원 설계 §8-1)라 코드 변경이 없지만,
  본인이 직접 누를 수 있게 하는 게 요청이었다.

## 결과

- 쉬워지는 것: 모임마다 "이 프로젝트 참가자도 받는다"를 화면에서 고른다. 내년 송년회에도 그대로 쓴다.
- 어려워지는 것: 조건을 판정하는 select 마다 `exm_evt_id` 를 실어야 한다 — 빠지면 면제 대상자가 조용히 막힌다.
  수정 폼 프리필 경로(상세 RPC → 달력 상태 → 폼)에서 빠지면 **저장하는 순간 면제가 지워진다.**
- 마일리지런을 열려면 그쪽의 "참가 확정"이 무엇인지부터 새 ADR로 정한다.
- 상세: 설계 문서 §13. 테스트: `lib/gathering/__tests__/join-condition.test.ts` · `application.test.ts`(면제 프로젝트).
