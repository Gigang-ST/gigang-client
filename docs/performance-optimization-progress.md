## 1. 일정 탭 성능 개선

상세 병목과 완료 조건은 로그인 실측 및 코드 재분석 후 확정한다.

### 현재까지 확인된 것

- `app/(main)/schedule/page.tsx`의 본문(`HomeContent`)은 `getCachedHomeCalendar` +
  `getCachedCmmCdRows`를 `Promise.all`로 묶어 캐시 히트 시 DB 쿼리 0개다. 헤더와 본문이
  각각 Suspense로 분리되어 헤더 조회가 캘린더를 막지 않는다. **정적 분석 범위에서는 이 탭의
  고우선 병목을 찾지 못했다.**
- 따라서 이 작업의 첫 단계는 수정이 아니라 **병목이 실재하는지 확정**하는 것이다. 체감 지연이
  있다면 공통 리소스(3번 폰트, 11번 탭바 로고, 아바타)가 원인일 수 있으므로 탭 고유 문제와
  분리해서 측정한다.

### 우선 확인 후보

- **헤더 티커 개인화 조회** (`schedule/page.tsx:28` 부근): 로그인 회원마다 `gthr_mst` +
  `gthr_attd_rel!inner` 조인으로 D-5 이내 내 모임 1건을 매 요청 조회한다. 이 탭에서 공개
  캐시를 타지 않는 유일한 조회다. 반환은 1행이고 헤더 Suspense 안이라 본문을 막지는 않지만,
  실측 시 가장 먼저 볼 지점이다. `stt_at` 범위 조건과 `gthr_attd_rel.mem_id` 조인의 인덱스
  사용 여부를 실행계획으로 확인한다.
- 월 이동 시 캐시 히트 여부와 재조회 범위.

### 진행 단계

- [x] 코드 정적 분석으로 캐시·병렬·Suspense 구조 확인
- [ ] 로그인 상태에서 최초 표시·월 이동 3회 이상 반복 측정
- [ ] 헤더 티커 조회 실행계획·지연 확인
- [ ] 병목 확정 또는 "탭 고유 병목 없음" 결론 기록

## 7. 프로젝트 원장 조회·집계 개선

### 문제

`lib/queries/project-data.ts`의 누적 활동 조회는 이벤트 시작일부터 선택 월까지 `evt_mlg_act_hist` 원장 행을 1,000개씩 반복해서 모두 가져온다. 환급 예정액과 월별 통계는 주로 회원·월별 `final_mlg` 합계가 필요하지만, 현재는 종목·거리·고도·배율·후기 등 상세 필드까지 전송한 뒤 애플리케이션에서 다시 합산한다.

당월 조회는 반대로 전체 행이 필요하면서도 페이지네이션이 없어, 운영 PostgREST 응답 상한이 1,000행일 경우 통계나 목록이 조용히 누락될 수 있다.

### 목표 구조

1. 누적 계산은 PostgreSQL RPC가 이벤트·기간 조건으로 집계해 필요한 합계만 반환한다.
2. 당월 상세 목록은 화면에 필요한 행만 안정적인 정렬과 페이지네이션으로 읽는다.
3. 환급 예정액처럼 금액에 영향을 주는 값에는 요청 간 캐시를 추가하지 않는다.
4. 기존 원장 기반 계산과 새 집계 결과가 회원별·월별·전체 합계에서 정확히 일치해야 한다.
5. 이벤트 미참여자, 중도 참여자, 목표 미설정자, 삭제·미승인 관계를 기존과 동일하게 처리한다.
