# 칭호획득 리드 슬롯 — 설계

> 2026-08-07 · 칭호 중규모 작업 1번. 홈(`/story` 전광판) 상단 스와이프 리드에
> "칭호획득 소식" 슬롯을 추가한다.

## 배경 / 목적

칭호는 획득 순간 인앱 알림(`ttl_grnt`)+푸시로 **본인에게만** 전해진다. 크루 전체가 보는
지면(전광판)에는 칭호 소식이 없어, 신규 칭호 대량 추가(중규모 작업 2번) 후 sweep으로
칭호가 무더기로 풀려도 공기가 조용하다. 리드 슬롯 하나로 "요즘 누가 뭘 달았나"를
1면에 올린다.

참고: `components/home/recent-titles.tsx`(RecentTitles)는 옛 홈(달력)용으로 만들다 만
**미사용 죽은 코드**다. 이 슬롯이 그 역할을 대체하므로, 구현 시 함께 삭제한다.

## 결정 요약 (브레인스토밍 수렴 과정)

| 쟁점 | 결정 | 근거 |
|------|------|------|
| 슬롯 주인공 | **나열형 — 칭호별 획득자 묶음** | 사람 중심(대표 1건)은 "한 번에 한 명만"이 아쉽고, 같은 칭호를 여러 명이 동시에 따는 지면(sweep)이라 칭호별 묶음이 소식의 실제 단위다. 한마디·소개 같은 사람 부품은 싣지 않는다 |
| 문법 | 대회 슬롯 roster 재사용 | "참가자를 종목별로 묶어 나열" → "획득자를 칭호별로 묶어 나열". 살아있는 문법이라 새 어법 발명이 없다. (우측 레일은 은퇴한 문법이라 기각 — story-lede.tsx:255) |
| 노이즈 | **뉴비 제외** | 가입 즉시 전원 수여(`membership_days: 0`)는 사건이 아니고, 새 얼굴 슬롯이 이미 그 소식을 전한다 |
| 칭호 선정 | **랜덤이 아니라 3개씩 회전** | 셔플이면 운 나쁘게 같은 칭호만 반복 노출될 수 있다(사용자가 직접 지적). rotate는 모든 칭호가 빠짐없이 주기적으로 오르는 걸 보장 — 리드의 기존 원칙 그대로 |
| 응원 | **생략** | 여러 칭호 × 여러 사람이라 응원 대상이 성립하지 않는다. 대회 응원의 교훈(여럿이 나눠 갖는 카운터는 개인 지표로 성립 안 함)과 같은 구조. 덕분에 `bump-reaction` 검증 확장도 통째로 불필요 |
| 윈도우 | 최근 **30일** | 새 얼굴·완주기록 슬롯과 동일 |

## 지면 설계

```
┌──────────────────────────────┐
│ 기강에 새 역사를 쓰다         │ ← kicker (서술체 — 기존 kicker들과 같은 결)
│                              │
│ 최근 30일, 새 칭호 7개 풀리다 │ ← 헤드라인 (hero: "headline")
│                              │
│ [서브4✨]   (준민)            │
│ [대회왕✨]  (현근)(지현)(수진) 외 9 │ ← 칭호별 한 줄 × 최대 3줄
│ [멀티러너✨] (우진)            │
│                              │
│ 획득 12건                    │ ← footer 왼쪽 사실 한 줄 (응원 없음)
└──────────────────────────────┘
```

- **kicker**: `기강에 새 역사를 쓰다` — "새 칭호를 달다"는 너무 직설적이라 업적 달성의
  결로(사용자 지정 방향). 문구는 구현 후 화면을 보며 다듬을 수 있다.
- **헤드라인**: `최근 30일, 새 칭호 {T}개 풀리다` — T = 30일 내 획득이 있었던 칭호
  **종류 수**(화면에 뽑힌 3개가 아님 — 회전해도 안 변한다). 서체는 기존
  `.lede-headline` + 26px 그대로(별도 서체 지정 없음 — 코드 주석의 "명조"는 옛 어휘고
  실제는 Pretendard다).
- **줄(row)**: `TitleBadge`(effect `null` — **이펙트는 칭호가 아니라 사람의 소유다.**
  `ttl_mst`엔 이펙트 컬럼이 없고 `team_mem_rel.selected_badge_effect`가 정본이라, 여러
  사람이 공유하는 칭호 나열에선 기본 배지 스타일이 정확하다) + 아바타 나열 + 넘치면 `외 N`.
  - 한 칭호는 **무조건 한 줄** — 줄바꿈하면 3줄 예산이 무너진다. 얼굴은 배지 폭에 따라
    4~6명, 나머지는 `외 N`(리드의 기존 `moreCount` 문법).
  - 줄 안 얼굴 순서는 **최신 획득순 고정**(랜덤 아님) — "누가 방금 받았나"가 정보값.
  - `외 35` 같은 큰 숫자는 지면 파손이 아니라 "이 칭호 엄청 풀렸다"는 뉴스 그 자체다.
- **탭**: 얼굴 → 프로필 카드 팝업(`onSelectMember`, 보이는 얼굴만 — `외 N`은 안 눌린다).
  배지 → 칭호 설명 툴팁(TitleBadge `tooltip` prop — desc·visibility. `isHeld`는 **RPC가
  실어주는 최신 10명**(칭호당 payload 상한 — 아래 데이터 설계 참조) 명단에 내 mem_id가
  있는지로 근사한다. 옛 보유자·11번째 이후 최근 보유자는 false로 판정되는 사소한
  어긋남이 있으나 허용 — 정확히 하려면 내 보유 칭호 전체 조회가 추가로 필요해 v1 범위 밖).
- **footer**: 왼쪽 `획득 {G}건`(G = 총 수여 건수. 기간은 헤드라인이 이미 말하므로
  다시 안 쓴다). 오른쪽 응원 버튼 없음 —
  "다섯 슬롯 모두 응원" 규칙의 예외이며 사유는 위 결정 표. 다른 슬롯의 버튼 위치는
  안 움직인다(이 슬롯에만 없을 뿐).
- **스와이프 순서**: `ORDER` 맨 뒤 — `… race → record → title`. 완주기록과 같은
  "실적 축하" 계열끼리 붙는다.
- **빈 상태**: 30일 내 획득(뉴비 제외)이 0이면 슬롯을 만들지 않는다(빈 칸 금지 — 기존 규칙).

### 회전 규칙

- pool = 30일 내 칭호 목록(각 칭호의 최근 수여 시각 내림차순), 길이 T.
- 표시 = `rotate(titles, titlePick).slice(0, 3)`.
- `initialTitlePick`은 **서버가 뽑는다**(`story/page.tsx` — 기존 initial*Pick과 같은 자리).
  방문마다 다른 페이지에서 시작해 첫 화면부터 다양하고 하이드레이션이 안전하다.
- 한 바퀴 완주마다 `rerollAllPicks`에서 **`titlePick += 3`** (페이지 단위 전진).
  step 3은 T와 무관하게 전 칭호를 커버한다 — gcd(3,T)=3이면 깔끔한 페이지 순환,
  아니면 어긋난 채 전체 순회. 어느 쪽이든 굶는 칭호가 없다.
- T ≤ 3이면 회전은 사실상 무의미(항상 전부 표시) — 그대로 둔다(코드 분기 불필요).

### 264px 예산

kicker + 헤드라인 1줄(숫자 포함이라 짧다) + 3줄 + footer로 여유가 예상되지만,
**반드시 375px 기기 에뮬레이션으로 실측**한다(DESIGN.md 경고 — 창 줄이기 방식은
브라우저 최소 폭에 걸려 잘못된 결론이 난다). 넘치면 줄 높이부터 줄인다.

## 데이터 설계

리드 슬롯이지만 `get_team_story_feed`에 CTE를 얹지 않는다(이미 CTE 10개+ — 깅스타그램·
목표 한마디와 같은 분리 원칙). **별도 통로**:

- **RPC** `get_team_recent_title_grants(p_team_id)`:
  - `mem_ttl_rel`(vers=0, del_yn=false, 만료 제외 — `exp_at IS NULL OR exp_at > now()`)
    × `ttl_mst` × `team_mem_rel`/`mem_mst` 조인.
  - 최근 30일 수여분(`mem_ttl_rel.grnt_at` 기준).
  - **뉴비 제외**: `cond_rule_json->>'type' = 'membership_days' AND (…->>'days')::int = 0`인
    칭호는 거른다.
  - **active 멤버만**(비활성·탈퇴자 얼굴이 지면에 오르면 안 된다 — 카드 RPC와 같은 경계).
  - 반환(칭호별 그룹): `ttl_id, ttl_nm, ttl_desc, desc_visibility, last_grnt_at,
    grant_cnt, grants: [{mem_id, mem_nm, avatar_url, grnt_at}]`(최신순). **`grants`는
    최신순 상위 10건만** 싣는다(얼굴 5명 + isHeld 근사 판정 여유) — 전 수여 행을 그대로
    실으면 sweep(수십 칭호 × 수십 명) 때 RSC payload·캐시가 수십~수백 KB로 는다.
    `grant_cnt`는 자르기 전 **전체 수여 건수**(같은 30일 창 기준)를 담아 `외 N`·footer
    총합 계산에 쓴다. badge_effect는 싣지 않는다(이펙트는 사람 소유 — 지면 설계 참조).
- **쿼리** `getRecentTitleGrants()` (`lib/queries/story-titles.ts`):
  - 캐시 태그 **`story-titles`**, TTL은 story-posts와 같은 급(5분). 획득의 실시간성은
    알림·푸시가 이미 맡고 있어 슬롯은 캐시로 충분하다. 수여 경로(엔진)는 fire-and-forget
    admin 컨텍스트라 revalidate를 걸지 않는다.
- **총계**: T(칭호 종류 수)는 반환 배열 길이로 클라이언트가 계산한다. G(수여 건수)는
  `grants`가 10건에서 잘리므로 배열 길이로는 셀 수 없다 — 각 칭호의 `grant_cnt`를
  더한 값이다.

## 연결 지점 (구현 개요)

1. `story/page.tsx` — `getRecentTitleGrants()` 병렬 호출 + `initialTitlePick` 추첨 →
   `StoryClient` → `StoryLede` props.
2. `story-lede.tsx` — `Lede`에 `titleRoster?` 필드(raceRoster 스타일), `buildLedes`에
   ⑦ 블록, `ORDER`에 `"title"`, `rerollAllPicks`에 `setTitlePick((n) => n + 3)`,
   전용 렌더 분기(3줄 roster).
3. 회전·그룹핑 헬퍼는 `lib/story-title.ts`로 빼서 유닛 테스트
   (`lib/__tests__/story-title.test.ts`) — 30일 필터·뉴비 제외는 RPC 몫이므로
   여기서는 페이지 회전(step 3 전체 커버)·`외 N` 절단을 못박는다.
4. `components/home/recent-titles.tsx` 삭제(죽은 코드 정리).

## 범위 밖 (이번 작업 아님)

- 중규모 작업 2번(신규 칭호 검토·대량 추가), 3번(획득 시 대표 칭호 자동 변경),
  4번(이펙트 해금 시스템) — 별도 설계. 3번이 구현돼도 이 슬롯과는 독립이다(이 슬롯은
  대표 칭호가 아니라 **획득 사건**을 그린다).
- `외 N` 전체 명단 뷰, 릴스식 상세 뷰 — 필요해지면 그때.
- 응원(리액션) — 의도적 생략(결정 표 참조).

## 검증

- `pnpm run lint` / 유닛 테스트(`lib/__tests__/story-title.test.ts`).
- 375px 에뮬레이션 실측(264px 예산) — 화면 확인은 사용자가 직접(관례).

  얼굴·`외 N`이 남는지 — TitleBadge `min-w-0 overflow-hidden`).
- sweep 직후 대량 수여 시나리오: 한 칭호 40명 → `외 35` 한 줄 유지 확인.
