# 전역 접속자 레이어 (Global Presence Layer)

> 2026-09-16 · 브랜치 `feature/global-presence-layer`
>
> **2026-09-17 구현 반영.** 구현하며 몇 군데가 설계와 달라져, 이 문서를 **실제 계약에 맞춰
> 고쳤다**(달라진 이유는 그 자리에 함께 적었다). 설계 시점의 판단만 남겨 두면 나중에 이 문서를
> 보고 작업하는 쪽이 틀린 소유자·레이아웃 값·수명주기를 기준으로 고치게 된다.
> 살아 있는 정본은 `DESIGN.md`의 §앱 셸 — 전역 접속자 레이어다.

전광판(`/story`) 리드 위에서만 유영하던 실시간 접속자 아바타를, **하단 탭바 윗변을 바닥으로 삼는
전역 레이어**로 끌어올린다. 어느 탭에 있든 지금 같이 들어와 있는 사람들이 보인다.

## 1. 지금 어떻게 돼 있나

`components/story/floating-avatars.tsx`(852줄) 한 파일이 네 가지를 한꺼번에 들고 있다.

| 역할 | 내용 |
|---|---|
| 채널 소유 | `story-avatars:${teamId}` — presence(누가 있나) + broadcast(튕김·위치) |
| 명단 상태 | `presence` state, sync마다 갱신 |
| 라벨 | `지금 보는 중 N명` |
| 물리 | rAF 루프 — 중력·바닥 상태머신(4행동)·성격·튕김 |

`story-client.tsx`가 리드 영역(`relative z-0 pb-[24px]`) 안에 `absolute inset-0`으로 얹는다.
아바타 바닥은 그 컨테이너 하단이고, 리드 진행 막대를 가리지 않게 story 쪽 패딩이
`FloatingAvatars`의 `LABEL_H`와 짝지어져 있다.

**루프는 `IntersectionObserver`로 꺼진다** — 밴드가 화면 밖이면 rAF를 취소한다
(`if (!allow || !onScreen) return`).

## 2. 무엇을 바꾸나

### 2.1 채널과 그리기를 분리한다

이 설계의 핵심이다. 셋을 한 몸에 두면 "전역"과 "일부 화면에만 그리기"가 양립하지 않는다.

```
lib/presence/store.ts            ← 모듈 store (명단 · 탭바 유무)
      ↑ write                                    ↑ read
PresenceLayer (루트, 채널 소유)          usePresenceCount() → story 라벨
```

- **채널은 루트 레이아웃에 한 번 붙는다.** 앱을 켜면 join, 닫으면 leave. 페이지를 옮겨도 안 끊긴다.
- **공은 탭바가 있는 화면에서만 그린다.** `(main)` 5탭과 그 하위. `(info)`·`(protected)`는 안 그린다.

**왜 채널을 페이지마다 붙였다 떼면 안 되나**: presence join/leave는 접속 중인 **전원에게** sync를
쏜다. 받은 쪽은 상태를 다시 계산하고 목록을 리렌더한다. 동시 접속 10명일 때 한 사람이
프로필↔설정을 왕복하면 **10대의 기기가** 그 일을 두 번 한다 — 비용이 내 기기가 아니라 남의
기기에서 발생하고 인원수에 비례해 불어난다. 게다가 남들 화면에서 내 공이 사라졌다 새로 떨어져
**눈에 보이는 결함**이 된다. 채널을 한 번만 붙이면 둘 다 없어진다.

**왜 `(info)`엔 안 그리나**: 그 화면들엔 탭바가 없어 바닥이 안전영역까지 내려가는데, 거기가
**폼 제출 버튼이 사는 자리**다(프로필 수정·건의하기·기록 등록). 탭바가 있는 화면에서는 탭바 자체가
방패라 이 충돌이 없다. 관리자 표 편집·약관처럼 "일하는 화면"에 공이 굴러다닐 이유도 없다.

### 2.2 Provider를 만들지 않는다

`AGENTS.md`의 "Context/Provider 패턴 미사용"과 부딪히지 않게, 모듈 레벨 store +
`useSyncExternalStore`를 쓴다. 이 코드베이스엔 이미 같은 문제를 같은 방식으로 푼 선례가 있다 —
`components/app-width-control.tsx`(셸 폭). 트리 어디서든 읽히고 Provider가 안 늘어난다.

**공 좌표(`ballsRef`)는 store가 아니라 `PresenceLayer`의 로컬 `useRef`가 들고 있다.**
설계 땐 store로 올리려 했는데 — `(info)`에 들렀다 돌아올 때 전원이 화면 위에서 새로 떨어지는 걸
막으려던 것이다 — **옮길 필요가 없었다.** 레이어는 루트에 마운트된 채 렌더만 건너뛰므로
컴포넌트가 언마운트되지 않고, 그래서 ref가 그대로 살아 있다. store로 올렸으면 같은 목적을 위해
상태를 한 겹 더 만드는 셈이었다.

store가 들고 있는 건 **명단과 "그리는 화면인가" 둘뿐**이다.

### 2.3 story는 라벨만 남는다

`지금 보는 중 N명`은 전광판에 그대로 둔다(전역으로 올리지 않는다 — 모든 화면에 인원수 카운터가
상주할 이유가 없다). 공이 story 지면을 떠나므로:

- 라벨은 **`PresenceCount`**(`components/story/presence-count.tsx`)가 그린다. 명단은
  `usePresenceCount()`로 읽는다. 설계 땐 `FloatingAvatars`를 라벨 전용으로 "축소"한다고 했는데,
  그 이름은 얼굴이 떠다닌다는 뜻이라 개수만 말하는 컴포넌트에 남길 수 없었다 — 파일 자체는
  `presence-layer.tsx`로 옮겨 갔고(`git mv`로 이력 보존), 라벨은 새 이름으로 뗐다.
- **`BADGE_LIFT`(바닥선 위 겹침)의 근거가 사라진다** — 겹칠 얼굴이 없다. 평범한 자리로 내린다.
- `story-client.tsx`의 `pb-[24px]`와 `LABEL_H` 결합이 풀린다.

## 3. 어디에 서는가

### 3.1 마운트

```
app/layout.tsx
  └ <Suspense fallback={null}><PresenceLayerGate /></Suspense>
```

기존 설치 배너·`PushPermissionPromptGate`와 **같은 자리, 같은 패턴**이다 — `cookies()`를 만지는
조회를 자기 Suspense 경계에 가둬 본문 렌더를 안 막는다. 루트 레이아웃은 지금 async가 아니고
fetch도 없는데, 그 성질을 깨지 않는다.

`PresenceLayerGate`(서버)가 `getCurrentMember()`로 `me`를 뽑아 클라이언트 레이어에 넘긴다.
비로그인도 레이어는 뜬다(익명 track — 지금 동작 유지).

**조회 실패는 격리한다**(`Promise.allSettled`). 루트 레이아웃이라 여기서 던지면 오류 경계가
페이지 본문까지 삼킨다 — **Suspense는 대기를 받아줄 뿐 오류를 막지 못한다.** 장식 하나 때문에
모든 페이지가 같이 죽을 이유가 없다.

- **팀 조회 실패** → 레이어를 안 세운다. 채널 이름이 `story-avatars:${teamId}`라 팀을 모르면
  어느 방에 들어갈지 정할 수 없다(틀린 방에 들어가면 남의 팀에 얼굴이 뜬다).
- **멤버 조회만 실패** → 레이어는 세우고 `me`만 null. 로그인 사용자가 그 한 번의 렌더에서
  익명 얼굴로 보이지만, 레이어를 통째로 빼는 것보다 낫다.

### 3.2 바닥선

```css
:root { --tabbar-h: calc(3.5rem + env(safe-area-inset-bottom, 0px)); }
```

레이어는 `bottom: var(--tabbar-h)`에 선다. `3.5rem`은 지금 `(main)/layout.tsx`의 본문 하단
패딩에 리터럴로 박혀 있다 — **변수로 뽑아 둘이 같은 것을 보게 한다.** 한쪽만 고치면 공이
탭바에 파묻힌다.

> 처음엔 `body:has([data-tabbar])`로 탭바 유무에 따라 바닥을 바꾸려 했으나 **필요 없다.**
> 탭바가 없는 화면에선 아예 안 그리므로(§2.1) 그 분기는 영원히 안 쓰이는 죽은 코드가 된다.
> 그릴지 말지는 CSS가 아니라 store가 판정한다 — JS가 알아야 rAF 루프까지 건너뛴다.

### 3.3 레이어 속성

| 속성 | 값 | 근거 |
|---|---|---|
| position | `fixed` + **`.app-fixed`** | `DESIGN.md` 규칙 — 안 붙이면 데스크톱에서 셸 밖 화면 전폭에 남는다 |
| bottom | `var(--tabbar-h)` | 탭바 윗변 |
| top | `0` — **천장은 화면 끝** | 설계 땐 45px 띠였다. 그러면 바닥이 0이 되어 탭해도 공이 안 뜬다. 224px(튕김 최고점 ≈177 + 32 + 13)로 늘렸다가, 그 매직넘버마저 없애고 화면 끝까지 열었다 — 공중의 공을 한 번 더 쳐서 계속 올려 보낼 수 있다. 실제 높이는 ResizeObserver가 잰다 |
| z-index | **`z-40`** | 탭바·FAB·다이얼로그(`z-50`) **아래** — 공이 FAB 뒤로 지나간다 |
| pointer-events | 래퍼 `none`, 공만 `auto` | |
| overflow | `hidden` | 날아간 공이 문서 크기를 늘려 스크롤바를 만들지 않게 |

`z-40`이 FAB 충돌을 구조적으로 없앤다. 공은 FAB **뒤로** 걸어가고 탭은 FAB이 받는다.
띠 안에 걸치는 본문 콘텐츠와는 여전히 겹칠 수 있으나, 본문은 스크롤되므로 되돌릴 수 있다.

> ⚠️ 셸에 `transform`/`contain`을 걸지 않는다(`DESIGN.md` 경고). 이 레이어는 `<body>` 직계라
> 셸 스태킹 컨텍스트에 안 갇힌다.

## 4. 버리는 것

| 버림 | 이유 |
|---|---|
| `IntersectionObserver` + `onScreen` | 고정 레이어는 항상 보인다 — 관찰 대상이 없어진다 |
| `hasPresence` deps 우회 | 위 옵저버가 `return null` 타이밍에 안 붙던 문제를 막던 장치. 같이 없어진다 |
| ~~루프 재시작용 `syncTransforms()` 호출~~ | **안 버렸다.** 탭바 있는 화면으로 돌아오면 DOM 노드가 새로 생겨 좌상단에 있으므로, 여기서 한 번 찍어야 아까 걷던 자리로 복귀한다 |
| `wrapRef.clientWidth/clientHeight` 매 프레임 읽기 | 프레임마다 레이아웃 플러시를 강제한다 → ResizeObserver 캐시 |
| `prefers-reduced-motion`의 정적 얼굴 줄 | 모든 화면 하단에 상시 얼굴 줄은 장식이 아니라 방해다 → **아무것도 안 그린다** |
| story의 `BADGE_LIFT` · `pb-[24px]`↔`LABEL_H` 결합 | 겹칠 얼굴이 없어진다 |

`visibilitychange`(탭 복귀 시 `last = 0`)는 **남긴다.** 백그라운드에서 rAF가 멈췄다 돌아올 때
`d`가 상한 3까지 튀는 걸 막는 장치라 전역에선 더 자주 쓰인다.

**"안 보일 땐 안 움직인다"는 형태를 바꿔 남는다**: 스크롤 위치가 아니라 **이 화면이 공을 그리는
화면인가**로 판정한다(`(main)` 여부). 훨씬 싸고 판정이 명확하다.

## 5. 최적화

| 항목 | 지금 | 바꿀 것 |
|---|---|---|
| 컨테이너 치수 | 프레임마다 `clientWidth/Height` 읽기 | ResizeObserver로 캐시. 폭은 셸 폭이라 거의 안 변한다 |
| 렌더 개수 | **상한 없음**(`presence.map` 전원) | **30명**에서 끊는다 |
| `renderHitBadges` | 공마다 매 프레임 `Array.from` + `sort` | `hits.size === 0 && host.childElementCount === 0`이면 즉시 return |
| 그리지 않는 화면 | — | 렌더와 rAF 루프를 **통째로** 건너뛴다 |

### 5.1 렌더 상한 30

**실사용에선 안 걸리는 값이다.** 활동 멤버가 135명(prd 실측)이라 동시 접속이 30을 넘길 일이
사실상 없다 — 이건 "몇 명까지 보여줄까"가 아니라 **비정상 상황의 뚜껑**이다(익명·크롤러가 몰리는
경우 등). 총원은 story 라벨이 말하므로 공은 분위기만 맡는다.

> 설계 땐 12였다. "몰리면 공이 들어차 신청 버튼을 누르기 어렵다"는 이유였는데, 그 전제가
> 실제와 달랐다 — 층이 `pointer-events-none` + `z-40`이라 버튼을 가리지 않고, **공끼리 겹쳐
> 보이는 건 막을 이유가 없는 의도된 모습**이다. 남는 진짜 제약은 이름표 가독성뿐이다.

**선별은 결정적이어야 한다.** 랜덤이면 presence sync마다 얼굴이 갈려 깜빡인다. 규칙은 둘뿐이다:

1. 내가 명단에 있으면 **나는 항상 포함**한다 — 내 공이 안 보이면 "나는 왜 없지"가 된다
2. 나머지는 `mem_id` **오름차순**으로 채운다

`mem_id`는 안 변하는 값이라 같은 명단이면 같은 얼굴들이 나온다. 접속·이탈로 명단이 바뀔 때만
얼굴이 바뀌고, 그건 실제로 바뀐 것이라 맞다.

### 5.2 느려지면 그건 버그다

30개 요소가 `transform`으로 움직이는 건 요즘 기기에 부담이 아니다. 느려진다면 용량 문제가 아니라
아래 중 하나가 깨진 것이다. 구현·리뷰에서 이 표를 확인한다.

| 하면 느려지는 것 | 지킬 것 |
|---|---|
| 매 프레임 React 리렌더 | rAF에서 **DOM에 직접** 쓴다(지금 코드가 그렇다 — 리팩터링하며 깨지 않는다) |
| 스타일 쓴 뒤 치수 읽기 | 읽기를 **아예 없앤다**(ResizeObserver 캐시) |
| `top/left`로 이동 | `transform`만 — 컴포지터가 처리 |
| `boxShadow`를 매 프레임 | 튕긴 직후(`pop > 0`)에만 — 지금도 그렇다 |
| 인원 상한 없음 | 30 |
| **rAF가 두 개 도는 것** | cleanup에서 `cancelAnimationFrame` · `removeChannel`이 확실히 돌 것 |

마지막이 이 작업의 가장 현실적인 위험이다. 레이어를 전역으로 올리면서 마운트가 잘못 걸리면
루프가 겹쳐 돌 수 있고, 그게 전형적인 "갑자기 느려졌다"의 정체다.

## 6. 안 건드리는 것

broadcast 튕김(누구·방향·세기), 성격(`getPresencePersona`), 색 고정(`mem_id` 해시), 물리 상수,
바닥 4행동, 익명 track, `useAllowMotion` 게이트 — 전부 그대로다.

**채널 이름 `story-avatars:${teamId}`도 유지한다.** 이름이 story를 가리키게 되지만, 바꾸면 배포
중 구·신 버전이 **다른 방에 들어가 서로 안 보인다.** 이름값보다 연속성이 중요하다.

순수 함수에만 붙인다. 물리와 rAF는 지금도 테스트가 없고 이 변경으로 생기지 않는다.

- `lib/presence/__tests__/pick.test.ts` — **선별**: 결정적인가(같은 입력 → 같은 출력),
