# 모임 참여조건 · 운영진 승인제 — 설계 스펙

> 작성일: 2026-08-25 · 상태: 설계 확정(구현 전)
> 계기: 2026 송년회 — "최근 6개월 모임 참석 6회 이상"인 사람만 신청할 수 있고,
> 입금을 확인한 운영진이 승인해야 참가가 확정된다.

## 1. 목적 · 범위

모임에 **참여조건**과 **운영진 승인제**를 건다. 둘 다 **모임별 옵션**이고 **서로 독립**이다.

- **In scope**: 조건(최근 N개월 모임 참석 M회 이상) · 승인제(신청 → 대기 → 승인/거절) ·
  모임 생성/수정 폼의 설정 UI · 모임 상세의 신청/승인 UI · 알림 3종.
- **Non-goals**: 회원등급제(§10 — 확장점만 열어두고 만들지 않는다) · 입금 자동 대사 ·
  대기열 자동 승격 · 조건 OR 조합 · MCP 도구에 조건 필드 노출.
- **원칙**: 옵션을 안 켠 모임(= 현재 존재하는 모든 모임)은 **코드 경로가 지금과 완전히 동일**해야 한다.

## 2. 핵심 결정 — 왜 별도 신청 테이블인가

`gthr_attd_rel`은 **행이 존재하면 곧 참석 확정**이다(상태 컬럼이 없다). 그리고 그 불변식에
70개 파일이 매달려 있다 — 포인트 적립 트리거(`trg_pt_gthr_attd_rel`, `AFTER INSERT`),
칭호 엔진, 월 활동량 집계, 팀 펄스, 전광판 피드, 유령회원 판정, 관리자 참석통계, MCP,
뉴비 넛지 크론.

따라서 **승인 대기를 이 테이블에 담으면 신청만 해도 포인트가 붙고 참석자 수에 잡힌다.**

| 안 | 내용 | 판정 |
|---|---|---|
| **A** | 별도 `gthr_aply_rel`에 신청/대기/거절을 담고, **승인되는 순간에만** `gthr_attd_rel`에 INSERT | **채택** |
| B | `gthr_attd_rel`에 `st_cd` 추가 | 기각 — `COUNT(*)`를 참석자 수로 쓰는 곳 전수에 필터를 넣어야 하고, **DB 트리거는 앱 코드에 훅이 없어**(AGENTS.md) 누락이 조용히 통과한다. `UNIQUE(gthr_id, mem_id)`가 거절 이력과도 충돌 |
| C | 정책 엔티티 분리(`gthr_plcy_mst` + 조건 행 N개) | 기각 — 조건이 하나뿐인데 정책 CRUD가 생긴다. 게다가 정책을 나중에 수정하면 **이미 끝난 모임의 조건이 소급으로 바뀐다**(§3.1) |

A안의 대가는 승인제 모임에서 한 사람이 두 테이블에 행을 갖는다는 것이다. 승인·취소를
**원자적 RPC**로 묶어 해소한다(`cancel_gthr_attendance` 선례와 같은 이유).

## 3. 데이터 모델

### 3.1 `gthr_mst` 컬럼 3개 추가

```sql
ALTER TABLE public.gthr_mst
  ADD COLUMN aprv_req_yn     boolean NOT NULL DEFAULT false,
  ADD COLUMN req_attd_cnt    int,
  ADD COLUMN req_attd_months int;

COMMENT ON COLUMN public.gthr_mst.aprv_req_yn     IS '운영진 승인제 여부. true면 신청→승인 후에만 참가 확정';
COMMENT ON COLUMN public.gthr_mst.req_attd_cnt    IS '참여조건: 필요 모임 참석 횟수 (NULL=조건 없음)';
COMMENT ON COLUMN public.gthr_mst.req_attd_months IS '참여조건: 최근 N개월 (req_attd_cnt와 함께만 의미)';

ALTER TABLE public.gthr_mst ADD CONSTRAINT ck_gthr_mst_req_attd
  CHECK ((req_attd_cnt IS NULL) = (req_attd_months IS NULL));
```

**jsonb가 아니라 컬럼인 이유**: 조건 값이 모임 행에 박혀 있으면 **과거 모임이 자기 조건을
영구히 들고 있다.** 조건 체계가 나중에 바뀌어도 작년 송년회는 "최근 6개월 6회"로 남는 게
맞다. 화면 문구 조립도 zod 검증도 컬럼 쪽이 공짜다.

### 3.2 `gthr_aply_rel` 신설

```sql
CREATE TABLE public.gthr_aply_rel (
  aply_id       uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  gthr_id       uuid        NOT NULL REFERENCES public.gthr_mst(gthr_id),
  mem_id        uuid        NOT NULL REFERENCES public.mem_mst(mem_id),
  aply_st_cd    text        NOT NULL CHECK (aply_st_cd IN ('pending','approved','rejected','canceled')),
  aply_memo_txt text,                                  -- 신청자 한마디(입금자명 등)
  rvw_by        uuid        REFERENCES public.mem_mst(mem_id),
  rvw_at        timestamptz,
  rvw_memo_txt  text,                                  -- 거절 사유
  crt_at        timestamptz NOT NULL DEFAULT now(),
  upd_at        timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT uk_gthr_aply_rel_gthr_mem UNIQUE (gthr_id, mem_id),
  CONSTRAINT ck_gthr_aply_memo_len     CHECK (char_length(aply_memo_txt) <= 200),
  CONSTRAINT ck_gthr_aply_rvw_memo_len CHECK (char_length(rvw_memo_txt) <= 500)
);

CREATE INDEX ix_gthr_aply_rel_gthr_st ON public.gthr_aply_rel(gthr_id, aply_st_cd);
CREATE INDEX ix_gthr_aply_rel_mem     ON public.gthr_aply_rel(mem_id);
```

`UNIQUE(gthr_id, mem_id)`로 한 사람당 한 행. 재신청은 같은 행 UPDATE(`rejected`/`canceled` → `pending`)다.
길이 상한은 서버 액션과 DB 양쪽에서 강제한다(`gthr_attd_hist.reason_txt`와 같은 태도).

### 3.3 RLS — 떨어진 사람이 공개되지 않게

| 대상 | SELECT |
|---|---|
| 본인 행 | 허용 |
| 모임 개설자(`gthr_mst.crt_by`) · 팀 owner/admin | 허용 |
| 그 외 팀원 · anon | **차단** |

INSERT/UPDATE 정책은 두지 않는다 — 쓰기는 전부 SECURITY DEFINER RPC와 서버 액션이 한다
(`gthr_attd_hist`와 같은 패턴).

> 확정 참가자 명단(`gthr_attd_rel`)은 **지금처럼 팀 전체 공개 그대로**다. 비공개로 돌리는 건
> 대기·거절뿐이다. "누가 떨어졌는지"가 공개되면 안 된다.

## 4. 조건 판정 — `lib/gathering/join-condition.ts`

반환은 `boolean`이 아니라 **조건 목록**이다. 화면이 "현재 4회"를 보여줘야 해서 boolean으로는
어차피 부족하고, 조건이 늘어도 호출부·UI를 안 고치게 된다.

```ts
export type JoinCondition = {
  cd: "attd_cnt";            // 등급제가 오면 | "grade" 만 늘어난다
  label: string;             // "최근 6개월 모임 참석 6회 이상"
  met: boolean;
  current: string | null;    // "현재 4회"
};
export type JoinConditionResult = { ok: boolean; conditions: JoinCondition[] };
```

집계 쿼리(`gthr_attd_rel` ⋈ `gthr_mst`):

- `team_id` 일치 · `del_yn = false`
- **`stt_at <= now()`** — 안 걸면 아직 열리지도 않은 미래 모임 신청분이 "참석 6회"에 섞인다.
  `app/actions/gathering/toggle-attendance.ts`의 칭호 주석이 지적한 것과 같은 함정이다.
- `stt_at >= (기준일 - N개월)`

**기준 시각은 신청 시점의 KST**(`todayKST()`). 승인 시점에 재판정하지 않는다 — 6개월 롤링이라
시간이 지나면 옛 참석이 윈도우 밖으로 빠져 조건이 조용히 떨어질 수 있는데, 신청 때 통과한
사람을 나중에 떨구는 건 부당하다. 사용자가 화면에서 본 숫자와 판정이 일치해야 한다는 이유도 같다.

## 5. 상태 전이 · 서버 구성

### 5.1 경로 셋

| 조건 | 승인 | 동작 |
|---|---|---|
| ✗ | ✗ | **현행 그대로.** 코드 경로 변화 없음 |
| ✓ | ✗ | 참석 토글 앞에 조건 검사만 추가. `attd_rel` 직행 |
| ✗/✓ | ✓ | 신청 → 대기 → 승인 시에만 `attd_rel` 진입 |

### 5.2 승인제 상태 전이

```text
(없음) ──신청──▶ pending ──승인──▶ approved ─┬─본인취소───▶ canceled
                    │                        └─운영진취소─▶ canceled
                    ├──거절────▶ rejected ──재신청──▶ pending
                    └──본인 신청취소──▶ canceled ──재신청──▶ pending
```

`approved`로 넘어가는 순간에만 `gthr_attd_rel`에 INSERT한다. **그 한 줄이 "확정"의 정의**이고,
포인트·칭호·집계가 거기서 비로소 돈다.

### 5.3 구성

| 자리 | 내용 |
|---|---|
| `lib/gathering/join-condition.ts` | 조건 판정 코어. 액션·MCP 공유 |
| `lib/gathering/application.ts` | 신청/승인/거절 코어 — **클라이언트 주입식**(AGENTS.md MCP 규약) |
| RPC `approve_gthr_application` | **모임 행을 `SELECT ... FOR UPDATE`로 잠그고 → 정원 재확인 → `attd_rel` INSERT → `aply_st_cd='approved'`를 한 트랜잭션에** |
| 액션 | `applyToGathering` / `cancelMyApplication` / `approveApplication` / `rejectApplication` |
| 검증 | `lib/validations/gathering.ts`에 조건·승인 필드 추가(기존 스키마 확장) |

**정원은 승인 시점에만 본다** — 승인된 사람만 정원을 먹는다(§9-b). 신청(대기)은 정원과
무관하게 무제한으로 받는다.

> ⚠️ **`joinGatheringWithCapCheck`를 승인 경로에 재사용하지 않는다.** 그 함수의 정원 체크는
> `COUNT` → `upsert` 2단계라 원자적이지 않다(TOCTOU). 지금은 사람이 각자 누르는 참석 토글이라
> 동시성이 낮아 견디지만, **승인은 운영진이 목록에서 연달아 누르는 동작**이라 정확히 그 레이스를
> 탄다. 승인은 RPC 안에서 모임 행을 잠그고 센다.

**`toggleGatheringAttendance`는 승인제 모임에 대해 서버에서 거부한다.** 버튼을 감추는 건
안내일 뿐이고 `gthr_id`만 알면 액션은 직접 호출된다 — 안 막으면 승인제가 통째로 우회된다.
조건만 켠 모임에서는 토글 앞에서 조건을 서버가 재검증한다.

**지난 모임 잠금**(`isPastLockedFor`)은 신청·승인에도 그대로 적용된다.

## 6. UI

### 6.1 설정은 생성 폼과 수정 폼 **양쪽**에 (별도 관리 화면 없음)

접이식 **"참여 조건 · 승인"** 섹션, 기본 접힘. 모임 타입과 무관하게 노출한다.

폼이 두 벌이다 — `components/schedule/gathering-form-dialog.tsx`(일정탭 다이얼로그)와
`app/(info)/gatherings/new/gathering-form.tsx`(전용 페이지).
**공용 필드 컴포넌트 `GatheringConditionFields` 하나**를 만들어 양쪽에 꽂는다. 각자 그리면
한쪽만 고쳐져 반드시 어긋난다(`PhotoPicker`·`RecordDeleteDialog`와 같은 이유).

### 6.2 모임 상세 — 화면이 두 벌이 아니라 **데이터 경로가 두 벌**이다

`app/(info)/gatherings/[id]/page.tsx`는 **서버 컴포넌트가 직접 쿼리**하고,
`components/schedule/gathering-detail-dialog.tsx`는 **`mini-calendar.tsx`가 클라이언트에서
`get_gathering_detail` RPC로** 채운다. 따라서 공용화는 **표시 컴포넌트까지만** 되고 데이터
조달은 두 경로에 각각 붙여야 한다.

**신청 자체는 다이얼로그 안에서 끝난다** — 참석 토글이 있던 **바로 그 자리에** 같은 모양으로
신청 버튼이 선다. 다른 화면으로 보내지 않는다: 달력에서 연 사람에게 페이지 이동은 맥락을
끊고, 신청은 버튼 하나로 끝나는 일이라 넓은 화면이 필요하지도 않다.
(한때 "참가 신청하러 가기" 링크로 모임 상세로 보냈는데 걷어냈다 — 2026-08-27.)

조건 블록·버튼 상태는 **공용 컴포넌트**를 페이지와 다이얼로그가 함께 쓴다. 다이얼로그는
클라이언트라 조건을 스스로 계산할 수 없어 `getMyGatheringApplication` 액션으로 받아 온다
(`get_gathering_detail` RPC 에 실으면 anon 에게까지 샌다 — §8-9).

**신청 "관리"(승인·반려 목록)만 페이지에 남는다** — 목록과 메모를 보고 판단하는 다른 성격의
일이라서다.

- **조건 블록**: `conditions` 배열을 그대로 렌더 — `최근 6개월 모임 참석 6회 이상 · 현재 4회`.
  미달이면 버튼 비활성 + 사유 노출.
- **버튼 상태**: `참가 신청` → `승인 대기 중`(신청취소 가능) → `참가 확정` / `거절됨`(사유 표시, 재신청 가능)
- **신청 관리 (N)** 섹션: 개설자·운영진에게만. 대기 목록 + 승인/거절 버튼, 처리된 건은 접힘.
  신청 메모(입금자명)를 각 행에 함께 보여준다.

디자인 토큰·타이포그래피는 DESIGN.md 규칙을 따른다(`EmptyState`·`Body`·`Caption`·`CardItem`,
설명이 필요한 자리엔 `HelpTip`).

## 7. 알림 3종 신설

| 타입 | 수신자 | 내용 |
|---|---|---|
| `gthr_aply` | 개설자 + 팀 운영진(`team_role_cd` in `owner`/`admin`), 중복·본인 제외 | "{이름}님이 '{모임}' 참가를 신청했어요" |
| `gthr_aprv` | 신청자 | "'{모임}' 참가가 확정됐어요" |
| `gthr_rjct` | 신청자 | "'{모임}' 참가 신청이 반려됐어요" + 사유 |

세 곳을 함께 건드려야 한다: `noti_mst`의 `noti_type_enm` CHECK 제약 마이그레이션 ·
`lib/notifications/deep-link.ts` 맵(모두 `?gthr=` 딥링크) · 알림 수신거부 설정 항목.

발송은 `insertNoti`/`insertNotiMany`를 그대로 쓴다(웹푸시가 자동으로 따라온다).
응답 경로 밖(`after`)에서 보낸다 — 승인 버튼의 체감 지연이 되지 않게.

## 8. 함정 목록

놓치면 조용히 깨지는 것들. 구현 시 각각 테스트로 못박는다.

1. **운영진 대리 참석 추가**(`addGatheringAttendance`, `app/actions/admin/manage-gathering-attendance.ts`)가
   `attd_rel`만 넣으면 `aply_rel`과 어긋난다 → 승인제 모임이면 `approved` 행도 함께 만든다.
   **이 문이 조건 미달자의 유일한 예외 구제 경로다**(조건은 하드 게이트라서).
2. **운영진 대리 취소**(`removeGatheringAttendance`)도 `aply`를 `canceled`로 내린다.
3. **이미 참석자가 있는 모임에 승인제를 켤 때** — `updateGathering` 안에서 기존 `attd_rel` 행을
   `aply_rel`에 `approved`로 백필한다. 안 하면 확정자들이 상태 없는 유령이 된다.
4. 조건 집계의 **`stt_at <= now()`** (§4).
5. **KST** — 6개월 경계는 `todayKST()`, `_at` 표시는 `formatKST`(AGENTS.md 날짜 규칙).
6. **RLS** — 대기·거절은 본인 + 개설자 + 운영진만(§3.3).
7. **MCP** `lib/mcp/create-gathering.ts`는 조건 필드를 노출하지 않고 기본값으로 생성한다.
   검증 스키마는 앱과 같은 것을 쓴다(AGENTS.md 운영 MCP 규약).
8. **캐시** — `revalidatePath('/gatherings/[id]')`. 일정 목록 RPC의 `attd_count`는 승인 전엔
   변하지 않는다(의도대로).
9. **`get_gathering_detail` RPC에는 조건 필드만 싣는다.** 그 RPC는 `SECURITY DEFINER`이고
   `GRANT EXECUTE ... TO anon`이라, 대기·거절자를 실으면 §3.3의 RLS를 통째로 우회해
   **비로그인 방문자에게까지 떨어진 사람 명단이 나간다.** 조건 필드
   (`aprv_req_yn`/`req_attd_cnt`/`req_attd_months`)는 모임 속성이라 anon이 봐도 무방하다
   (`gthr_mst` 자체가 이미 anon SELECT 허용). **내 신청 상태·신청 관리 목록은 RLS 클라이언트로
   별도 조회**한다.
10. **개설자 자동 참석**(`createGathering`이 `after`에서 `gthr_attd_rel`에 넣는다)도 승인제 모임이면
    `aply_rel`에 `approved` 행을 함께 만든다. 안 하면 **모임을 만든 사람 자신이 상태 없는 유령**이
    되고, 정원 계산에는 잡히는데 신청 관리 목록엔 안 보인다. 개설자에게는 조건을 적용하지 않는다.
11. **알림 수신자 중복 제거** — 개설자가 운영진이면 `gthr_aply`가 두 번 간다. `mem_id` 기준으로
    합치고, **신청자 본인은 수신자에서 뺀다**(운영진이 조건부 모임에 직접 신청하는 경우).

## 9. 확정된 정책 결정

| # | 결정 | 근거 |
|---|---|---|
| a | **조건 미달자는 신청 버튼이 잠긴다** (하드 게이트, 서버도 거부) | 거절 커뮤니케이션 부담을 없앤다. 예외는 §8-1의 운영진 대리 추가로만 |
| b | **승인된 사람만 정원을 먹는다** | 사실상 "입금 선착순". 대기는 무제한으로 받고 운영진이 정원까지 승인 |
| c | **조건의 '참가'는 모임 참석만**(`gthr_attd_rel`) | "모임에 오는 사람에게 송년회 자격"이라는 취지가 가장 선명 |
| d | **승인 주체는 운영진 + 모임 개설자** | 입금 확인은 총무가, 개설자는 다를 수 있다. 일반 멤버가 조건부 모임을 열어도 그대로 굴러간다 |
| e | **거절 후 재신청 허용** | 미입금으로 거절했다가 입금하면 다시 받아야 한다 |
| f | **신청은 한 번 누르면 끝난다 — 입력 단계 없음** (2026-08-27 정정) | 처음엔 "입금자명" 메모 모달을 뒀는데 **입금 확인은 송년회 한 사례일 뿐**이고 승인제는 그 말고도 쓴다. 항상 필요하지도 않은 입력을 모두에게 세우면 버튼 하나로 끝날 일이 매번 모달을 닫는 일이 된다. `aply_memo_txt` 컬럼과 액션의 `memo` 인자는 남겨 둔다 — 필요해지면 그때 받으면 되고, 지금 지우면 마이그레이션만 왕복한다 |
| g | **승인제 해제는 대기 0건일 때만** | 자동 승인은 정원을 넘기고, 방치하면 신청자가 영원히 대기에 갇힌다 |
| h | **정원을 승인 인원보다 작게 줄이는 건 경고만 하고 허용** | 이미 승인한 사람을 밀어내지 않는다 |
| i | **대기 중에는 "참석 예정"으로 안 보인다** | `attd_rel` 불변식 그대로 — 일정탭 참석 표시·참석자 수에 안 잡힌다 |

## 10. 회원등급제가 오면

이 설계는 등급제의 모양을 **전혀 선점하지 않는다.** 등급이 어떤 형태로 오든 붙이는 건 넷뿐이다.

| 자리 | 추가 |
|---|---|
| `gthr_mst` | `req_grade_cd text` 컬럼 하나 |
| `join-condition.ts` | 판정 갈래 하나 (`cd: "grade"`가 배열에 하나 더 들어갈 뿐) |
| 폼 | 등급 셀렉트 하나 |
| 상세 | 안내 문구 한 줄 |

**신청→승인 상태머신은 한 줄도 안 바뀐다** — 조건이 무엇이든 흐름이 같기 때문이다.
조건과 승인을 독립 옵션으로 갈라둔 값어치가 여기서 나온다.

다만 **등급이라는 개념을 만드는 일 자체**는 이번 기능의 몇 배짜리 별건이다. 현재
`team_mem_rel.team_role_cd`는 `owner/admin/member` **권한**이지 등급이 아니다. 등급을 어디에
둘지, 누가 언제 올리고 내리는지(수동 부여 / 활동량 기반 자동 승급), 강등이 있는지, 이력을
남기는지는 그때 따로 브레인스토밍한다.

## 12. 마이그레이션 순서

1. `gthr_mst` 컬럼 3개 + CHECK
2. `gthr_aply_rel` + 인덱스 + RLS
3. `approve_gthr_application` RPC (SECURITY DEFINER, service_role 전용)
4. `get_gathering_detail` RPC에 조건·승인·내 신청 상태 추가
5. `noti_mst` CHECK 제약에 `gthr_aply`/`gthr_aprv`/`gthr_rjct` 추가

기존 데이터 백필은 없다 — 새 컬럼 기본값이 "옵션 꺼짐"이라 현재 모든 모임이 현행 그대로다.

**dev(ggd) 적용 완료(2026-08-25). prd 는 아직이다.**

타입은 **전체 재생성하지 않고 신규 블록만 손으로 끼워 넣었다**(KNOWLEDGE.md의 dev↔prd
스키마 drift 경고). `git diff --numstat` 기준 103줄 추가 · **0줄 삭제** — 재정렬 노이즈나
drift 소실이 없다는 뜻이다. 같은 방식으로 prd 에 적용할 때도 전체 재생성은 하지 않는다.

⚠️ **컬럼명을 손볼 땐 gen types 를 먼저 돌린다** — supabase-js 의 `.insert()`/`.update()` 는
초과 속성 검사를 하지 않아 오타를 tsc 가 안 잡아 준다(KNOWLEDGE.md).
