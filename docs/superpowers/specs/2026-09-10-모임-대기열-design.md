# 모임 대기열 — 설계

- 날짜: 2026-09-10
- 대상: 비승인제 모임(`aprv_req_yn = false`)의 정원 마감 대기열
- 선행 설계: [`2026-08-25-모임-참여조건-승인제-design.md`](./2026-08-25-모임-참여조건-승인제-design.md)

## 0. 왜

정기런은 정원이 20명인데 실제로는 20명을 넘겨 받고 있다(운영진이 필요한 사람을 직접
넣는다). 그 상태에서 더 오고 싶은 사람이 생기면 지금은 **길이 없다** — 버튼이 "인원이
마감됐습니다"로 막히고, 나중에 누가 취소해도 그 자리가 났다는 걸 아무도 모른다.

대기열은 그 자리를 **선착순으로 잇는다.** 취소가 나면 가장 오래 기다린 사람이 자동으로
참석자가 되고 알림을 받는다.

## 1. 결정 사항 (오너 확인 완료)

| 질문 | 결정 |
|---|---|
| 자리가 나면 어떻게 올리나 | **자동 승급 + 알림.** 운영진 손이 안 간다 |
| 어떤 모임에 붙나 | **비승인제만.** 승인제는 지금처럼 운영진이 골라 승인 |
| 대기 줄을 어디에 세우나 | **새 테이블 `gthr_wait_rel`** |
| 온보딩 뉴비가 만석 모임을 고르면 | **대기로 등록** (지금은 가입 도중 오류) |

### 1-1. `gthr_attd_rel`에 상태 컬럼을 얹지 않는 이유

그 테이블에는 포인트 트리거(`trg_pt_gthr_attd_rel`)·칭호 엔진·월 활동량 집계·유령회원
판정이 **"행이 있으면 곧 참석 확정"** 이라는 불변식에 매달려 있다. 대기 상태를 컬럼으로
얹으면 **대기만 걸어도 포인트가 붙는다.** 승인제 설계가 같은 이유로 이미 이 길을 막아 놨고
(`20260825110000_gthr_aply_rel.sql` 주석), 이번에도 같은 판단이다.

### 1-2. `gthr_aply_rel`(승인제 신청)을 재사용하지 않는 이유

모양은 비슷하다(UNIQUE + 상태 enum). 그런데 재사용의 이득이 생각보다 작다:

- **승급 RPC는 어차피 새로 써야 한다.** `approve_gthr_application`은 "운영진이 지정한
  mem_id를 승인"이라, "가장 오래 기다린 사람을 올려라"와 시그니처가 다르다. 재사용되는
  건 테이블 껍데기뿐이다.
- `aply_st_cd = 'pending'`이 모임 종류에 따라 *심사 대기*와 *자리 대기* 두 뜻이 된다.
  그러면 기존 승인제 쿼리 전부에 `aprv_req_yn` 분기가 붙는다 —
  `listPendingApplicationGatherings()`(운영진 "심사 대기 남은 모임")가 비승인제 대기자까지
  긁어와 "심사해라"로 보이는 종류의 **조용한 회귀**가 생긴다.
- `aply_memo_txt` · `rvw_by` · `rvw_memo_txt` 같은 심사용 컬럼이 대기열에 무의미하게 딸려온다.

테이블 하나를 아끼는 값보다 **승인제 흐름에 회귀를 안 심는 값**이 크다.

## 2. 테이블 — `gthr_wait_rel`

```
wait_id     uuid        PK
gthr_id     uuid        NOT NULL FK gthr_mst
mem_id      uuid        NOT NULL FK mem_mst
wait_st_cd  text        NOT NULL DEFAULT 'waiting'
                        CHECK IN ('waiting','promoted','canceled')
wait_at     timestamptz NOT NULL DEFAULT now()   -- 순번의 정본
crt_at      timestamptz NOT NULL DEFAULT now()
upd_at      timestamptz NOT NULL DEFAULT now()
UNIQUE (gthr_id, mem_id)
```

### 2-1. 순번은 `wait_at` 하나로 정해진다 — `crt_at`이 아니다

두 컬럼을 따로 두는 이유가 이 기능의 핵심 엣지케이스다.

> 참석 → 취소 → (그 사이 만석) → **다시 참석을 누름**

이때 같은 행을 재사용(`UNIQUE` upsert)하면서 `wait_at`을 `now()`로 갱신해 **줄 맨 뒤로**
보낸다. `crt_at`으로 정렬하면 이 사람이 처음 줄 섰던 자리를 그대로 물고 새치기한다.
스스로 자리를 비웠다가 돌아온 사람이 그 사이 기다린 사람을 제치는 건 선착순이 아니다.

**이미 `waiting`인 사람이 또 누르는 건 멱등** — `wait_at`을 갱신하지 않는다. 안 그러면
버튼 연타로 자기 순번을 스스로 뒤로 미는 사고가 난다.

### 2-2. 행을 지우지 않고 상태 컬럼을 둔다

`promoted` · `canceled` 행이 남아 있어야 `wait_at`이 보존되고, 그래야 §2-1의 "재진입은
뒤로 간다"를 판정할 수 있다. `gthr_aply_rel`이 쓰는 것과 같은 관용구다.

### 2-3. RLS

`gthr_attd_rel`과 같은 수준 — **팀 멤버만 SELECT.** INSERT/UPDATE/DELETE 정책은 두지
않는다(= `authenticated`는 직접 쓰기 불가). 쓰기는 SECURITY DEFINER RPC만 한다.

## 3. 승급 — `promote_gthr_waitlist(p_gthr_id, p_team_id) RETURNS uuid[]`

**"빈자리만큼 채운다"** 한 문장이 정의다. 1명이 취소하든 정원을 20→25로 늘리든 같은
함수가 처리하고, 올라간 `mem_id` 배열을 돌려준다.

모임 행을 `FOR UPDATE`로 잠그고 대기자를 `wait_at` 오름차순으로 훑으며, 아래를 **모두**
만족할 때만 한 명을 올린다.

| 조건 | 이유 |
|---|---|
| `aprv_req_yn = false` | 승인제는 운영진이 고른다 (방어적 재확인) |
| `max_prt_cnt IS NOT NULL` | 정원 없는 모임엔 대기열 개념이 없다 |
| `COUNT(gthr_attd_rel) < max_prt_cnt` | **여기서 22명 케이스가 해결된다**(§5-1) |
| `COALESCE(end_at, stt_at) > now()` | 끝난 모임에 자동으로 넣지 않는다(§3-2) |
| 대기자가 활성 팀원(`team_mem_rel`) | 탈퇴자가 자리를 먹으면 줄이 영구히 막힌다 |
| 대기자가 아직 참석자가 아님 | 관리자가 우겨넣은 사람이면 대기 행만 닫고 **자리는 안 쓴 채** 다음 사람을 본다 |

승급 = `gthr_attd_rel` INSERT + 그 사람의 `gthr_wait_rel` 행을 `promoted`로. 이 INSERT가
곧 "확정"의 정의이므로 포인트 트리거·집계가 여기서 비로소 돈다(`approve_gthr_application`과
같은 자리, 같은 뜻).

### 3-1. 왜 취소 RPC **안에서** 부르는가

서버 액션에서 "취소 RPC → 그다음 승급 RPC"로 나눠 부르면 두 가지가 깨진다:

1. 두 명이 동시에 취소하면 둘 다 같은 대기 1번을 올리려 한다.
2. 두 호출 사이에서 죽으면 **자리가 빈 채로 영영 남는다.** 다음 취소가 나기 전까지
   아무도 안 올라간다.

그래서 `cancel_gthr_attendance`가 DELETE · 이력 INSERT · 승급을 **한 트랜잭션**으로 묶는다.
이 함수의 반환형이 `void` → `uuid[]`로 바뀌므로 `CREATE OR REPLACE`가 아니라 **`DROP`
후 재생성**이 필요하다.

### 3-2. 끝난 모임 게이트는 `isPastLockedFor`의 복제가 아니다

참석 잠금 판정 정본은 `lib/past-event.ts`의 `isPastLockedFor`(KST 날짜 기준, 관리자 예외)이고,
그걸 SQL에 한 벌 더 만들면 진실이 둘이 된다. 여기 쓰는 `COALESCE(end_at, stt_at) > now()`는
그 규칙을 흉내 낸 게 아니라 **더 보수적인 독립 게이트**다:

> 이미 끝난(또는 시작한) 모임에 시스템이 사람을 자동으로 밀어 넣지 않는다.

관리자가 지난 모임의 참석자를 정리할 때 대기자가 딸려 올라가면, 실제로 뛰지 않은 사람에게
포인트가 붙는다. 사람이 판단해 넣는 것(`admin_add_gthr_attendance`)과 시스템이 자동으로
넣는 것은 다른 일이다.

## 4. 등록 — `join_gthr_or_wait` (기존 TOCTOU 동시 수정)

`lib/gathering/join-gathering.ts`의 `joinGatheringWithCapCheck`는 정원 검사가
`COUNT → upsert` **2단계라 원자적이지 않다**(코드 주석도 인정하고 있다). 만석 직전에 두 명이
동시에 누르면 21명이 된다.

지금까지는 넘어갈 수 있는 결함이었지만 **대기열이 붙으면 성격이 달라진다** — 사고로 넘친
1명 때문에 대기열이 이유 없이 얼어붙고(§5-1의 규칙이 그대로 적용된다), 그게 "운영진이 의도해
우겨넣은 초과"와 구분되지 않는다. 그래서 이번에 같이 고친다.

```
join_gthr_or_wait(p_gthr_id, p_mem_id, p_team_id, p_is_admin)
  RETURNS text  -- 'joined' | 'waiting' | 'not_found' | 'past_locked'
```

모임 행을 `FOR UPDATE`로 잠그고 → 자리가 있으면 `gthr_attd_rel` INSERT(`'joined'`),
없으면 `gthr_wait_rel` upsert(`'waiting'`). 정원이 `NULL`이면 항상 `'joined'`.

### 4-1. RLS 방어를 잃지 않기

지금은 참석 INSERT를 **사용자의 RLS 클라이언트**로 보내 "본인만 INSERT" 정책을 DB 레벨에서
지키고 있다(`writeClient` 인자). RPC로 옮기면 그 방어가 사라지므로,
`approve_gthr_application`과 같은 방식으로 막는다:

- `REVOKE ALL ... FROM public, authenticated, anon` / `GRANT EXECUTE ... TO service_role`
  — SECURITY DEFINER만으로는 `/rpc/` 직접 호출 IDOR가 열린다(사고 #425 전례).
- **`p_mem_id`에는 서버 액션이 세션에서 꺼낸 `member.id`만 넘긴다.** 클라이언트 입력이
  이 인자에 닿는 경로를 만들지 않는다.
- `p_team_id`는 `getRequestTeamContext()`에서 오고, 모임 조회에 `team_id` 필터가 들어가
  다른 팀 `gthr_id` 조작을 막는다(기존과 동일).

### 4-2. 참여조건은 이 RPC 밖에 남는다

판정 정본은 `lib/gathering/join-condition.ts` 하나다(승인제 설계 §4). RPC는 앱 서버가
그 게이트를 통과시킨 뒤에만 호출된다. **참여조건 미달이면 대기열 진입도 못 한다.**

## 5. 승급이 끼어드는 자리는 셋

| 자리 | 처리 |
|---|---|
| **참석 취소**(본인/관리자) | `cancel_gthr_attendance` 안에서 `promote_gthr_waitlist` 호출(§3-1) |
| **정원 증가** | `updateGathering`이 `max_prt_cnt`가 **늘어난 경우에만** 호출 |
| **관리자 대리 추가** | 승급이 아니라 *정리* — `admin_add_gthr_attendance`가 그 사람의 `waiting` 행을 `promoted`로 닫는다 |

승인제 취소 경로(`cancel_gthr_application`)는 **건드리지 않는다** — 비승인제 전용이라
승급할 대상이 없다.

### 5-1. 22명 케이스 (이 기능의 발단)

정원 20, 운영진이 2명을 우겨넣어 참석 22명, 대기 3명인 상태:

| 사건 | 참석 수 | 승급 |
|---|---|---|
| 1명 취소 | 21 | 없음 (`21 >= 20`) |
| 또 1명 취소 | 20 | 없음 (`20 >= 20`) |
| 또 1명 취소 | 19 | **대기 1번 승급** → 20 |

규칙은 `COUNT < max` 하나뿐이고, 초과분을 되돌리려고 **이미 확정된 참석자를 시스템이 내리는
코드는 어디에도 없다.** 운영진이 의도해 넣은 사람이다.

| # | 상황 | 동작 | 근거 |
|---|---|---|---|

| 2 | 참 → 불참 → (만석) → 다시 참 | 대기열 **맨 뒤** | §2-1 |
| 3 | 대기 중 "대기 신청" 연타 | 멱등, 순번 유지 | §2-1 |

| 5 | `max_prt_cnt = null` | 대기열 없음, 항상 즉시 참석 | §3 |
| 6 | 정원 20 → 25 | 대기 5명 즉시 승급, 각자 알림 | §5 |
| 7 | 참석 22명에서 정원 20 → 15 | 아무도 안 내려감, 대기열 동결 | §5-1 |

| 10 | 승급 대상이 이미 참석자 | 대기 행만 닫고 **자리는 안 쓴 채** 다음 사람 | §3 — 아니면 빈자리가 증발한다 |
| 11 | 모임 시작 이후 취소 | 취소는 되나 승급 없음 | §3-2 |

| 13 | 만석 직전 두 명이 동시에 참석 | 1명 참석, 1명 대기 | §4 (현재는 둘 다 참석해 21명) |
| 14 | 참여조건 미달자 | 대기열 진입도 차단 | §4-2 |
| 15 | 대기 중 조건이 깨짐 | 그대로 승급 | 아래 §6-1 |
| 16 | 승인제 모임 | 대기열 없음 | §1 |
| 17 | 승급 직후 본인이 취소 | 정상 취소 → 다음 사람 승급 | 임박 취소 사유 필수는 그대로 적용(확정 참석자와 같은 규칙) |
| 18 | 모임 soft delete | 대기열도 조회에서 사라짐 | 별도 정리 없음 |
| 19 | 온보딩 뉴비가 만석 모임 선택 | 대기로 등록 | §7-2 |

### 6-1. 승급 시점에 참여조건을 재검증하지 않는다 (의도적 타협)

조건이 "최근 N개월 M회"라 줄 서 있는 동안 자격이 사라질 수 있다. 그걸 막으려면 판정
로직(`join-condition.ts`)을 SQL에 복제해야 하는데, **드문 경우 하나를 막자고 판정 정본을
둘로 쪼개는 값이 더 비싸다.** 조건은 등록 시점에만 본다.

## 8. 알림 — `gthr_promo` 한 종류만

**승급 알림만 넣는다.** "누가 대기 걸었다"를 개설자에게 보내는 건 뺐다 — 화면에 대기 명단이
뜨는 걸로 충분하고, 정기런처럼 사람이 몰리는 모임에서 개설자 알림함이 도배된다.

발송은 취소한 사람의 `after()` 안에서(응답 밖). 푸시는 `insertNoti`가 자동으로 붙인다.

**수신거부 가능한 일반 타입으로 둔다.** 끄면 자리가 나도 모르게 되지만, 이 알림만 강제 발송
예외를 만드는 것보다 규칙이 하나인 편이 낫다.

승급자에게는 칭호 엔진(`trigger: "gathering_attend"`)도 같이 돌린다 — 안 돌리면 정확히
정원 번째로 올라간 사람이 `막차`를 못 받는다. 승급 RPC가 `mem_id`를 주므로 `team_mem_id`는
한 번 조회한다.

> ⚠️ 마이그레이션 주석의 경고 그대로: 알림 타입을 CHECK에만 추가하고 **딥링크 맵을
> 빠뜨리면 알림을 눌러도 아무 데도 안 간다.**

## 9. UI — 버튼이 3상태

토글 액션 반환형이 바뀐다:

```ts
{ attending: boolean; monthlyAttendCnt?: number }
→ { state: "attending" | "waiting" | "none"; waitRank?: number; waitCount?: number; monthlyAttendCnt?: number }
```

| 내 상태 | 버튼 | 보조 표시 |
|---|---|---|
| 미참석 + 자리 있음 | 참석하기 | |
| 참석 중 | 참석 취소 | |
| 미참석 + 만석 | **대기 신청** | 현재 N명 대기 중 |
| 대기 중 | **대기 취소** | 대기 N번 |

토글 한 번으로 순환한다(`none → attending|waiting → none`).

**낙관적 업데이트는 "대기 중"까지만** — 순번은 서버가 정하므로 낙관적으로 못 찍는다.
숫자를 미리 그렸다가 서버 값과 어긋나면 "3번이었는데 5번이 됐다"로 보인다.

목록 순서는 **참석자 → 대기자(순번순) → 취소자**. 취소자 표시(`GatheringCanceledAttendees`)는
그대로 맨 아래에 남는다.

관리자 화면엔 대기 명단 옆에 **바로 추가** 버튼 — 기존 `addGatheringAttendance`를 그대로
쓰고 정원을 안 보는 것도 그대로다. 이게 "필요한 사람 우겨넣기"의 정식 경로다.
**대기 순서를 손으로 바꾸는 기능은 만들지 않는다** — 우겨넣기가 같은 일을 더 직접적으로 한다.

## 11. 하지 않는 것 (YAGNI)

- **승급 승낙 시한** — 자동 승급 후 N시간 안에 확인 안 하면 다음 사람에게 넘기기.
  크론/지연작업이 한 겹 붙는데, 모임 하루 전 취소 같은 경우엔 시한 자체가 무의미하다.
- **대기 인원 상한** — 무제한. 줄이 길어서 생기는 문제가 아직 없다.
- **대기 순서 수동 조작** — §9.
- **대기 등록 시 개설자 알림** — §8.
- **대기 취소 이력** — 볼 화면이 없다. 확정 참석의 취소 이력(`gthr_attd_hist`)은 그대로 남는다.
