# 모임 대기열 — 임박 구간과 대기 명단 노출 — 설계

- 날짜: 2026-09-11
- 대상: 비승인제 모임 대기열의 **시작 2시간 전 이후** 동작 + 대기 명단이 안 보이던 문제
- 선행 설계: [`2026-09-10-모임-대기열-design.md`](./2026-09-10-모임-대기열-design.md)

## 0. 왜

대기열을 붙인 지 하루 만에 두 가지가 드러났다.

**① 대기 명단을 아무도 못 본다.** 명단은 모임 상세 페이지(`/gatherings/{id}`)와 관리자 화면에만
붙였는데, **상세 페이지로 가는 길이 사실상 없다.** 코드 전체에서 그 경로로 보내는 건 모임 생성
직후 `router.push` 하나뿐이고(`gathering-form.tsx`), 일정탭·홈 캘린더·알림 딥링크·공유 링크가
전부 다이얼로그(`gathering-detail-dialog.tsx`)로 간다. 대기를 걸어도 내가 몇 번인지 누른 직후
토스트로만 보고, 다이얼로그를 다시 열면 순번이 사라진다. **선착순이라는 대기열의 유일한 약속을
확인할 방법이 없다.**

**② 모임 직전에 자동 확정되면 빠져나올 길이 험하다.** 시작 3시간 전에 누가 취소하면 대기 1번이
가만히 있었는데 참석자가 된다. 못 가면 본인이 취소해야 하는데 그 시점은 이미 임박 구간이라
취소 사유가 강제되고 취소자 명단에 회색으로 박힌다.

②를 파고들다 더 큰 문제를 찾았다 — **모임이 코앞인데 줄 순서를 지키는 게 맞나.** 시작 1시간
전이면 "가장 오래 기다린 사람"보다 **지금 올 수 있는 사람**이 중요하다. 대기 1번이 알림을 못 보면
자리는 빈 채로 모임이 시작된다.

## 1. 결정 사항 (오너 확인 완료)

| 질문 | 결정 |
|---|---|
| 임박 구간에 승급 방식을 바꾸나 | **시작 2시간 전까지는 지금 그대로 자동 승급.** 그 뒤로는 대기열을 무시하고 선착순 |
| 우선권을 시간에 따라 넓히는 안 | **폐기.** 검토했으나 복잡도 대비 값이 안 나온다(§1-1) |
| 자동 승급자가 못 가서 취소하면 | **일반 참석자와 같은 규칙.** 사유 필수·취소자 명단 그대로 (§1-2) |
| 대기 신청 시 안내 | **확인 다이얼로그로 누르기 전에.** 자동 확정된다는 사실 + 2시간 규칙 |
| 대기 명단 | **일정탭 다이얼로그에도 붙인다.** RLS로 세션 클라이언트 직접 조회 |

### 1-1. 폐기한 안 — "30분마다 우선권을 넓히기"

한때 이렇게 잡았다: 임박 구간엔 승급하지 않고 대기 상위 k명에게만 버튼을 열되, 30분마다 한
명씩 아래로 넓힌다(`열림 = 빈자리 k + floor(경과/30분)`). 자리 홀드도 만료 배치도 없이 계산만으로
돌아가고, 무응답으로 자리가 묶이는 것도 막는다.

**버린 이유는 "내 차례가 언제인지 알 수 없다"** 였다. 알림에 개방 시각을 박으면 지킬 수 없는
약속이 된다 — 그 시각엔 이미 자리가 찼을 수도, 반대로 두 명이 더 취소해 더 일찍 열릴 수도 있다.
알림은 한 번 나가면 고쳐지지 않는다. 그렇다고 시각을 빼면 대기자는 **자리가 났다는 것만 알고
자기가 언제 누를 수 있는지는 모르는 채** 앱을 들여다봐야 한다.

여러 명이 동시에 취소할 때 기준 시각을 잘못 잡으면 **열렸던 사람이 다시 닫히는** 문제도 있었다
(마지막 취소를 기준으로 삼으면 자리가 늘었는데 열림 인원이 줄어든다). "가장 오래된 빈자리"를
기준으로 삼아 풀리긴 했지만, 그 정도 장치가 필요하다는 것 자체가 신호다.

**지금 안은 "언제 내 차례인가"라는 질문을 없앤다** — 차례가 오면 자동으로 확정되고 알림이 온다.

### 1-2. 승급자 취소에 면책을 두지 않는 이유

임박 구간 자동 승급자가 취소할 때 사유를 면제하고 취소자 명단에서 빼는 안을 검토했다. 채택하지
않았다 — **대기 신청 시 "자리가 나면 자동으로 확정된다"를 미리 확인받기 때문이다.** 그걸 알고
줄을 섰으면 못 갈 것 같을 때 **대기를 먼저 빼는 게** 본인 몫이다. 예외를 만들면 "대기로 들어온
취소"와 "직접 신청한 취소"를 화면마다 갈라야 하고, 운영진이 인원을 세는 입장에선 어느 쪽이든
똑같이 한 자리가 빈 것이다.

## 2. 시간 경계 — 하나의 축, 두 개의 눈금

```
시작 5시간 전 ─────────── 시작 2시간 전 ─────────── 시작
    │                          │
    │                          └─ GATHERING_WAITLIST_OPEN_HOURS = 2 (신규)
    └─ GATHERING_CANCEL_IMMINENT_HOURS = 5 (기존, 취소 사유 필수 경계)
```

두 상수는 **성격이 다르다**(취소 사유 vs 대기열 개방). 그래서 값을 공유하지 않되,
`lib/gathering/cancel-imminent.ts` 옆 같은 층에 나란히 둔다 — "임박"의 정의가 흩어지면 한쪽만
바뀐다.

| 구간 | 취소가 발생하면 | 대기 신청은 |
|---|---|---|
| 시작 2시간 전까지 | **순번대로 즉시 자동 확정** + `gthr_promo` 알림 (현행 그대로) | 받는다. 순번대로 자동 확정됨 |
| 시작 2시간 전부터 | 승급 없음. **대기자 전원에게** `gthr_seat` 알림 1발 | 받는다. **알림 구독**의 뜻이 된다(§4-2) |

**승급 연쇄는 이미 동작한다.** 1번이 승급 후 취소하면 `cancel_gthr_attendance` RPC가 같은
트랜잭션에서 `promote_gthr_waitlist`를 다시 부르고 2번이 올라간다. 새로 만들 것이 없다.

## 3. 2시간 이후에도 알림은 보낸다 — 안 보내면 지금보다 나빠진다

"그냥 열린다"만으로 두면 **자리가 났다는 걸 알릴 수단이 사라진다.** 시작 1시간 전 취소 →
자동 승급 없음 → 알림 없음 → 대기자 전원이 모른 채 자리가 빈 채로 모임이 시작된다. 현행
(자동 승급 + 알림)보다 후퇴다.

그래서 선착순 구간에 취소로 **실제 빈자리**가 생기면 대기자 전원에게 알림을 한 발 보낸다.

**보낼지는 `cancel_gthr_attendance`가 트랜잭션 안에서 정한다**(반환의 `notify_open_seat`,
PR #532 리뷰로 변경). 처음엔 앱이 "시작 2시간 전인가"만 보고 정했는데 두 가지가 틀렸다.

- **실제 빈자리를 안 봤다.** 운영진이 정원을 넘겨 넣은 모임(22/20)에서 한 명이 취소하면
  21/20으로 여전히 만석인데 알림이 나갔고, 1회 제한 때문에 **정작 19명이 됐을 때의 진짜 알림이
  막혔다.** #530을 만든 계기였던 바로 그 상황이다.
- **판정 시각이 갈렸다.** 승급 게이트는 DB의 `now()`, 알림 판정은 앱 서버의 시계라 2시간 경계
  직전에 승급이 일어난 뒤 알림까지 나갈 수 있었다. Postgres의 `now()`는 트랜잭션 시작 시각으로
  고정이라, 같은 트랜잭션 안에서 판정하면 두 값이 어긋날 수 없다.

dev 실측(롤백 트랜잭션): 정원 2에 3명 → 1명 취소 `notify_open_seat=false` / 1명 더 취소
`true`(승급 없음) / 선착순 구간 전으로 옮겨 취소 → 대기자 승급 + `false`.

> **'수요 한강런' 빈 자리가 났어요**
> 지금은 순번 없이 먼저 누르는 분이 참석하실 수 있어요.

**시각을 약속하지 않는다**(§1-1의 교훈). "지금 상태"만 말하고, 자리가 찼는지는 화면이 실시간으로
말한다 — 화면은 틀리면 즉시 갱신되므로 거짓말을 할 수 없다.

**한 모임당 1회로 제한한다.** 정기런은 당일 취소가 서너 건씩 나는데 매번 보내면 알림함이
도배된다. 이미 "빈 자리가 났어요"를 받은 사람에게 **자리가 하나 더 났다는 건 새 소식이 아니다**
(유리해졌을 뿐 할 일이 같다). 판정은 "이 모임에 대해 그 사람에게 `gthr_seat` 알림이 이미
나갔는가" — `noti_mst`의 `ref_id` + `noti_type_enm` 조회 한 번이다.

## 4. UI

### 4-1. 대기 명단 — 다이얼로그에도 붙인다

**RPC를 건드리지 않는다.** `get_gathering_detail`이 `anon` 실행 허용이라 명단을 실을 수 없었던
건데, `gthr_wait_rel`에는 이미 `authenticated` + 팀 멤버 한정 SELECT RLS가 걸려 있다. 다이얼로그가
**세션 클라이언트(`lib/supabase/client.ts`)로 테이블을 직접 조회**하면 RLS가 알아서 막는다 —
비로그인 0행, 남의 팀 0행. 마이그레이션도 RPC 수정도 없다.

`GatheringWaitlist` 컴포넌트는 이미 `components/schedule/`에 있어 그대로 쓴다(상세 페이지와
다이얼로그가 **한 벌을 공유**해야 순번 표기가 한쪽만 바뀌는 사고가 안 난다).

같이 고치는 것: 다이얼로그가 **내 대기 상태를 초기값으로 못 받아** 이미 대기 중인 사람에게도
버튼이 "참석하기"로 보이던 문제(선행 설계 §9-1의 알려진 제약). 위 조회로 명단을 받으면 내
순번도 같은 데이터에서 나온다.

### 4-2. 대기 신청 확인 다이얼로그

대기 버튼을 누르면 **바로 등록하지 않고** 한 번 더 확인받는다. 자동으로 참석자가 되는 건
되돌리기 번거로운 일이라(취소 사유·취소자 명단) **누르기 전에** 알려야 한다. 사후 토스트로는 늦다.

구간에 따라 문구가 갈린다.

**시작 2시간 전까지:**

> **대기 신청할까요?**
>
> · 참석자가 취소하면 순번대로 자동 참석됩니다.
> · **참석이 어려우면 미리 대기를 취소해주세요.**
> · 시작 2시간 전부터는 대기 순번이 없고 선착순으로 바뀝니다.
> · 이후 빈 자리가 나면 알림을 보내드리니 직접 참석해주세요.
>
> `[ 취소 ]` `[ 대기 신청 ]`

**사실 → 경고 순으로 적는다.** 경고를 맨 앞에 두면 자동 참석된다는 것을 모르는 상태에서
읽게 되어 왜 취소해야 하는지가 안 잡힌다.

**취소 페널티(사유 필수·취소 이력)는 여기 적지 않는다.** 대기를 신청하는 자리에서 취소했을
때의 불이익까지 설명하면 겁주는 문서가 된다. 필요한 건 "안 갈 거면 네가 빼야 한다" 하나다.

**"2시간 뒤 대기가 취소된다"고 쓰지 않는다.** 사실도 아니고(대기 행을 지우지 않는다) 무엇보다
**박탈로 읽힌다** — 실제로는 여전히 참석할 수 있고 순번만 무의미해지는, 오히려 기회가 열리는
쪽이다.

경고를 **다이얼로그에만 두지 않는다.** 이건 신청하는 순간이 아니라 **줄 서 있는 내내**
유효한 약속인데, 확인 다이얼로그는 한 번 보고 지나간다. 며칠 뒤 자리가 날 때쯤이면
읽은 기억이 없다. 그래서 대기 중에는 버튼 아래 보조 문구가 같은 말을 계속 들고 있는다.

```
[ 대기 취소 ]
  대기 3번 · 자리 나면 자동 확정
```

`waitHintText`가 지금 `대기 3번`만 내는 자리다(`lib/gathering/waitlist.ts`). 여기에 한 마디를
붙이는 것으로 **"취소는 내가 해야 한다"가 늘 눈에 남는다.**

**시작 2시간 전부터 — 이건 대기가 아니라 알림 요청이다.**

이 구간엔 줄이 없다. 순번도 자동 확정도 없고 받는 것은 알림 하나뿐인데, 버튼이 `대기 신청`으로
남아 있으면 **버튼이 지키지 못할 약속을 한다** — "대기"라는 말이 순번과 자동 확정을 기대하게
만든다. 그래서 어휘를 통째로 바꾼다.

| | 시작 2시간 전까지 | 시작 2시간 전부터 |
|---|---|---|
| 미신청 | `대기 신청` | **`빈 자리 알림 요청`** |
| 신청 후 | `대기 취소` / `대기 3번 · 자리 나면 자동 확정` | **`알림 요청 취소`** / `빈 자리가 나면 알려드려요` |

> **빈 자리 알림을 요청할까요?**
>
> · 지금은 순번 없이 선착순입니다.
> · 빈 자리가 나면 알림을 보내드립니다.
>
> `[ 취소 ]` `[ 알림 요청 ]`

버튼이 이미 무슨 일이 일어나는지 말하므로 설명이 두 줄로 끝난다. 알림 문구(§3)도 같은 어휘를
쓴다 — **"빈 자리가 났어요"**. 한쪽만 "대기", 다른 쪽만 "빈 자리"로 부르면 같은 것을 두 이름으로
부르게 된다.

> ⚠️ **DB·내부 식별자는 그대로 `gthr_wait_rel` · `waiting` 이다.** 바꾸는 것은 화면에 보이는
> 말뿐이다. 같은 행이 시각에 따라 "대기"로도 "알림 요청"으로도 불리는 것이지, 두 종류의
> 데이터가 있는 게 아니다.

### 4-3. 버튼

2시간을 지나면 대기 중인 사람의 버튼이 "대기 취소" → **"참석하기"** 로 바뀐다(자리가 있을 때).
대기 행을 DB에서 지우지 않는다 — 그러려면 그 시각에 돌 배치가 필요하다. **계산과 화면이
대기열을 없는 것처럼 취급**할 뿐이고, 실제로 참석을 누르면 `join_gthr_or_wait`가 남은 대기 행을
`promoted`로 닫는다(기존 동작).

| `<ts>_noti_gthr_seat_type.sql` | 알림 타입 `gthr_seat` 추가 (`noti_mst` CHECK) |

`join_gthr_or_wait`는 **고치지 않는다.** 2시간 이후에도 만석이면 대기 등록을 받는 게 맞고
(§4-2), 자리가 있으면 누구나 들어가는 현행 동작이 곧 "그냥 열림"이다.

> ⚠️ **처음 설계는 틀렸다(PR #532 리뷰로 변경).** 원래는 `promote_gthr_waitlist`의 빈 배열이
> "올릴 사람이 없었다"와 "임박이라 안 올렸다"를 구분하지 못하니 **앱이 시작 시각으로 구간을
> 판정**하게 했다. 그러자 실제 빈자리를 보지 않아 정원 초과 모임에서 가짜 알림이 나갔다(§3).
>
> 지금은 `promote_gthr_waitlist`는 `uuid[]` 그대로 두고, 그걸 부르는 **`cancel_gthr_attendance`의
> 반환형을 `jsonb {promoted, notify_open_seat}`로 바꿨다**
> (`20260914100000_gthr_cancel_result_jsonb.sql`). 호출부 둘(본인 취소·운영진 제거)은
> `lib/gathering/cancel-result.ts`의 `parseCancelResult` 하나로 읽는다 — 조건을 각자 조립하면
> 한쪽만 틀린다. 파서는 옛 `uuid[]` 응답도 받으므로 **배포 순서가 뒤집혀도** 승급 알림은 끊기지 않는다.

추가된 마이그레이션(PR #532 리뷰):

| 파일 | 내용 |
|---|---|
| `20260911110000_noti_gthr_seat_type.sql` | `gthr_seat` 추가 **+ `batch_failed` 복원**(`20260825140000`에서 유실 — `KNOWLEDGE.md` 참고). `VALIDATE`는 뺐다 |
| `20260911110100_noti_type_check_validate.sql` | `VALIDATE`만 별도 트랜잭션으로 |
| `20260914100000_gthr_cancel_result_jsonb.sql` | `cancel_gthr_attendance` 반환형 `uuid[]` → `jsonb` |

**선착순 구간의 대기자는 직접 참석한다 — 토글에 의도를 넘긴다.** 처음 구현은 버튼 라벨만
"참석하기"로 바꾸고 클릭은 여전히 대기 취소로 보냈다(클라이언트는 `state === "waiting"` 분기,
서버는 대기 행이 있으면 무조건 대기 취소). 토글만으로는 "대기 취소"와 "참석"을 구분할 수 없어
`toggleGatheringAttendance(gthrId, reason, "join")`으로 의도를 받는다. **새 RPC는 만들지 않았다** —
`join_gthr_or_wait`가 이미 모임 행 잠금 → 빈자리 확인 → 참석 INSERT → 대기 행 `promoted` 종료를
한 트랜잭션으로 한다. 선착순 구간 전에 `"join"`이 오면 거절한다(대기자가 앞 순번을 제치게 된다).
같은 이유로 버튼의 만석 판정도 `state === "none"`이 아니라 **실제 정원**을 본다.

## 9. 대기 로직 점검 반영 (PR #532, 2026-09-14)

코드리뷰는 **취소 경로**만 봤다. 자리 수를 바꾸는 모든 경로(`gthr_attd_rel` 삽입·삭제, `max_prt_cnt`
변경, `aprv_req_yn` 전환, MCP 운영 도구, SQL 함수)를 추적해 네 가지를 더 고쳤다.

| 경로 | 문제 | 처리 |
|---|---|---|
| 정원 증가 (`updateGathering`) | `promote_gthr_waitlist`를 직접 불러, 선착순 구간이면 승급도 **빈 자리 알림도 없었다** | `promote_gthr_waitlist_notice` RPC로 교체 — 취소 RPC와 같은 `{promoted, notify_open_seat}`. 승급은 응답 전에 동기로 끝내고 그다음 캐시를 턴다(`updateTag`는 서버 액션 본문 전용이라 `after()` 안으로 못 옮긴다) |
| 승인제 전환 | 대기 행이 `waiting`으로 남아 **갇혔다** — 토글이 승인제 모임을 막고, promote도 안 돌고, 명단은 계속 화면에 뜬다 | 승인제를 켜면 대기 행을 **삭제**. 알림은 보내지 않는다(운영진이 단톡방으로 안내 — 오너 결정). 수정이 실패했을 때 대기자만 사라지지 않도록 플래그를 켠 **뒤에** 지운다 |
| 운영진 제거 · 정원 증가 | 승급자 칭호(`막차`) 평가가 본인 취소 경로에만 있었다 | 뒷처리를 `lib/gathering/promotion-followup.ts`의 `runPromotionFollowups` 하나로 모아 세 경로가 공유 |
| 운영진 추가 · 제거 | 캐시 무효화가 없어 참석자 수가 최대 1시간 낡았다 | `updateTag(HOME_CALENDAR_CACHE_TAG)` + 상세 경로 `revalidatePath` |

빈 자리 알림 판정은 SQL 헬퍼 `gthr_open_seat_notice_yn(gthr_id, team_id)` 하나로 모았다
(`20260914110000_gthr_promote_notice_rpc.sql`). 두 RPC가 조건을 각자 적으면 한쪽만 바뀐다. 팀을 함께
받는 이유는 다른 팀 모임 id로 그 팀 대기자에게 알림을 보내게 만들 수 없도록 하기 위해서다.

dev 실측(롤백 트랜잭션): 선착순 구간에서 정원 2→3 → 승급 없음 · 알림 `true` / 다른 팀 id로 판정 →
`NULL` / 선착순 구간 전으로 옮겨 정원 3→4 → 대기 2명 순번대로 승급 · 알림 `false`.

MCP 운영 도구(`lib/mcp`)는 모임 생성·조회만 있어 대기열에 영향이 없다.

### 9-1. 알림이 가는 경우

| 사건 | 당사자 | 승급된 대기자 | 나머지 대기자 |
|---|---|---|---|
| 본인 참석 취소 | 없음(모임장에게 `gthr_cncl`) | `gthr_promo` | 선착순 구간 + 실제 빈자리면 `gthr_seat` |
| 운영진이 참석자 제거 | 제거된 사람에게 **없음** | `gthr_promo` | 위와 같음 |
| 정원 증가 | 없음(참석자에게는 모임 수정 알림 `gthr_upd`) | `gthr_promo` | 위와 같음 |
| 운영진 직접 추가(대기자 `바로 추가` 포함) | 추가된 사람에게 **없음** | — | — |
| 승인제 전환으로 대기자 삭제 | **없음**(오너 결정) | — | — |

### 9-2. 고치지 않은 것

- **대기 순번에 비활성·탈퇴 대기자가 포함된다.** promote는 그들을 건너뛰지만 순번 표시는 센다. 대기 중에
  상태가 바뀌는 드문 경우라, 명단을 읽는 네 곳(액션 · 상세 페이지 · 다이얼로그 · 관리자)을 모두 바꾸는
  위험 대비 가치가 낮다.
- 빈 자리 알림 1회 제한의 경합 — 같은 모임에서 두 취소가 ms 차이로 겹치면 중복 1건. 부분 유니크 인덱스는
  `insertNotiMany`의 배치 INSERT를 통째로 실패시켜 역효과라 감수한다(`seat-notice.ts` 주석).
- 1회 제한 때문에 같은 모임에서 두 번째로 진짜 빈자리가 나도 이미 받은 사람에게는 다시 가지 않는다(도배 방지와 맞바꿈).
- 다이얼로그를 연 채로 2시간 경계를 넘기면 다시 렌더될 때까지 이전 구간 문구가 남는다.
