# 배치 자동화 — 수동 실행을 크론으로

> 상태: **제안(미구현)**. 신규 칭호 25종(`2026-07-30-신규-칭호-후보-모임-깅스타그램.md`)이
> **일 배치 + 월 배치**를 요구하면서 배치 자동화가 선행 조건이 됐다. 그런데 회비 감면·마일리지런
> 배치도 **지금은 단장이 매월 1일 손으로 돌리고 있어**, 이참에 같이 자동으로 돌린다.
> 브랜치는 따로 파지 않고 칭호 작업과 같은 브랜치에서 간다.

---

## 1. 이미 깔려 있는 것 — 새로 만들 게 거의 없다

`20260530110000_batch_management.sql`이 **레지스트리 + 이력**을 이미 만들어 뒀다.

| 조각 | 내용 |
|---|---|
| `batch_job_mst` | `job_cd` · `cron_expr` · `param_schema_json` · `use_yn` |
| `batch_run_hist` | `trig_type CHECK ('manual', **'auto'**)` — **auto를 처음부터 예상해 뒀다** |
| `runBatch()` (`app/actions/admin/run-batch.ts`) | `job_cd` → 핸들러 디스패치 + 이력 INSERT/UPDATE + 성공·실패·`duration_ms` |
| `/admin/system/batch` | `param_schema_json`으로 폼을 그리고 손으로 실행 |

**prd 실측(2026-08-14)**

| job_cd | cron_expr | 실행 | 자동 실행 | 최근 |
|---|---|---|---|---|
| `DUES_EXEMPTION_BATCH` | `0 15 1 * *` | 1회 | **0회** | 2026-08-01 |
| `MILEAGE_TITLE_BATCH` | `0 15 1 * *` | 5회 | **0회** | 2026-08-01 |

`cron_expr`은 **둘 다 이미 채워져 있는데 아무도 읽지 않는다**(컬럼 주석이 "자동화 예정용"이다).
즉 **없는 건 크론 진입점 하나뿐이다.**

## 2. 설계 — 크론은 하나, 배치는 N개

```
Vercel Cron  →  /api/cron/batch  →  batch_job_mst 조회
                                 →  "오늘 돌 차례"인 job만 executeBatch()
                                 →  batch_run_hist (trig_type = 'auto')
```

**크론을 배치마다 만들지 않는다.** 레지스트리가 이미 있으므로 진입점 하나가 목록을 읽어
디스패치하면 된다. 배치가 늘어도 크론은 그대로다.

> ⚠️ **Vercel 크론 상한이 실제 제약이다.** Hobby는 **2개**가 끝인데 `keep-alive`·`newbie-nudge`로
> 이미 다 썼다. 배치마다 크론을 파는 설계였다면 여기서 막혔다.

**`keep-alive`를 걷어내고 그 자리를 쓴다.** 그 크론은 Supabase 무료 플랜이 7일 무요청이면
프로젝트를 재우는 걸 막으려고 `mem_mst`를 하루 한 번 긁던 것인데, **모임 관리가 붙으면서 실사용
요청이 매일 들어와 잴 이유가 없어졌다.**

> 게다가 **배치 크론이 그 역할을 그대로 흡수한다** — 매일 `batch_job_mst`를 조회하므로 그 자체가
> DB 요청이다. 슬립 방지를 위해 따로 쿼리를 날리는 크론을 유지할 이유가 없다. 대체가 아니라
> 흡수라서, 지우고 나서 "혹시 잠들까" 걱정할 것도 없다.
>
> `newbie-nudge`는 **건드리지 않는다.** 성격이 다르고(개인별 넛지 발송) 이미 잘 돌고 있어,
> 배치 디스패처와 한 라우트에 묶으면 한쪽 실패가 다른 쪽을 끌고 내려간다.

### 2.1 등록할 job

| job_cd | 주기 | 내용 | 지금 |
|---|---|---|---|
| `TITLE_GATHERING_DAILY` | 매일 | 참석 계열 칭호(끝난 지 3일 지난 모임) | 신규 |
| `TITLE_MONTHLY` | 월 마감 | `투머치토커` · `프로참석러`(월이 끝나야 확정) + `인간화로` · `하수야~` · `고수님..`(전원 재평가가 필요) | 신규 |
| `DUES_EXEMPTION_BATCH` | 월 마감 | 출석 회비 감면 | **수동 → 자동** |
| `MILEAGE_TITLE_BATCH` | 월 마감 | 마일리지런 칭호 | **수동 → 자동** |

칭호 배치를 job으로 등록하면 **관리자 화면에서 손으로도 돌릴 수 있게 되는 게 덤**이다
(재계산이 필요할 때 배포 없이 대응된다).

## 3. 손봐야 할 것

### 3.1 `runBatch`가 관리자 세션에 묶여 있다

지금은 `withAdmin(...)` 안에 이력 기록과 디스패치가 통째로 들어 있어 **크론이 부를 수 없다.**

```
executeBatch(jobId, params, trigType, actorId)   ← 이력·디스패치·성공/실패 (공용)
  ├─ runBatch()        = withAdmin + executeBatch(..., 'manual', member.id)
  └─ /api/cron/batch   =            executeBatch(..., 'auto',   null)
```

> ⚠️ **이력 기록 코드를 두 벌로 만들지 않는다.** 크론용을 따로 쓰면 `duration_ms`나 실패 처리 중
> 한쪽만 고쳐져 어긋나고, 그때부터 관리자 화면의 "최근 실행"이 자동 실행을 못 보여 준다.

**핸들러 자체도 관리자 세션에 묶여 있다.** 디스패처만 푸는 걸로는 부족하다:

| 의존 | 어디 | 크론에서 |
|---|---|---|
| `withAdminOrThrow` | `batchDuesExemption` · `batchMileageTitles` **내부** | 로그인 세션이 없어 **던진다** |
| `getRequestTeamContext()` | `batchDuesExemption` 내부 | `headers()`의 Host로 팀을 해석한다 |
| `member.id` | 감면 행의 `aprv_by_mem_id` | 자동 실행엔 사람이 없다 |

- **`withAdminOrThrow`를 핸들러에서 걷어낸다.** 권한 검사는 **호출부**(관리자 액션)의 몫이지
  배치 로직의 몫이 아니다. 크론은 `CRON_SECRET`으로 이미 자기 관문을 지난다.
- ⚠️ **팀은 Host로 해석하지 않고 파라미터로 받는다.** Vercel Cron이 부르는 요청의
  `x-forwarded-host`가 `*.vercel.app`이면 `extractTeamCdFromHost`가 `vercel`을 팀코드로 읽어
  **`DEFAULT_FALLBACK_TEAM_ID`로 조용히 떨어진다.** 팀이 하나뿐인 지금은 우연히 맞지만,
  "우연히 맞는 것"에 회비 감면을 걸어 둘 수는 없다. `batch_job_mst`에 `team_id`를 두거나
  `param_json`으로 넘긴다.
- **`aprv_by_mem_id`는 null을 허용**하고 화면에서 "자동"으로 표시한다(`batch_run_hist.trig_by`가
  이미 같은 방식이다).

### 3.2 `cron_expr`을 곧이곧대로 파싱하면 KST에서 틀린다

`0 15 1 * *`는 **UTC 매월 1일 15시 = KST 2일 자정**이다. 의도한 "KST 1일 자정"은 UTC로
**전월 말일 15시**인데, 말일이 28~31로 변해 표준 cron으로 표현이 안 된다.

**그래서 cron 표현식을 평가하지 않는다.** 대신 **"이번 주기에 이미 성공했나"**를 본다:

```
freq_cd = 'daily'    → 오늘(KST) success 이력이 없으면 실행
freq_cd = 'monthly'  → 이번 달(KST) success 이력이 없으면 실행
freq_cd = null       → 자동 실행 안 함 (수동 전용)
```

- **크론이 하루 밀리거나 실패해도 다음 날 따라잡는다**(catch-up). cron 표현식 방식은 그 시각을
  놓치면 다음 주기까지 통째로 건너뛴다.
- **단장이 먼저 손으로 돌렸으면 자동은 그냥 건너뛴다** — 멱등성이 공짜로 따라온다.
- `cron_expr`은 **화면 표시용으로 남긴다**(지우면 관리자 화면에서 주기를 못 보여 준다).

```sql
alter table batch_job_mst add column freq_cd varchar;  -- 'daily' | 'monthly' | null
```

### 3.3 `MILEAGE_TITLE_BATCH`의 `evt_id`

`evt_id`는 **어떤 마일리지런 시즌을 대상으로 돌릴지**다(`evt_team_mst` 한 행 = 시즌 하나).
코드는 이걸 **필수**로 요구하는데 `param_schema_json`에는 없다 — 관리자가 드롭다운에서 고르는
값이라서다. 크론에는 고를 사람이 없다.

**규칙: 기준 월에 걸치는 `ACTIVE` 시즌을 전부 돌린다.** 하나면 하나, 여럿이면 각각.

- 시즌마다 참가자·목표가 독립이고, **중복 부여는 엔진이 이미 막는다**(보유 중이면 스킵)
- **하나도 없으면 스킵한다** — 마일리지런이 안 도는 기간이라 실패가 아니다. 이력을 남기지 않는다

> `batchMileageTitles`가 **이미 기준 월 겹침을 필터한다**
> (`stt_dt <= 기준월말 AND end_dt >= 기준월초`). 그래서 안 겹치는 시즌을 넘겨도
> `"평가 대상 참여자 없음"`으로 조용히 끝난다 — 엉뚱한 시즌에 칭호가 나갈 위험이 없다.
> 이 필터가 있어서 "여럿이면 위험하니 멈춘다"는 방어가 필요 없어졌다.
>
> prd 실측(2026-08-14): `evt_team_mst` **ACTIVE 1건**(`26 마일리지런 시즌4`, 2026-05-01~09-30).
> 시즌제라 겹치는 일이 드물지만, 규칙이 "전부"면 겹쳐도 사람이 개입할 일이 없다.

`base_month` 같은 나머지 파라미터는 **`param_schema_json`의 `default`를 크론이 해석**한다
(`"default": "prev_month"`가 이미 들어 있다 — 처음부터 이걸 염두에 둔 스키마다).

### 3.4 자동이 되면 실패를 아무도 모른다

지금은 수동이라 **화면에서 결과를 바로 본다.** 자동으로 돌면 조용히 실패하고, 다음 달에
"감면이 왜 안 됐지"로 발견된다.

→ **`status = 'failed'`면 운영진에게 알림**(`insertNoti`). 배치는 자주 실패하지 않으므로
시끄러워질 걱정은 없고, 실패를 못 보는 쪽이 훨씬 비싸다.

### 3.5 동시 실행과 좀비 `running`

`status = 'running'`인 행이 있으면 같은 job을 다시 시작하지 않는다. 다만 **함수가 타임아웃으로
죽으면 `running`이 영영 남아** 그 job이 영원히 막힌다.

→ **30분 넘은 `running`은 무시하고 새로 시작**한다(그 행은 `failed`로 마감). 잠금을 완벽하게
만들려고 별도 락 테이블을 두는 건 배치 4개짜리 규모에 과하다.

### 3.6 회비 잔액 반영은 자동화하지 않는다 — 사람이 보는 관문이다

`batchDuesExemption`은 면제 행을 **`rflt_yn = false`로 INSERT만 하고 잔액은 건드리지 않는다.**
실제 반영은 관리자가 `recalculateBalance()`를 돌릴 때 `rflt_yn = false`를 합산·마킹하며 일어난다.

**이건 빠뜨린 게 아니라 의도된 순서다.** 배치를 자동으로 돌려도 이 경계는 그대로 둔다:

```
[자동] 감면 배치 → 면제 행 적재(rflt_yn=false)
                    ↓
[사람] 감면이 제대로 돌았는지 결과 확인   ← §4 결과 화면이 이 판단의 근거다
                    ↓
[사람] 재계산 → 잔액에 반영
```

- **돈이 걸린 값이라 한 번은 사람 눈을 거치는 게 맞다.** 감면이 잘못 계산되면 회원 잔액이
  틀어지고, 그건 조용히 넘어가면 안 되는 종류의 오류다.
- 감면 배치가 실패하거나 이상한 수치를 내도 **잔액은 아직 안 움직인 상태**라 되돌릴 게 없다.
- 그래서 **§4의 결과 가시성이 여기서 값을 한다** — "34명 중 5명 감면"이 지난달과 비슷한지,
  누구에게 얼마가 붙었는지를 보고 재계산을 누른다. 화면이 약하면 이 관문이 형식만 남는다.

> 반대로 **칭호는 사람이 볼 이유가 없다** — 틀려도 배지 하나고, 비회수라 되돌릴 일도 드물다.
> 그래서 칭호 배치는 부여까지 완전 자동이고 회비만 관문을 둔다. **자동화의 경계를 "되돌리기
> 비용"으로 긋는다.**

### 3.7 수동 실행은 그대로 남는다 — 자동은 얹는 것이지 대체가 아니다

**`/admin/system/batch`의 실행 버튼은 모든 job에 계속 있다.** 자동으로 도는 job도 마찬가지고,
새로 등록하는 칭호 배치 2종도 여기서 손으로 돌릴 수 있다(오히려 그게 덤이다 — 재계산이 필요할 때
배포 없이 대응된다).

| | 자동 | 수동 |
|---|---|---|
| 진입점 | `/api/cron/batch` | 관리자 화면 |
| **주기 체크(§3.2)** | **한다** — 이번 주기에 성공했으면 스킵 | **안 한다** — 눌렀으면 돈다 |
| 파라미터 | `param_schema_json`의 `default`로 채움 | 관리자가 폼에서 지정(과거 월 소급 등) |
| 이력 | `trig_type='auto'`, `trig_by=null` | `trig_type='manual'`, `trig_by=관리자` |

> ⚠️ **주기 체크를 수동에도 걸면 안 된다.** "이번 달 이미 성공함"으로 막아 버리면 **자동이 한 번
> 돈 뒤에는 손으로 다시 못 돌린다** — 결과가 이상해서 다시 돌리고 싶을 때가 정확히 그때다.
> 주기 판정은 **크론이 자기 차례인지 정하는 규칙**이지 job의 실행 조건이 아니다.

> **두 번 돌아도 안전하다.** 감면은 같은 달 퀘스트 면제가 이미 있으면 스킵하고
> (`alreadyGranted`), 칭호는 보유 중이면 스킵한다. **재실행이 안전한 게 수동 버튼을 남겨 둘 수
> 있는 근거**다 — 멱등이 아니었다면 자동화하는 순간 수동 버튼을 치워야 했다.

동시 실행만 막는다(§3.5) — 수동으로 도는 중에 크론이 뜨면 크론이 스킵하고, 그 반대도 같다.

### 3.8 실행 시간 — Vercel 함수 타임아웃

sweep 계열은 팀 전원 × 조건 수를 도는 작업이라 수십 초가 걸릴 수 있다. Vercel 함수 기본
타임아웃에 걸리면 **중간에 잘리고 `running`만 남는다**(§3.5).

→ 라우트에 `maxDuration`을 명시하고, 그래도 모자라면 **job을 쪼갠다**(칭호 일 배치는 "3일 전에
끝난 모임의 참석자"만 보므로 애초에 대상이 좁다 — §7.2 참조).

## 4. 실행 결과를 눈으로 확인하기

자동으로 돌기 시작하면 **결과 화면이 유일한 창구**가 된다. 지금은 그게 약하다.

### 4.1 무엇이 약한가

배치는 내부적으로 꽤 세밀한 집계를 갖고 있다 — `batchDuesExemption`만 해도
`granted` · `skippedZero` · `alreadyGranted` · `skippedInactive` · `errors`를 따로 센다.
그런데 이걸 **전부 한국어 문장 하나로 뭉쳐** `result_msg`에 넣는다:

```
대상 월 2026-07: 34명 중 5명 감면 부여, 27명 미해당, 2명 기존 부여(스킵)
```

| 문제 | 결과 |
|---|---|
| 자유 텍스트라 **집계·비교가 안 된다** | "지난달보다 감면이 줄었나"를 눈으로 세야 한다 |
| **누구에게 무슨 일이 있었는지 없다** | `fee_due_exm_hist`·`mem_ttl_rel`을 따로 뒤져야 하고, **어느 실행이 만든 행인지 연결 고리가 없다** |
| **"성공 + 변화 0"과 "성공 + 5건"이 같은 초록 배지** | 대상이 없어 아무것도 안 한 실행이 정상 수행처럼 보인다 |

### 4.2 `batch_run_hist.result_json` (신규 컬럼)

```sql
alter table batch_run_hist add column result_json jsonb;
```

`result_msg`는 **그대로 둔다** — 한 줄 요약으로 쓸모가 있고, 지우면 기존 이력이 빈칸이 된다.

```jsonc
{
  "metrics": { "대상": 34, "부여": 5, "미해당": 27, "기존보유": 2 },
  "changes": [
    { "mem_nm": "홍길동", "what": "7월 회비 감면 4,000원" },
    { "mem_nm": "김철수", "what": "칭호 '미라클' 부여" }
  ],
  "warnings": ["활성 시즌이 둘이라 각각 돌렸습니다"]
}
```

> **`metrics`는 고정 필드가 아니라 라벨→숫자 맵이다.** 배치마다 세는 게 다른데
> (`부여/미해당/기존보유` vs `평가/부여`) 컬럼을 고정하면 **배치를 추가할 때마다 UI를 고쳐야
> 한다.** 화면은 키를 모른 채 칩으로 그리기만 하면 되므로, 새 배치가 자기 지표를 그냥 실어 보낸다.

> **`changes`에는 실제로 바뀐 대상만 담는다.** 수백 명을 훑어도 대부분은 무변화라, 전부 담으면
> jsonb만 커지고 정작 볼 게 묻힌다. **200건을 넘으면 자르고 `"truncated": true`를 남긴다** —
> 그 이상은 원본 테이블을 보는 게 맞다.

이러려면 배치 핸들러의 반환 타입이 바뀐다:

```
Promise<string>  →  Promise<{ msg: string; metrics?: …; changes?: …; warnings?: … }>
```

기존 핸들러 2개(`batchDuesExemption` · `batchMileageTitles`)를 함께 고친다. 둘 다 셀 것을 이미
세고 있어서 **반환만 바꾸면 된다** — 새로 집계할 게 없다.

### 4.3 화면

| 자리 | 지금 | 바꿀 것 |
|---|---|---|
| 카드 상단 | 최근 실행 시각 · 상태 · 소요 | 그대로 + **핵심 지표 칩** |
| 이력 행 | 트리거·상태 배지 + 시각 + `result_msg` 한 줄 | + **`metrics` 칩**, **직전 성공 대비 증감**(▲2 ▼1) |
| 이력 행 펼침 | 없음 | **`changes` 목록**(누구에게 무엇이) + `warnings` |
| 상태 배지 | `running`/`success`/`failed` | + **변화 0이면 회색 "변화 없음"** |

- **증감은 같은 job의 직전 `success` 실행과 비교**한다. 월 배치는 이게 곧 "지난달 대비"라,
  숫자 하나로 이상 징후가 잡힌다(감면이 5명 → 0명이면 뭔가 잘못된 것이다).
- **`status`의 CHECK 제약은 건드리지 않는다.** "변화 없음"은 별도 상태가 아니라
  `metrics`의 변화 건수가 0인 `success`다 — enum을 늘리면 기존 행 마이그레이션이 따라온다.

> **실패 알림(§3.4)도 이 구조를 쓴다.** 알림 본문에 `result_msg` 한 줄을 실으면, 관리자 화면에
> 들어가기 전에 무엇이 실패했는지 알 수 있다.

## 5. 구현 순서

1. `batch_job_mst.freq_cd` 컬럼 추가 + 기존 2건에 `'monthly'` 설정
2. `executeBatch()` 분리 — `runBatch()`는 이걸 감싸는 얇은 래퍼로.
   **핸들러에서 `withAdminOrThrow`를 걷어내고 `team_id`를 파라미터로** 받게 바꾼다(§3.1)
3. `/api/cron/batch` 라우트 — `CRON_SECRET` 검증(`newbie-nudge`와 같은 패턴) → 대상 job 조회 →
   순차 실행. `vercel.json`에서 **`keep-alive` 항목을 이 경로로 교체**하고
   `app/api/cron/keep-alive/route.ts`를 삭제한다(크론 수 2개 유지)
4. 실패 알림 + 좀비 `running` 정리
5. **`result_json` 컬럼 + 핸들러 반환 타입 변경 + 관리자 화면 보강**(§4)
6. 칭호 배치 2종을 `batch_job_mst`에 등록(칭호 조건 구현이 끝난 뒤)

1~4는 칭호와 무관하게 **그 자체로 회비 감면·마일리지런 자동화를 끝낸다.** 5는 자동화가 돌기
시작한 뒤에 해도 되지만, **자동으로 돌수록 화면이 유일한 창구가 되므로** 너무 미루지 않는 게 좋다.
6은 칭호 작업이 끝나는 시점에 얹는다.
