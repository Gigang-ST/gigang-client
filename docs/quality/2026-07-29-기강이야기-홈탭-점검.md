## QS-13 — 댓글 알림 딥링크 `?rec=`가 오래된 글에서 무반응 · P1 · 6.이음새

- [ ] 확인

**증상**: "내 운동기록에 새 댓글" 알림을 눌렀는데 릴스가 안 열리고 전광판 맨 위만 뜬다.
주소창엔 `?rec=<post_id>`가 멀쩡히 붙어 있어, 사용자에겐 "알림이 고장났다"로 읽힌다.
`deep-link.ts` 주석이 경계하던 바로 그 상태 — *주소는 살아 있는데 화면이 안 뜬다* — 가
`/schedule` 대신 `/story` 안에서 재발한 것이다.

**재현** (dev, 로그인 상태):

1. `/story?rec=73c18a0e-ff07-43f2-8d36-384b18c7fa92` 로 접속한다 → **릴스가 안 열린다**.
2. 대조군: `/story?rec=<격자 첫 16칸 안의 post_id>` → 릴스가 정상으로 열린다.
3. 1번 주소에서 깅스타그램 격자를 오른쪽 끝까지 민 뒤(더보기가 발동) 다시 접속하면 열린다 —
   즉 "목록에 있으면 열리고 없으면 안 열린다"가 확인된다.

> 위 post_id는 점검 시점 dev에서 가장 오래된 기록이다(당시 20건 → 이후 1건 추가돼 21건.
> 순위는 밀리지만 여전히 16번째 밖이라 재현 조건은 그대로다). 첫 묶음은 16건
> (`STORY_POST_LIMIT`)이므로 17번째부터가 사각지대. **점검 시점 dev에는 17번째 이후 글에
> 달린 댓글이 0건이라 실사용 재현은 아직 없다** — 위 1번처럼 주소를 직접 넣어야 보인다.
> 기록이 쌓일수록(그리고 오래된 글에 댓글이 달릴수록) 자연 발생 확률이 올라가는 잠복 결함이다.

**근거**: [record-flex-feed.tsx:142](../../components/story/record-flex-feed.tsx#L142)
— `all.some((p) => p.post_id === recParam)`이 참일 때만 뷰어를 연다. `all`은 서버가 준 첫
16건 + 사용자가 스크롤해서 이어붙인 것뿐이다. RPC 인자는 `(p_team_id, p_limit, p_offset)`뿐이라
단건 조회 경로 자체가 없다([20260728110000:122](../../supabase/migrations/20260728110000_post_photo_required_and_mlg_photo.sql#L122)).

**원인**: 코드 주석은 "못 찾으면 `handledRec`을 굳히지 않고 목록에 나타나는 순간 열리게 둔다.
사용자가 스크롤하면 자연히 채워지고, 안 하면 지면을 보는 것이라 손해가 없다"고 판단했다.
그 전제가 틀렸다 — **알림을 눌러 들어온 사람은 스크롤할 이유를 모른다.** 목적지가 안 열린
채로 지면을 보는 건 "손해 없음"이 아니라 실패다.

**제안**: 목록에 없으면 그 한 건을 따로 받아온다. 둘 중 하나.
- (a) `get_team_posts`에 `p_post_id` 인자를 추가해 단건 조회 → 액션으로 노출.
- (b) 단건 조회 전용 서버 액션 신설(`getPostById`) → 받은 글을 `all` 맨 앞에 주입해 릴스를 연다.

(a)가 RPC 하나로 끝나 얇지만 시그니처가 바뀌므로 배포 순서 주의(§배포 주의). (b)는 격리가
깨끗하다. 어느 쪽이든 **못 찾았을 때의 폴백 안내**(토스트 "이미 삭제된 기록이에요")도 함께 둘 것 —
지금은 삭제된 글의 알림을 눌러도 조용히 아무 일도 안 일어난다.

## QS-14 — 서버 렌더 KST 어긋남 · P1 · 2.신뢰

- [ ] 확인

**증상**: **KST 00:00~09:00** 사이에 접속하면 서버가 그린 첫 HTML이
① 제호 날짜가 **어제**, ② 대회 D-day가 **하루 밀림**, ③ 매월 1일 새벽엔 활동량 라벨이 **지난달**,
④ 새얼굴 "최근 30일" 경계가 하루 어긋남 — 으로 나온다. 이어서 브라우저가 하이드레이션하며
값이 달라 React 불일치가 나고, 그 서브트리가 다시 그려진다(화면이 한 번 튄다).

**재현**: 셋 중 편한 것.
- (a) 로컬에서 `TZ=UTC pnpm run build && TZ=UTC pnpm run start` 후 `/story` 접속 → 제호 날짜가
  KST 기준 오늘과 다른지 확인(한국 시간 오전 9시 전이면 어제로 찍힌다).
- (b) 배포본(Vercel=UTC)에 KST 새벽에 접속 → **뷰 소스**(SSR HTML)의 제호 날짜와, 화면에
  최종 렌더된 날짜를 대조. 콘솔에 hydration mismatch 경고가 뜬다.
- (c) 단위 확인: Node에서 `TZ=UTC` 로 `dayjs().format("YYYY-MM-DD")` 와
  `todayKST()` 를 새벽 시간대 값으로 비교.

**근거**: `lib/dayjs.ts`는 KST 헬퍼(`todayKST`/`nowKST`)를 제공하지만
**`dayjs.tz.setDefault`를 부르지 않는다**(전 저장소 grep 결과 0건). 따라서 tz 없는 `dayjs()`는
실행 환경 로컬 타임존을 쓴다 — 브라우저=KST, Vercel 서버=UTC. 스토리 렌더 경로에서 "오늘"을
tz 없이 판정하는 곳:

| # | 위치 | 무엇이 틀어지나 |
|---|---|---|
| 1 | [story-masthead.tsx:30](../../components/story/story-masthead.tsx#L30) | 제호 날짜 |
| 2 | [story-lede.tsx:223](../../components/story/story-lede.tsx#L223) `withinDays` | 새얼굴 30일 창 |
| 3 | [member-card.ts:124](../../lib/member-card.ts#L124) `getRaceDday` | 리드 D-day |
| 4 | [activity-index.ts:47](../../lib/activity-index.ts#L47) `getActvMonthLabel` | "N월 기강 활동량" |
| 5 | [member-card.ts:115](../../lib/member-card.ts#L115) `isNewRecord` | 기록 NEW 배지(90일) |
| 6 | [member-card.ts:132](../../lib/member-card.ts#L132) `getDaysSinceJoin` | 프로필 "N일째" |
| 7 | [story-pulse.tsx:66](../../components/story/story-pulse.tsx#L66) | months 빈 경우 월 라벨 폴백 |

3·5·6은 프로필 카드 등 **스토리 밖에서도 공용**이라 영향 범위가 이 지면을 넘는다.

**원인**: `AGENTS.md`·`QUALITY-BAR.md` 2.신뢰가 "시각·날짜 KST 고정(`lib/dayjs`만 사용)"을
규정하는데, `lib/dayjs`에서 **`dayjs` 인스턴스 자체를 재export**하다 보니 `import { dayjs }`만
지키면 규칙을 지킨 것처럼 보인다. 실제 위반은 "tz 없는 `dayjs()`로 *오늘*을 판정"하는 쪽이다.

**제안**: 두 단계.
1. 위 7곳을 KST 헬퍼로 교체(`dayjs()` → `nowKST()` 계열, 포맷은 그대로).
2. 재발 방지 — `nowKST()`를 export하고, 린트 룰이나 `lib/dayjs` 주석으로 "**오늘/지금 판정에는
   `dayjs()`를 쓰지 않는다**"를 명문화. 표시용 `dayjs(값)` 파싱은 그대로 둬도 된다(값에 오프셋이 있음).

> 메모리의 "형제 경로 전수 적용" 원칙 대상이다. 이 지면만 고치지 말고
> `rg "dayjs\(\)\.(startOf|diff|format)"` 로 같은 패턴을 전수 확인할 것.

## QS-15 — 피드 payload의 71%가 화면이 안 쓰는 데이터 · P1 · 1.첫인상

- [ ] 확인

**증상**: 눈에 보이는 증상은 없다. 다만 `/story`는 쿠키를 읽어 dynamic이므로 **매 방문마다**
45KB짜리 RSC payload가 내려가고, 그중 32KB가 화면이 절대 읽지 않는 필드다. 모바일·저속망에서
첫 화면 도달을 늦춘다.

**재현 / 실측** (dev, 아래 SQL 그대로):

```sql
WITH f AS (SELECT public.get_team_story_feed('c0ffee00-0000-4000-8000-000000000001'::uuid) AS j)
SELECT length((SELECT j FROM f)::text)                       AS feed_bytes,       -- 44,879
       jsonb_array_length((SELECT j->'actv_rank' FROM f))    AS actv_rank_rows,   --     68
       length((SELECT j->'actv_rank' FROM f)::text)          AS actv_rank_bytes,  -- 31,894
       length((SELECT j->'week_stat' FROM f)::text)
     + length((SELECT j->'month_rank' FROM f)::text)         AS unused_bytes;     --    714
```

브라우저 쪽 대조: DevTools Network에서 `/story` 문서 응답 크기와, 그 안 RSC 페이로드에
`best_records` / `running_profile` 문자열이 68명분 들어 있는지 확인.

**근거**: RPC가 `actv_rank` **전원**에게 `best_records`(종목별 최고기록 4종)·`running_profile`·
`primary_title`·`mth_*_cnt`를 실어 준다([20260728100000:194-278](../../supabase/migrations/20260728100000_story_feed_record_comp_link.sql#L194)).
그런데 소비처는 둘뿐이다.

- 리드 활동지수 슬롯: **상위 3명 중 1명**만, 그것도 `parts: ["title", "intro"]`뿐 —
  `best_records`·`running_profile`은 아예 안 그린다([story-lede.tsx:515](../../components/story/story-lede.tsx#L515),
  [person-profile.tsx:124](../../components/story/person-profile.tsx#L124)에서 `bestRecord` 필터로 버림).
- 무더기 `ActvPile`: `mem_id`·`mem_nm`·`avatar_url`·`actv_score`만 쓴다([actv-pile.tsx](../../components/story/actv-pile.tsx)).

즉 68명 × (최고기록 4종 + 러닝프로필)을 실어 보내 **최대 3명분의 칭호·소개만** 쓴다.
DB 실행시간은 45ms로 문제없다 — 병목은 쿼리가 아니라 **전송량**이다.

**제안**: RPC에서 무거운 부품을 `rn <= 3` 행에만 채운다(그 외는 `null`). 클라 타입은 이미 전부
옵셔널이라([story-feed.ts:126](../../lib/queries/story-feed.ts#L126)) **앱 코드 변경 없이** 적용된다.
예상 절감 약 28KB/요청(−60%).

덧붙여 `week_stat`·`month_rank`는 어느 화면도 안 읽는다(→ QS-21). 같은 개정에서 함께 걷어내면
CTE 5개 스캔도 사라진다.

## QS-22 — 리드 사진 슬롯이 빈 `src`를 그린다 · P2 · 2.신뢰

- [ ] 확인

> QS-13 수정 중 dev 서버 로그에서 발견(2026-07-29). 점검 본문에는 없던 항목이다.

**증상**: 리드 운동기록 슬롯의 사진 URL이 없으면 `<Image src="">`가 그려진다. Next가 경고를
띄우고(`An empty string ("") was passed to the src attribute`), 브라우저는 **현재 페이지 URL을
이미지로 다시 요청**한다 — 문서를 이미지로 받으려다 실패해 깨진 아이콘이 뜨고 요청 한 번이 샌다.

**재현**: dev 서버를 재시작하고 첫 요청으로 `/` 또는 `/story`를 연다 → 서버 로그에 위 경고가
찍힌다(캐시가 데워진 뒤 요청에는 안 나온다).

**근거**: [story-lede.tsx:1081](../../components/story/story-lede.tsx#L1081) — `src={lede.photo.url ?? ""}`.
저장소 전체에서 Image `src`에 `?? ""`를 쓰는 곳은 여기 **한 곳뿐**이고, 형제 컴포넌트 둘은
정확히 이걸 하지 말라고 주석에 적어 두고 값이 없으면 아예 안 그린다:

- [record-flex-feed.tsx:333](../../components/story/record-flex-feed.tsx#L333) — `{p.photo_url && <Image …>}`
  ("`?? ""`로 때우지는 않는다: 빈 src는 브라우저가 **현재 페이지 URL을 다시 요청**하게 만들어…")
- [record-reel-viewer.tsx:331](../../components/story/record-reel-viewer.tsx#L331) — `{bgSrc && …}` (같은 주석)

`Avatar`는 `src?.trim() || null`로 빈 문자열을 걸러내므로 원인이 아니다(확인함).
DB에도 빈 문자열은 없다(dev: `photo_url = ''` 0건, NULL 20건은 RPC가 정상적으로 거른다).

**원인**: 평소에는 `get_team_posts`의 `photo_url IS NOT NULL` 필터가 막아 줘서 이 `?? ""`가
드러나지 않는다. 그런데 `getStoryPosts`는 `unstable_cache`라 **필터가 생기기 전의 payload가
캐시에 남아 있으면** 사진 없는 기록이 그대로 내려온다(`team-overview.ts`가 "캐시에 남은 옛
payload"를 경고하는 것과 같은 함정). 서버 재시작 직후 첫 렌더에만 경고가 뜨고 이후엔 안 뜨는
것이 그 증거다. 즉 **RPC 필터에만 기대고 있고 클라이언트 방어가 이 한 곳만 빠져 있다.**

**제안**: 형제와 같게 맞춘다 — 사진이 없으면 `<Image>`를 그리지 않는다(빈 판 `bg-muted`만 남긴다).
`?? ""`는 어떤 경우에도 두지 않는다.
